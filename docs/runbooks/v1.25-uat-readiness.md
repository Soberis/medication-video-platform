# V1.25 UAT Readiness Runbook

> 状态：HISTORICAL / V1.25 UAT 准备手册。本文保留历史现场准备模板，不定义 V1.27 当前验收；当前范围、唯一 CaptureGroup 主链和 `training-data.v3` 以 [V1.27 正式需求基线](../requirements/baselines/V1.27/配药视频数据管理平台需求文档_V1.27.md) 为准。

> 本文件是供医院/客户用户执行的 UAT 准备包，不是 UAT 结果。所有 `PASS`、`FAIL`、`Issue ID` 和签名栏必须由现场执行人填写；开发机或 synthetic service E2E 结果不能替代 UAT。

## 1. 范围与执行方式

本手册覆盖 V1.25 新 CaptureGroup 主链：

```text
显式 CaptureGroup
→ Receipt
→ per-view Media/Quality
→ CaptureGroup Quality
→ 一个 AnnotationTask / 一条 AnnotationRevision 链
→ Review
→ 事件级 Cleaning
→ training-data.v3 preview/export
```

每个 UAT case 使用独立的、获授权的测试事件和证据包。不要复用生产事件、患者身份映射、生产凭据或真实医院密钥。V1.25 的 `N=1` 仍必须走 CaptureGroup 路径，不切换到 V1.24 的历史单视频任务路径。

执行顺序：

1. 环境负责人冻结版本、环境、账号、数据授权和相机配置。
2. 管理员完成项目与成员准备；三类角色使用不同账号，不共享密码或令牌。
3. 操作员按 A–J 执行，每个 case 单独保存必需证据。
4. 独立复核员确认 Review 相关 case；环境负责人汇总问题和退出结论。

仓库已有的 [Synthetic E2E 记录](../architecture/v1.25-synthetic-service-acceptance-2026-08-28.md) 只能作为开发/部署前置参考，`Synthetic E2E != UAT`，不得复制其结果填入本手册。

## 2. 角色与权限

| 角色 | 责任 | UAT 账号要求 |
| --- | --- | --- |
| Administrator | 建立/确认项目与 CameraSet、管理成员、检查组事实；执行需要管理员权限的 Cleaning 与 training-data.v3 预览/导出 | 全局 `ROLE_ADMIN`，并有目标项目 ACTIVE `ADMIN` membership |
| Annotation operator | 接收/查看事件、逐视图 Quality、提交 group quality、选择 Primary View、提交 AnnotationRevision | 目标项目 ACTIVE member；提交 Revision 时必须是该 task 的 assignee |
| Independent reviewer | 独立审阅正式 AnnotationRevision，记录 `APPROVED`/`REJECTED` | 使用与操作员不同的账号。当前契约要求全局 `ROLE_ADMIN` + 目标项目 ACTIVE `ADMIN` membership；若客户权限模型不允许，先记录配置缺口，不绕过权限 |

管理员可以承担操作员角色，但若要验证“独立复核”，必须使用不同账号、不同人员，并在证据中记录实际 actor。不得临时给操作员提权后把结果当作独立复核。

## 3. 前置条件清单

开始 UAT 前，环境负责人将下表每项标为 `READY` 或记录 Issue；这里不填写实际结果。

| 类别 | 必须确认 |
| --- | --- |
| 授权数据 | 有书面 data authorization/privacy approval、允许的用途和保留期限；测试媒体已脱敏或明确批准使用；禁止使用未授权患者/医院数据 |
| 项目与账号 | 专用 UAT project；Administrator、Annotation operator、Independent reviewer 账号均启用；ACTIVE membership 和角色已核对；项目隔离测试账号/项目已准备 |
| 版本与服务 | 记录 Core API、Web、Media Worker、AI Worker（如启用）、数据库 migration/schema、部署版本和配置摘要；PostgreSQL、对象存储、RabbitMQ、Worker 队列和日志可观测 |
| 相机配置 | 记录冻结的 CameraSetSnapshot、expected camera numbers、camera role/channel；编号稳定，缺号不重排；为 C/D 准备可解释的缺失/差质量事件 |
| 媒体 | 每个 case 的来源授权、文件清单、期望 Media Probe 结果和事件时间已登记；不得把文件路径、预签名 URL 或令牌放进证据 |
| 浏览器/终端 | 使用目标桌面浏览器和准确版本；记录 OS、浏览器、viewport、缩放比例、显示器、网络/代理/TLS；移动端不在本轮范围。目标浏览器矩阵若尚未由客户冻结，记录为待决策而不是宣称兼容 |
| AI（仅 E） | AI Worker、批准模型/profile、模型 hash 和适用 camera role 已部署；若 AI 不在本次授权范围，E 必须标为 `N/A + approved deviation`，不能标为 PASS |
| 隐私与证据 | 已确定证据存储位置、访问人、保留/删除责任；截图只截状态、编号和错误信息，裁剪/遮盖不必要的视频画面、患者信息和身份信息 |

## 5. 五类评估分开记录

一个 case 不能用单一总分掩盖不同风险。每类单独填写 `PASS / FAIL / N/A + 批准偏差`、证据位置和 Issue ID。

| 维度 | 只评估什么 | 不应混入什么 |
| --- | --- | --- |
| System correctness | Receipt、Quality、Group Quality、task/revision 唯一性、Primary 冻结、Review/Cleaning 闸门、权限、保留、View Set 和导出 provenance 是否正确 | 操作员是否觉得页面易懂、AI 准确率、响应时间 |
| Operator usability | 目标角色能否理解状态、找到下一步、完成操作；错误信息、导航、可见性和培训负担 | 把“页面难用”改写成业务事实错误，或因体验问题宣称系统状态错误 |
| AI effectiveness | Candidate 的检测质量、`NO_HAND_DETECTED` 是否与现场观察一致、模型/profile provenance 和可解释性 | AI 结果不能替代人工 Quality/Revision/Review；无手不应自动阻断人工路径 |
| Performance | 上传、Media Probe、Candidate、页面/API 响应、Revision/Review/Cleaning/导出耗时和并发观察 | 没有预先约定的容量目标时，不把一次慢请求直接归为业务失败 |
| Deployment/environment | 浏览器/OS、网络/TLS、对象存储、RabbitMQ、Worker、配置、日志、监控、备份/保留和升级回滚 | 用 synthetic 本地环境结果代替目标医院部署结论 |

## 6. 强制证据模型

每个 case 至少保存一份可追溯证据包，字段如下：

- `uat_run_id`、产品/部署版本、Git commit 或不可变构建标识、环境标识、执行日期；
- project ID、CaptureGroup/event ID、expected/present/missing camera numbers；
- Receipt、各 view 的 media/quality/Candidate 状态及 reason/provenance；
- group-quality result、revision、reviewer、decided_at、confirmed View Set/input version；
- AnnotationTask ID、`assignee_actor_id`、`created_by`、Primary View、AnnotationRevision ID/number；
- Review decision、reviewer actor、时间、reason；Cleaning ID/result、参与/排除 cameras；
- training-data.v3 schema、export identifier/digest（如系统提供）和读取时间；
- 实际 operator/reviewer/admin、时间、浏览器/环境；Issue ID、日志/截图位置。

截图只保留能证明状态、编号、权限错误或导出元数据的最小画面；裁剪、遮盖或使用无敏感内容的状态面板。不得保存密码、令牌、预签名 URL、原始患者画面或不必要的身份信息。

## 7. Issue classification

| 等级 | 定义与处置 |
| --- | --- |
| `BLOCKER` | 无法开始或继续 UAT、出现隐私/安全风险、数据不可控或环境不可用；停止受影响路径，未解决前不能 PASS |
| `CRITICAL` | 权威 Receipt/Quality/Revision/Cleaning/export provenance 错误，或权限越界/数据泄露；停止发布判断并升级 |
| `MAJOR` | 必需业务路径无法完成、数据被错误排除/纳入或关键角色无法完成工作，但影响范围可界定；必须修复或有正式豁免 |
| `MINOR` | 不阻断业务且有可接受 workaround 的功能/显示问题；记录修复责任和版本 |
| `OBSERVATION` | 改进建议、性能/易用性观察或尚未构成失败的偏差；不能伪装成 PASS，也不自动阻断业务结论 |

## 8. UAT 退出标准

### PASS

- 本轮范围内 A–J 的所有 mandatory business paths 都有现场证据并通过；若某 case 经批准不在本次范围，必须记录 `N/A`、理由、批准人和后续计划，不能写成 PASS。
- 没有未关闭的 `BLOCKER` 或 `CRITICAL`；`MAJOR` 只有在有明确 workaround、责任人、期限和正式接受记录时才可放行。
- 权限/项目隔离、隐私、权威事实、append-only provenance 和 v3 导出关系均正确。
- 所有已知偏差已由指定业务/隐私/技术负责人正式接受；操作员 usability、AI effectiveness、performance、deployment/environment 的结论分别记录。

### FAIL

出现任一条件即为失败或停止签署：

- mandatory business workflow 无法完成；
- Receipt、Quality、Group Quality、Task/Revision、Review、Cleaning 等权威事实错误、被覆盖或不可审计；
- 权限越界、项目隔离失败、隐私/保留规则违反；
- 导出缺少组/视图/Revision/Cleaning provenance，或产生虚假的 supporting action timestamps；
- 没有足够证据证明结果，或用 synthetic/开发机结果冒充 UAT。
