## 1. 设计目标与边界

V1.27 的“连续”指用户在一个配药事件上下文中连续完成多个视图和阶段，不再为每个机位重复找路、选中和等待准备。系统负责准备可证明的事实、保持工作上下文并在服务端成功后定位下一项；人工仍负责所有专业判断和正式写入。

核心原则：

- 自动导航和准备，不自动作出最终医疗数据决定。
- 一次只突出一个当前任务和一个主操作。
- 只有服务端成功响应并刷新权威快照后，才允许自动进入下一项。
- AI 输出始终是事实、候选或“需关注”提示，不是 `QualityReview`、`CaptureGroupQualityReview`、`AnnotationRevision` 或 Review 结论。
- 继续复用 V1.26 的 `CaptureGroup`、逐视图质量、一个组任务、一条修订链、权限、审计和 provenance；不新增持久化 `next_action`、`blockers` 或通用工作流引擎。

本文描述目标交互和自动化边界，不预设新的领域状态、接口字段或技术实现。任何实现所需的 API 或事件变化，必须另行版本化并同步契约与测试。

## 2. 当前工作流问题

当前路径是：

```text
打开事件
→ 选择机位
→ 查看质量
→ 提交
→ 选择下一机位
→ 重复
```

该路径存在以下待验证的体验问题。它们是从当前交互序列推导出的设计假设，实际点击次数、等待时间和漏处理情况仍需 UAT 或产品遥测验证：

1. **重复建立上下文。** 用户每次都要重新选择机位，并自行确认当前选择是否仍属于同一个事件；机位数量较多时，事件身份、机位身份和未决状态之间不断切换。
2. **准备工作阻塞人工判断。** Media Probe、手部检测和候选准备如果由打开当前机位才触发，用户会在每路视频前重复等待，且无法提前知道下一路是否已准备好。
3. **事实与判断混在一起。** “媒体可读”“检测到手”“可能存在质量问题”和“人工质量结论”如果没有清晰分层，用户容易把自动提示当作已批准结果。
4. **手工下一步容易出错。** 用户可能跳过未决机位、重复提交已处理机位、误选相邻机位，或在提交尚未被服务端确认时提前切换，产生伪成功感。
5. **视图级流程和事件级流程断开。** 最后一台机位提交后，用户还要理解何时转到事件质量、任务或标注；“完成当前机位”没有自然衔接到“处理整个事件”。
6. **异步失败会放大认知成本。** 某一路媒体失败、候选失败、权限变化或并发修改时，当前路径缺少统一的停留、解释和恢复位置，用户只能回退或重新打开事件。
7. **审计边界容易模糊。** 如果“接受 AI 建议”被实现为后台自动通过，事后无法清楚区分系统观察、用户确认和正式业务写入。

## 3. 目标工作流

### 3.1 连续主链

目标路径如下：

```text
打开/恢复配药事件
→ 读取一轮权威事件快照
→ 系统为已收到的视图准备自动事实
→ 自动聚焦第一个当前用户未决视图
→ 人工查看当前视图与事实摘要
→ 人工确认质量，或处理异常并填写理由
→ 服务端成功后刷新权威快照
→ 自动聚焦下一未决视图
→ 所有视图质量完成后进入事件质量
→ 人工确认事件质量
→ 幂等创建/显示一个组任务
→ 人工选择主视图并提交事件级修订
→ 人工 Review
→ 系统执行确定性 Cleaning / 训练资格检查
```

用户在正常路径中不离开事件工作台，也不需要为每台相机单独创建任务。机位选择只在首次聚焦、异常处理、回看或用户明确要查看其他视图时发生；普通的“下一台”由服务端快照驱动。

### 3.2 正常路径与异常路径

自动准备层先给出简短事实摘要，例如“媒体可读”“检测到手部”“未发现明显需关注证据”。这只降低用户寻找证据的成本，不产生最终质量结论。

- **正常路径：** 用户查看当前视频和摘要后，点击一次明确的“确认当前机位”主操作。该点击写入用户有权提交的正式 `QualityReview`，不是后台接受 AI 结果。
- **异常路径：** 摘要缺失、事实冲突、媒体不可读、手部检测异常或用户发现画面问题时，主操作变为“处理当前机位异常”。用户查看证据，明确选择 `QUALIFIED`、`NEEDS_REVIEW` 或 `REJECTED`，并按既有契约填写理由；系统不得替用户选择结果。
- **不能确认路径：** 事实仍在准备、读取不完整或发生并发冲突时，停留在当前上下文并说明“状态暂不可确认”或“正在准备”，不得以默认值提交或跳到下一路。

“人只处理例外”不等于“正常情况由 AI 通过”。正常情况下仍保留一次可追溯的人工确认，只把准备、解释和导航从人工操作中移除。

### 3.3 连续作业的节奏

每一个视图质量循环只保留以下三个认知动作：

```text
看当前视图 → 判断自动事实是否足够 → 明确提交人工结论
```

提交后的刷新和下一视图定位不占用新的业务判断。最后一个视图完成后，主操作自然收敛为事件级质量；事件质量完成后，主操作自然衔接到组任务和事件级标注。任何阶段的正式结论仍是一道独立人工闸门，不能因为连续展示而合并成批量通过。

## 4. 自动动作

自动动作必须有明确触发事实、可安全重试、失败可恢复、结果可追溯，并且不能替代专业判断。以下动作沿用 V1.26 已允许的服务端能力和展示推导。

| 触发时机 | 自动动作 | 明确不做的事 |
| --- | --- | --- |
| 打开或恢复事件 | 读取同一轮的事件身份、receipt、视图集合、逐视图质量、组质量、任务状态和 capability；按服务端稳定顺序确定当前未决视图 | 不按文件名、上传顺序、时间邻近或浏览器缓存猜测归组和下一项 |
| 视图已收到且现有接收/作业规则允许处理 | 按现有规则幂等启动或继续 Media Probe；可处理的视图继续准备 MediaPipe Candidate | 不因某一路检测失败回写 receipt，也不因超时自动关闭多机位 receipt；逐视图准备不替代组 receipt finalize |
| 自动事实可用 | 为当前视图和其他已收到视图准备事实摘要：媒体可读性、手部检测、候选可用性、可能的质量关注证据及其 provenance | 不把事实摘要写成 `QualityReview`、组质量、正式标签或 Review |
| 用户处理当前视图期间 | 后台准备其他视图的自动事实；更新列表中的低权重准备状态 | 不自动播放、批量加载所有视频、改变用户正在查看的视图或抢夺键盘焦点 |
| 人工质量命令成功返回 | 重新读取权威快照，聚焦下一未决视图并以动态状态告知用户；若无未决视图则转向事件级质量 | 不在请求发出后提前切换，不复制结论，不自动提交下一路 |
| 有效事件质量成功返回 | 依照现有幂等规则创建并分配唯一组任务，直接显示标注工作上下文 | 不按机位创建多个任务，不自动选择主视图，不自动生成正式修订 |
| Review `APPROVED` | 依照冻结规则执行 Cleaning / 训练资格检查并展示结果和 provenance | 不提供人工选择 Cleaning 结果，也不把 Cleaning 结果改写为 Review 结论 |

### 4.1 自动事实包

自动准备层对每个已收到视图形成一个可解释事实包。以下是展示语义，不是新增持久化枚举：

| 事实 | 来源和表达 | 业务边界 |
| --- | --- | --- |
| `media_valid` | Media Probe 的媒体可读性、解码、时长等事实，并标注处理中/失败/未知 | 不能直接决定人工质量；失败只绑定该视图 |
| `hand_detected` | MediaPipe 对手部观测的事实，如检测到、未检测到、候选不可用 | `NO_HAND_DETECTED` 或候选为零不是“没有真实手”证明，除非服务端已有真实业务守卫，不得单独阻断 |
| `quality_hint` | 基于已有自动证据的可能质量关注提示、证据范围、置信/运行信息 | 只能提示“建议查看”，不能映射为最终 `QUALIFIED`、`NEEDS_REVIEW` 或 `REJECTED` |
| `provenance` | 输入版本、检测/模型运行标识、生成时间和可追溯关联 | 便于复核自动事实；不替代人工 actor、理由和提交时间 |

摘要缺少必要事实时显示“尚未准备好”或“状态暂不可确认”，不使用空值填充成“正常”，也不从旧浏览器状态补齐。

## 5. 人工检查点

连续展示只减少找路和重复确认，不减少以下正式闸门。

### 5.1 逐视图质量

当前视图必须由有权限的用户明确提交以下既有结果之一：

- `QUALIFIED`：确认该视图可以支持下游；
- `NEEDS_REVIEW`：证据不足或需要后续复核；
- `REJECTED`：确认该视图不参与下游，但保留媒体、候选、理由和审计。

自动摘要可以提供“建议查看”的上下文。用户不能仅因摘要显示“媒体有效/检测到手”就绕过视频判断；同样也不能仅因 `NO_HAND_DETECTED` 或候选失败被系统强制拒绝。正常确认和异常处理都要记录 actor、结果、理由（按现有契约）、输入事实版本和服务端时间。

### 5.2 事件质量

所有视图的可处理事实和 receipt 已按服务端规则关闭后，用户在事件级明确提交：

`QUALIFIED`、`QUALIFIED_WITH_EXCLUSIONS`、`NEEDS_REVIEW` 或 `REJECTED`。

系统可以汇总并解释当前视图集合，但不能根据“多数视图合格”、自动提示数量或相机数量替用户得出组结论。`INCOMPLETE` 事件只有在收件已显式关闭且人确认剩余视图足够时，才可提交 `QUALIFIED_WITH_EXCLUSIONS`；`RECEIVING` 时不得最终化为可标注的组质量。

### 5.3 主视图与事件级标注

事件进入唯一组任务后，用户明确选择 `primary/anchor view`，它只确定正式时间基准，不是事件 owner。之后以事件级任务进行标注：

- Candidate 和 MediaPipe 只能作为辅助 overlay 或候选证据；
- 用户必须人工创建、修改并提交正式 `AnnotationRevision`；
- 同一动作不因机位数量重复标注，不把主视图时间区间直接复制到支持视图；
- 只有已有且可验证的 `RELIABLE` 映射才可推导支持视图区间，并保留映射 provenance/version；近似或不可靠同步只作参考。

### 5.4 Review 与 Cleaning

Review 仍由人工完成，审阅组身份、参与/排除视图、主视图、动作区间和相关候选证据。Review 通过后由系统执行冻结规则的 Cleaning；连续工作流不得把 Review 和 Cleaning 合并为一个“完成”按钮，也不得让用户手工选择 Cleaning 的 PASS、WARNING 或 REJECT。

## 6. 多机位处理

### 6.1 机位集合和显示规则

- 机位数量 `N`、预期集合、已收到集合和稳定顺序均来自服务端 `CaptureGroup` 事实。
- `N=1` 时直接显示唯一视图，只保留低权重“机位 1”身份，不渲染无价值的切换流程。
- `N>1` 时使用紧凑、键盘可操作的机位选择器。默认只显示稳定机位编号、人工质量摘要、准备/异常提示和是否仍未决；技术详情和完整 ID 渐进披露。
- 缺失机位不重编号。缺少机位 2 时，机位 3 仍显示为机位 3；缺失行可解释接入事实但没有播放按钮。
- 普通路径只聚焦一个视频，不自动播放或同时加载全部视频。需要对照时，用户再明确打开支持视图。

### 6.2 自动聚焦规则

首次进入或刷新时：

1. 若 URL 或合法深链指定的视图仍可访问且未决，保留该视图；
2. 否则聚焦服务端稳定顺序中的第一个当前用户未决视图；
3. 若没有未决视图，选择第一个可用视图，并把主操作转向事件级质量、等待或完成结果。

逐视图质量提交成功后：

1. 等待服务端成功响应；
2. 重新读取同一事件的权威快照；
3. 从新快照计算下一未决视图并聚焦；
4. 若没有下一未决视图，进入事件级质量，而不是要求用户再点击机位或返回列表。

自动聚焦只改变界面选择，不提交结论、不批量复制结论、不自动播放、不改变任务归属。若当前视图仍在准备，系统可以继续准备其他视图，但不应无提示地跳过当前未决项；用户可通过紧凑选择器明确查看其他已准备视图。

### 6.3 事件级一致性

同一 `CaptureGroup` 始终只有一个组任务和一条正式修订链。逐视图质量可以独立完成，事件质量只提交一次组范围决定；支持视图是同一事件的参考证据，不产生第二份动作真值。迟到视图、视图质量变化或重新准备的候选不得静默改写已经提交的组质量和修订；若要纳入新事实，必须按照现有版本化规则重新提交并追加修订。

## 7. 错误处理

### 7.1 统一恢复原则

任何自动动作失败都遵守同一顺序：

1. 停留在最近一次可证明的事件和当前视图上下文；
2. 明确说明影响对象是整个事件、某一路视图、当前命令还是权限；
3. 在 `Current Action` 原位只提供一个最主要的恢复动作；
4. 恢复后重新读取权威快照；
5. 只有服务端确认成功，才允许继续自动聚焦或衔接下一阶段。

浏览器的本地选择可以帮助恢复界面，但不能补写服务端事实、覆盖版本冲突或显示伪成功。

### 7.2 场景处理

| 场景 | 连续工作流行为 | 人工恢复与边界 |
| --- | --- | --- |
| 事件快照读取失败 | 显示“状态暂不可确认”，保留事件身份和当前工作语境，但禁用会产生业务写入的主操作 | 用户执行“重新读取”；成功前不自动跳转、不使用旧快照完成提交 |
| Media Probe / MediaPipe 准备中 | 当前视图显示准备中；其他视图可在后台准备，正常事实不使用虚假百分比或倒计时 | 若视频仍可查看，用户可按现有 capability 人工判断；准备状态本身不等于合格或拒绝 |
| Media Probe 失败 | 只标记对应视图媒体失败，receipt 保持原事实，其他视图继续可用 | 提供既有媒体恢复/重试入口；不能自动拒绝视图或阻断整个事件，除非服务端真实守卫证明影响下游 |
| `NO_HAND_DETECTED`、候选为零或 MediaPipe 失败 | 作为自动证据和需关注提示显示，保留人工质量主操作（若 capability 允许） | 用户结合视频决定质量；不得自动 reject、自动改标签或把局部候选失败显示成事件 blocker |
| 视频播放或授权 URL 失败 | 当前视图进入可解释的播放失败状态，不切换到下一路冒充完成 | 用户重试播放或使用已有恢复入口；视频不可查看时由人提交 `NEEDS_REVIEW`/`REJECTED` 等正式结果 |
| 人工命令返回业务失败 | 保持当前视图和未决状态，显示服务端原因，不清空用户正在处理的语境 | 用户按服务端提示修正或重试；不能先行聚焦下一路 |
| 并发冲突/版本不匹配 | 显示“该事件已变化”，重新读取权威快照；当前选择只有在仍合法时才保留 | 不覆盖他人决定，不静默重放高风险命令；刷新后由当前用户再次确认 |
| 命令超时、结果未知 | 不把超时当失败或成功，也不立即重复正式提交 | 先查询既有幂等结果或刷新权威快照，确认未写入后才能由人发起重试 |
| receipt 仍为 `RECEIVING` | 可以查看已经收到的视图和准备事实，但事件级质量不能最终化为可标注结果 | 等待有权限的显式 finalize；不按超时、数量或当前画面关闭 receipt |
| `INCOMPLETE` 或迟到视图 | 明确显示缺失/迟到的稳定机位；不重编号，也不静默撤销已有视图决定 | receipt 关闭后由人决定是否 `QUALIFIED_WITH_EXCLUSIONS`，新视图纳入需按现有规则重新提交 |
| 无权限或登录失效 | 主操作显示无权限/重新认证，不伪装为等待系统 | 恢复权限后重新读取 capability；不在浏览器侧缓存权限并提交 |

错误和等待状态均在同一 `Current Action` 表达，不新增弹窗链、临时流程节点或竞争性“下一步”面板。局部失败必须绑定具体机位；只有服务端明确阻断整个事件时，才提升为事件级 blocker。

## 8. 审计与可验证自动化

连续工作流的自动化和人工决定必须可分辨：

- 自动事实记录已有检测/候选作业的输入摘要、运行标识、模型/profile 版本、产生时间和视图关联；其 actor 语义是系统作业，不是人工审核人。
- 人工质量、事件质量、主视图、Revision 和 Review 记录 actor、权限校验、提交时间、结果、理由、依据的 View Set/输入版本摘要和服务端版本。
- 自动聚焦、刷新和展示推导不产生业务结论，也不能作为“已处理”审计事实；它们最多记录为界面行为或可选遥测。
- 自动化命令使用既有幂等和审计边界。重试必须能够关联原始命令或明确证明原命令未成功，不能生成重复任务、重复修订或重复质量决定。
- 每次自动前进都能回答“哪个服务端成功事实触发了它”；无法回答时停留在当前上下文。

## 9. 后续实现约束与验收方向

V1.27 实现应优先复用 V1.26 事件工作台的权威事实、capability 和纯展示推导函数，不新增工作流持久化层。实现前至少应覆盖：

- `N=1` 无冗余机位切换，`N>1` 首次聚焦第一个未决视图；
- 正常视图质量仍有一次明确人工确认，异常路径要求人工结果和理由；
- 成功提交后必须先刷新权威快照，再聚焦下一未决视图；最后一路完成后自动转向事件质量；
- Candidate 失败、`NO_HAND_DETECTED` 和单路 Media Probe 失败不被伪造成自动质量结论或无依据的事件阻断；
- 并发冲突、读取失败、命令未知结果时停留原上下文，不显示伪成功；
- 一个 `CaptureGroup` 不产生按相机拆分的任务、修订或事件动作标签；
- 键盘焦点、动态状态和错误反馈可感知，自动聚焦不造成不可预测的焦点跳转。

以下事项不在本文或 V1.27 连续工作流中自动化：批量质量决定、一键通过全部机位、自动选择主视图、自动修复/提交正式标注、自动 Review、人工可选 Cleaning 结果、CaptureSync、相机控制和通用工作流引擎。
