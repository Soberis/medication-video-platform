# V1.29 Backend Runtime 断舍离审计

状态：AUDIT / Task A（只读）
日期：2026-09-04
范围：Core API 的 `assetcapture`、`annotationreview`、`qualitycleaning`、`mediaprivacy`、`datasetexport`、`aicandidate`、`governance`、`iamproject`、`integration`，及其已存在的 OpenAPI、event、Web、Worker、合成工具、脚本、测试与运行文档引用。本文不改动 runtime、契约、迁移、Worker、Web 或测试。

## 结论

V1.29 的最小后端边界应为：`CaptureGroup` 接收事实、媒体检查、MediaPipe `CandidateAnnotation` 与独立的 `hand-landmarks.v1`；人工质量、标注、复核和 Cleaning 仅在项目明确需要 human ground truth 时启用。当前实现仍是 V1.28 的默认线性人工链，故本报告提出的是后续变更顺序，不是“现已收缩”的声明。

最直接的收缩点是停止 `CaptureGroupQualityReview` 的 admitting 结果自动创建或重开 `AnnotationTask`。这不是删除人工链：`QualityReview`、唯一 task、append-only revision、独立 Review、确定性 eligibility、权限、审计、幂等和历史记录在 human-label 路径仍须保留。`hand-landmarks.v1` 已不读取这些人工事实，Media/AI Worker 也不写它们。

## 基线、方法与证据边界

- 需求方向：`docs/requirements/baselines/V1.29/配药视频数据处理平台需求文档_V1.29.md` 是 DRAFT；V1.28 仍为当前 runtime 基线。DRAFT 不授权删除 migration、事实或公开契约。
- 已吸收而不重复：`docs/audits/v1.29-data-group-workflow-audit.md` 已界定数据组/人工流程，`docs/audits/v1.29-ingest-ai-pipeline-audit.md` 已覆盖 ingest、Candidate 与 detection export。
- 方法：只读检索实际 controller/service/repository 调用、Spring transaction event、OpenAPI/event schema、Web API/组件、两个 Worker、synthetic client、quality gate、测试和 runbook；没有使用真实视频或外部服务，也没有运行全量质量门禁。
- 分类仅使用：`KEEP_CORE`、`KEEP_SUPPORT`、`SIMPLIFY_NOW`、`DELETE_CANDIDATE`、`HISTORICAL_ONLY`、`UNCERTAIN`。`DELETE_CANDIDATE` 不是删除授权，必须先完成数据保留、API 兼容和下游 consumer 确认。

## Quality、Annotation、Review、Cleaning 的最小职责

```text
CaptureGroup / media / Candidate evidence     ← 默认路径
        │
        └─ 项目明确需要 human truth 时
             QualityReview（逐视图人工判断）
             → 标签输入视图集合/排除事实
             → 一个 AnnotationTask → append-only AnnotationRevision
             → AnnotationReview（仅 revision 可信度）
             → deterministic LabelEligibility（当前 CaptureGroupCleaning）
```

必须保留的 guard：项目成员/管理员权限、asset/stream 项目归属与可用性、任务每组唯一性、revision append-only、Primary View 在首 revision 后冻结、Review 独立性与不可重复性、view-set/input version 防止陈旧输入、Cleaning 的 approved-review/fingerprint/idempotency/reason codes/audit。它们只在人工标签路径运行；不能被 Candidate、handedness、媒体技术状态或浏览器推导替代。

当前有两种不同事实，不能混为一个“quality 状态”：`QualityReview` 是每条可人工标签视图的人工结论；`CaptureGroupQualityReview` 是对同一组已确认视图集合能否进入标注的聚合准入记录。后者当前重复承担“全视图已人工 resolved”和“自动派单”两个职责；后续保留其不可变 input snapshot 的价值，但移除默认自动派单和 detection-path 强制闸门。

## 调度顺序、after-commit、幂等与测试

- `ClipAssetMediaIngestService.complete(..., true, ...)` 在媒体成功路径调用 `HandPoseSchedulingPort`；`CaptureSessionIngestService.create` 在保存全部 `CameraStream` 后对当时为 `INGESTED` 的 asset 调用同一 port；`PlatformLocalCaptureSessionService` 对其单一 asset 做同样补调度。
- `HandPoseAutoSchedulingService` 在已有 transaction synchronization 时注册 `afterCommit`，并在 `REQUIRES_NEW` transaction 调用 `HandPoseJobService.queueAfterMediaIngested`；预期 eligibility 和意外 dispatch 异常只记录，不回滚已提交的媒体成功事实。
- `HandPoseJobService` 的 eligibility/natural key/idempotency receipt 使普通的双侧 ensure 不产生重复 job/attempt；这些约束和 Worker result 的 lease/inbox 语义为 `KEEP_CORE`。
- 已有测试：`ClipAssetMediaIngestServiceTests` 验证 media completion 调用 port；`PlatformLocalCaptureSessionServiceTests` 验证已 `INGESTED` local asset 的补调度；`HandPoseAutoSchedulingServiceTests` 验证 after-commit、新事务及吞掉辅助调度失败。`CaptureSessionIngestContractTests` 主要验证 ingest/绑定契约。

状态：`FOLLOW-UP: regression coverage`，不是新的 P0。未找到一个真实数据库事务交错测试覆盖“CaptureSession 先读取 `UPLOADED`，Media Probe 在 stream commit 前置为 `INGESTED`，媒体侧看不到未提交 binding”的时序。由于两个 ingest service 都依据先前读取的 entity status 决定是否补调度，不能仅凭现有 Mockito/单事务测试宣称 `CURRENT CODE APPEARS FIXED`；也不能仅凭历史审计把它升级成新 P0。

最小后续验证是一个 synthetic PostgreSQL integration test，固定该交错并断言 stream commit 后恰有一个 AI job/current attempt；另覆盖 probe 已先完成与重复 ensure。若该测试通过，标记 `CURRENT CODE APPEARS FIXED`；若失败，再单独批准复用既有 `scheduleAfterMediaIngested` 的最小修补，不新增扫描器、表、队列或 workflow。

## SAFE SIMPLIFICATION

1. 冻结“显式 opt-in human-label task”命令/policy 后，停止 admitting group-quality event 的默认自动建/重开 task；将 group quality、task/review/eligibility UI 和 synthetic 验收改为可选链。
2. 保持 Cleaning 的存储和确定性验证，收缩新文案/入口为 LabelEligibility；Detection export 继续仅按 Candidate provenance fail closed。

4. 在 OpenAPI deprecation 审批后，移除 generic `POST /media-jobs` 和已无 caller-authority 的 `support_mappings` compatibility body；不影响 scoped probe、Worker protocol 或 recheck endpoint。

## 风险、迁移顺序与 Coordinator 决策

风险在于当前 OpenAPI、Web、synthetic client、Core/Web tests 和 V1.25 UAT 文档把“group quality admitting → 自动 task → review/cleaning”当成默认路径。只删 listener 或只改页面会留下不一致的 API/审计行为；删除表、migration 或 audit 记录则违反 V1.29 的保留边界。

建议顺序：

1. Coordinator/业务先批准项目级 human-label opt-in 的命令、权限、idempotency、审计及历史 task/read 策略。
2. 以一个纵向变更停止默认派单，并同步 OpenAPI/event、Web、synthetic、contract tests、runbook；确认 detection export 不受人工链影响。
3. 在兼容窗口结束后处理 local event/schema、generic media create 与 empty-only compatibility field；不触碰历史 migration 和事实。
4. 独立补充上述调度交错回归测试；结果再决定是否需要极小修补。

需要 Coordinator 明确决定：human-label opt-in 的授权主体与是否允许已存在 task 被继续使用；public `POST /media-jobs` 的兼容/弃用窗口；local quality-qualified schema 是否属于需要发布弃用通知的 API contract；以及调度交错测试的验收结果是否授权后续最小修补。
