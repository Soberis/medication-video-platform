### 2.1 `medication-camera`：三套上传实现（计划项 1/2）

#### 事实澄清：三份文件是**两条不同的技术栈**，不是同一栈的三份拷贝

| 文件 | 行数 | 职责 | 被谁引用 | 判定 |
|---|---|---|---|---|
| `tools\loop_recorder.py` | 400 | 持续切片录制守护 + 转码 + spool 原子搬运 | `deploy\medication-record.service:9` | **KEEP（生产主线）** |
| `tools\batch_uploader.py` | 516 | 定量/定容/超时三维阈值批量上传守护 | `deploy\medication-uploader.service:10` | **KEEP（生产主线，但其内部实现需 MERGE）** |
| `tools\edge.py` | 489 | V2 `external-video-ingest` 断点续传上传器 + 录制编排（provision/record/prepare/upload/status） | 仅 `tests\test_edge.py:16`、`tests\e2e_upload.py:8`；**无 service、无部署脚本** | **NEEDS_DECISION** |
| `tools\quick_loop.py` | 324 | 最小闭环：单文件录制 + 上传 | 仅 README 提及；无 import、无 service | **DELETE_CANDIDATE** |

> **主控复核（A 级）**：`Glob **/*.service` 仅命中 `medication-uploader.service` 与 `medication-record.service` 两个文件；`edge.py` 与 `quick_loop.py` 均不在部署面内。这条是本次审计最重要的结构发现：**仓库里存在一条已部署的 V1 上传线和一条未部署的 V2 上传线**，而 V2 线才是更新的实现。

> **第二轮复核追加（A 级，修正上一轮定级过轻）**：已部署生产线的语义问题比"代码重复"严重得多。
>
> `batch_uploader.py:235-251` 的 `upload_segment()` **按视频逐个调用** `upload_single_video_file()`：
>
> ```python
> for video_entry in meta.get("videos", []):          # :246
>     rec = upload_single_video_file(client, file_path, project_id, device_id=device_id)  # :250
> ```
>
> 而 `upload_single_video_file()` 每次都新建**独立批次**：`POST /upload/init` 带 `file_count: 1`（`:177`）、`upload_source_type: "PLATFORM_LOCAL"`（`:176`）、`device_id: "PLATFORM_LOCAL"`（`:175`），最后 `PUT /upload/{batch_id}/capture-session`（`:223`）拿到**该视频自己的** `capture_group_id`（`:225`）。
>
> **结论：已部署的守护进程把一次双机位同步录像拆成了两个彼此独立的单机位 CaptureGroup**，`sync_group_id` / `expected_camera_numbers` / 同步语义全部丢失，且设备身份被写成 `PLATFORM_LOCAL`（与 `segment_meta` 真值不符）。
>
> 作为对照，`edge.py:322` 声明 `upload_source_type: "HOSPITAL_REMOTE"` 并组装带 `capture_group_key` / `expected_camera_numbers` 的 V2 manifest（`:285-290`）——**只有未部署的那条线在做多机位协同**。
>
> 这一条等级为 **P0（功能性）**，优先级高于本报告原 P0-3 的"双栈"表述。**验证建议**：直接在平台库中核对最近一次双机位录像产生了 1 个还是 2 个 `capture_group`，即可确认。

#### 需要纠正的一条原假设（重要）

原假设「三套 manifest 序列化规则不同，会导致平台校验失败或重复校验」——**经复核，该假设不成立**。

`edge.py` 的 manifest 摘要规则与平台 `UploadBatchManifest.java` 是**一致的**，且 `tests\test_edge.py:193-199` 已对此写了断言。因此 manifest 摘要在 V2 线上是**正确接线**的，唯一真实分叉是：V1 线把 `device_id` 硬编码成 `PLATFORM_LOCAL`（`batch_uploader.py:175`），与 `segment_meta` 真值不符。**这条纠正把 V2 线从「可疑」改成「更正确」**，直接影响 P0-3 的决策方向。

#### 2.2.0 `metadata.json` 不得删除（A 级，第二轮复核新增）

有人可能主张「V2 manifest 已能组装元数据，`metadata.json` 是冗余」。**该主张不成立**：

| 证据 | 内容 |
|---|---|
| 平台有专门 DTO | `assetcapture\CaptureSessionMetadataV1.java:16`，`schemaVersion` 被 `@Pattern` 约束为 `^capture-session-metadata-v1$` |
| 平台主动解析 | `CaptureSessionIngestService.java:169-178` `parseMetadata()`：解析失败即抛「Capture session metadata is not valid capture-session-metadata-v1 JSON」 |
| 解析结果驱动实体 | `CameraStream.java:72,90` 用 `CaptureSessionMetadataV1.Stream` 构造；`CaptureSessionIngestService.java:277,290,364` 用它做 stream 排序、绑定校验 |
| 会话实体持有该文件 | `CaptureSession.java:107` 构造参数含 `UploadFile metadataFile` |

→ 两者**不重叠**，删 `metadata.json` 会直接打断 capture-session 组装。

#### 这条分叉为什么是 P0 级

同一段视频，三份代码的**可观察输出不同**：

- 标签集不同：AW 用平台 `allowed_labels` 并做小写归一（`1269`、`1276`）；离线两份用**大写 5 标签且不过滤**。仓库里现成的 `output/actions_video1.json:35` 就是 `INJECT_MIX` —— 平台 V78 会直接 **400**（该标签在 v3 中不存在）。
- 时间区间不同：AW 钳制、中点消解；离线熔断或不处理。
- 解析成功率不同。

**后果**：**离线评测的指标不能代表线上**——这是比「代码重复」严重得多的问题。

#### 迁移风险（线上不可中断）

| ID | 风险 | 说明 |
|---|---|---|
| R1 | **高** | `PYTORCH_CUDA_ALLOC_CONF` 必须在 `import torch` **之前** `setdefault`（`worker:78-82`）。拆包后若 import 顺序反转会**静默失效** → 必须留在入口最顶部 |

| R5 | **中** | `run.sh:244/277` 的 CLI 参数名（`--model/--queue/--bearer-token-file/--idle-offload-seconds`）是**部署契约**，改名会让 `.env` 与 FTP 清单失效 |

### 2.4 动作标签双真源（计划项 4，P0）

**结论：双真源成立，且已漂移了三层。** 这是一处**真实架构缺陷**，不是代码风格问题。

#### 三层漂移

| 层 | 内容 | 证据 |
|---|---|---|
| ① Worker 兜底表 = **已 RETIRED 的 V77 v2** | `OPEN_CAP / DRAW_LIQUID / INJECT_MIX / CHECK_INFO / LABEL_SEAL` | `action_worker.py:114-120`（A 级复核）；`run_8b.py:47-53`；`run_8b_chunked.py:73-79`；`README.md:37-41`（第 4 份，措辞又不同） |
| ② 平台 ACTIVE = **V78 v3，7 个标签** | `retrieve_medicine / open_cap / draw_liquid / inject_liquid / mix_solution / check_info / label_seal` | `V78__atomic_action_label_schema.sql:8-20`（A 级复核）；v2 在同文件 `:4-6` 被置 `RETIRED`；v3 定义见 `:22-89` |
| ③ 契约**只下发 id** | `allowed_labels: { type: array, items: { type: string } }`，无 `display_name` / `description` | `contracts\events\ai-action-job-v1.schema.json:29-33`（A 级复核）；`additionalProperties:false`（`:6`），`allowed_labels` 为 `required`（`:10`） |
| ④ **平台 Java 侧也有一份硬编码兜底** | `FALLBACK_LABELS = ["retrieve_medicine","open_cap","draw_liquid","inject_liquid","mix_solution","check_info","label_seal"]`（即 V78 v3 的 7 个），在 active schema 取不到时使用 | `aicandidate\ActionJobEnvelopeFactory.java:22-23`；`resolveAllowedLabels():40-54`，注释明写「Fall through to the frozen P0 label set when the active schema is unavailable」（A 级复核） |

> **④ 是本次审计第二重要的发现**：标签真源实为 **3 处硬编码**（平台 DB schema / 平台 Java `FALLBACK_LABELS` / Worker `DEFAULT_LABEL_DEFINITIONS`），不是 2 处。但 ④ 同时是**好消息**：`FALLBACK_LABELS` 就是 Worker 兜底表应该对齐的**现成正确答案**，见下方最小改法。

#### 缺的是哪一环？

不是「平台未下发」（id 已下发），也不是「Worker 未使用」（`action_worker.py:1072-1085` 确实在用），而是：

> **契约没有定义标签的语义字段**，Worker 只能靠硬编码表补 `name`/`desc` → **第二真源必然存在**。

#### 现成的故障场景

管理员在平台新增 `REMOVE_NEEDLE`（或平台本来就有的 `retrieve_medicine`）：

- 平台知道 → 下发 id ✅
- Worker 的兜底表不知道 → `action_worker.py:1080-1083` 落到 `{"name": item, "desc": ""}` → **Prompt 里没有中文判据** → 模型很难产出该标签 → **漏标**。
- 反向：Worker 表里的 `INJECT_MIX` 在平台**不存在**（v3 已拆成 `inject_liquid` + `mix_solution`），会被 `allowed_map` 丢弃。

#### 最小改法（仅描述，未实施）

1. `action_worker.py:1107-1130` 已经存在一条**读取平台标签 Schema 的可用分支**（snake_case 读取正确）→ 把这条分支提为**主路径**，用平台返回的 `display_name` / `description` 注入 Prompt。
2. `DEFAULT_LABEL_DEFINITIONS` 降级为「远程与消息都取不到时」的**离线兜底**，并把兜底集合对齐 V78 的 7 个 id。
3. 在 `ActionJobEnvelopeFactoryTests` 与 `.workbuddy/tools/audit_action_worker.py` 增加断言：**Worker 兜底集合 ≡ 平台 `FALLBACK_LABELS`**，防止再次漂移。
   > 注意：现有审计脚本 `action_worker.py` 的用例硬编码了 5 个旧标签（`audit_action_worker.py:104-124`），**天然无法发现这类漂移**。这是审计工具本身的盲区，应一并修掉。

标签真源：**4 处 → 1 处真源 + 1 处离线兜底**。

> **第二轮复核追加 —— 存在不需要改契约的便宜修法（推荐先做这一步）**
>
> 上述「扩展契约携带 `display_name`/`description`」是**根治方案，但它不是唯一方案，也不是最省的第一步**。因为平台已经把正确答案硬编码在 `ActionJobEnvelopeFactory.java:22-23` 的 `FALLBACK_LABELS` 里（正是 V78 v3 的 7 个标签）。
>
> 便宜的修法：
> 1. 把 `action_worker.py:114-120` 的 `DEFAULT_LABEL_DEFINITIONS` 对齐为 V78 v3 的 **7 个 id**（补齐中文 name/desc），并把 Worker 的「读平台 Schema」分支（`action_worker.py:1107-1130`）设为主路径 —— **不改契约**。
> 2. 增加一个契约测试：断言「Worker 兜底集合 ≡ 平台 `FALLBACK_LABELS`」，任一侧漂移即失败。这把"双真源"从**语义漂移风险**降级为**编译/测试期可检测**。
> 3. 契约扩展作为**后续**独立变更推进，届时再删 Worker 兜底表。
>
> **不要**采用「Worker 取不到定义就 fail-closed 拒绝执行」的做法：平台自己保留 `FALLBACK_LABELS` 恰恰说明 active schema 存在不可用的情况；只让 Worker 侧 fail-closed 会在 schema 抖动时直接停机，是不对称设计。
>
> 另注：`ai-action-job-v1` 是 **const 版本化契约**（`schema_version` const `"ai-action-job.v1"`、`algorithm_version` const `"v1"`，见 `:13,25`），因此把 `allowed_labels` 换成富对象数组**必须新开契约版本**（如 `ai-action-job.v2`），不能原地改字段名。这是原始方案未覆盖的成本。

| 判定面 | 是否校验机器技术质量 |

Export eligibility   ← review APPROVED + group admitting + C7 provenance + C8 时长
