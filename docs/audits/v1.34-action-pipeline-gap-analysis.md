## 总体审计结论

经过对 V1.34 需求基线、技术设计架构以及现行代码实现的逐行核对，证实系统**在作业复用、RabbitMQ 拓扑、Payload 动态下发、服务端区间合法性校验以及前端智能初始化防覆盖**等主干链路上已经接通，但存在 **3 项核心设计缺口（P0/Tier 1）** 与 **4 项口径偏差/防御不足（P1/Tier 2）**。

下面逐条展开「缺口事实 → 对应验收条款 → 修法选项 → 风险评估」的完整对照。

## 一、核心大缺口对照表（Tier 1: P0 架构级缺口）

### 缺口 ①：V34-FR-001 动作预标注「合格自动派发」未接线（仅存异常手动兜底）

| 维度 | 详细内容 |
|---|---|
| **代码实证与现状** | 1. `queueActionCandidateJob` 在全仓**唯一**的调用者是 `ActionCandidateQueryController.java:54-71` 的 `POST /api/v1/projects/{projectId}/capture-groups/{captureGroupId}/action-candidate-jobs`，前端由 `CaptureGroupAnnotationPanel.tsx:520` 的手动按钮触发。<br>2. 核心领域中不存在 `ActionSchedulingPort` 或类似的调度接口。<br>3. `qualitycleaning` 的质检准入通过处、`annotationreview` 的标注任务创建处、以及 `assetcapture` 的主视频 Ingest 点，**没有任何动作预标注的触发挂载**。<br>4. 作为对比，手部检测链路具备完整的 `HandPoseSchedulingPort` 并由 `HandPoseAutoSchedulingService` 挂接在三处媒体 Ingest 点（`ClipAssetMediaIngestService:57`、`CaptureSessionIngestService:285`、`PlatformLocalCaptureSessionService:109`），测试侧亦有 `HandPoseAutoSchedulingServiceTests`。动作链路目前测试仅有 Controller 与 Query/Service 单元测试，**缺少自动调度测试**。 |
| **对应需求与验收条款** | - **需求基线 V34-FR-001**：“数据组通过质检（admitting group quality）并建立标注任务后，系统自动向队列派发动作推理作业，无需人工手动点击；未通过质检、存疑或特殊视频不自动占用 GPU，保留授权用户在任务内手动触发入口”。<br>- **需求基线 §3.1**：“视频与任务合格意味着媒体就绪、主视频与 schema 有效、已有人工任务且当前质检准入 → 自动派发一次预标注；覆盖先建任务后质检、先质检后建任务以及主视频就绪的不同顺序；同一任务、输入版本、schema 及推理配置不得因重复事件重复派发”。<br>- **技术设计 §7.1 步骤 3**：“自动派发是最终验收要求，不因先接通手动入口而省略”。 |
| **修法选项** | **选项 A（推荐 - 领域事件与调度编排服务）**：<br>在 `aicandidate` 模块定义领域事件监听器或 `ActionAutoSchedulingService`，监听两类关键事件：`CaptureGroupQualityAdmittedEvent`（质检合格）和 `AnnotationTaskCreatedEvent`（标注任务创建）。收到事件后，通过公开只读查询核对前置条件：<br>1) 存在合法主视频且处于 READY；<br>2) CaptureGroup 质检结论处于已准入（ADMITTED）；<br>3) 存在活跃的标注任务；<br>4) 当前主视频未派发过处于 ACTIVE 或 SUCCEEDED 的相同配置动作作业。<br>四项全部满足时，执行 `enqueueActionJob`。同时满足三种到达时序。<br><br>**选项 B（同步应用服务调用）**：<br>在质检准入和创建任务的方法末尾硬编码调用 `ActionCandidateJobService.tryScheduleAutoActionJob(...)`。缺点是破坏模块单向依赖，增加事务耦合。 |
| **风险与兼容性** | 1. **并发时序竞争**：质检合格与任务创建可能几乎同时发生，需依赖 `ai_job` 表的唯一约束或数据库行锁防止重复创建两个相同的推理作业。<br>2. **GPU 负载风暴**：若大量历史数据批量通过质检，可能瞬间积压大量队列消息；需严格保持每卡消费者串行与限流。 |

### 缺口 ②：标签 Schema 校验守卫依据不对称，派发与校验使用 Global 当前版本，候选缺版本记录

| 维度 | 详细内容 |
|---|---|
| **代码实证与现状** | 1. **派发时取全局当前**：`AnnotationActionAllowedLabelsAdapter.java:22` 实现 `ActionAllowedLabelsPort` 时直接调用 `schemaService.getGlobalCurrent()`，而非针对该标注任务锁定的 Schema。<br>2. **校验时重复取全局当前**：在 `ActionCandidateJobService.java:260` 校验 Worker 回传的 segments 时，再次调用 `this.actionEnvelopeFactory.resolveAllowedLabels()`（内部依然是 `getGlobalCurrent()`），完全无视了派发时 Envelope 已经携带的快照。<br>3. **前后端守卫不对称**：前端 `CaptureGroupAnnotationPanel.tsx:204-210` 检查的是 `task.label_schema_digest === currentSchema.digest`；如果派发后管理员升级了 Schema，后端用新 Schema 校验，前端却因 Digest 不一致而告警或拒绝自动铺设，产生认知割裂。<br>4. **候选表缺少 Schema 追溯列**：`action_candidate` 表（Flyway `V76`）仅包含 `action_label` 字符串，没有任何 `label_schema_id` 或 `label_schema_digest` 列。 |
| **对应需求与验收条款** | - **需求基线 §2.1**：“复用标签库和任务绑定的不可变 schema，不硬编码新的五类标签，不自动创建标签”。<br>- **需求基线 §2.2**：“候选保留视频身份与 SHA-256、任务输入与标签 schema 版本、模型版本及权重摘要……”。<br>- **技术设计 §3.1**：“标签从任务绑定的不可变 schema 获取……”。<br>- **技术设计 §3.2**：“任务输入版本、label schema 版本及摘要：防止旧输入或旧标签结果冒充当前结果”。 |
| **修法选项** | **选项 A（推荐 - 绑定任务 Schema 快照并增加候选 Schema 追溯）**：<br>1) 派发时，`ActionAllowedLabelsPort.resolveAllowedLabels(taskId)` 优先通过 `taskId` 获取该任务绑定的不可变 Schema 标签列表和 `schema_digest`，并存入 `ai_job` 或上下文；<br>2) 回传校验时，`ActionCandidateJobService` 直接使用该 Job 派发时记录的合法标签集合（或持久化在 `ai_job.payload` 中的 `allowed_labels`），彻底解除对 `getGlobalCurrent()` 的运行时依赖；<br>3) Flyway 增加迁移（如 `V79`），在 `action_candidate` 增加 `label_schema_digest VARCHAR(64)`，确保每条候选都能追溯其生成的规则版本。<br><br>**选项 B（纯内存闭环，不改库）**：<br>校验时直接解析 `ai_job` 原发送报文中的 `allowed_labels`，确保“派发什么就按什么校验”，暂不在 `action_candidate` 补列。 |
| **风险与兼容性** | 选项 A 需要新增 Flyway 迁移脚本，历史已有候选记录需填充默认或历史 schema digest；选项 B 0 数据库变更，但仍留下无法直接 SQL 查询候选所属 schema 版本的追溯遗憾。 |

### 缺口 ③：回传结果中的 Provenance 元数据声明了却未落库（全部被静默丢弃）

| 维度 | 详细内容 |
|---|---|
| **代码实证与现状** | 1. 在 `ActionCandidateResultRequest.java:12-20` 中，Java Record 严格定义了：<br>`@NotBlank String modelName, String promptVersion, @NotNull @Min(1) Integer totalWindows, @NotNull @Min(1) Long durationMs, @NotNull @Min(0) Long inferenceDurationMs, @NotNull Instant startedAt, @NotNull Instant completedAt`<br>类注释明确写道：“every field the Worker sends is modelled here so provenance is persisted instead of being silently dropped”。<br>2. 然而在 `ActionCandidateJobService.java:167-174` 的持久化逻辑中：<br>`INSERT INTO action_candidate (...) VALUES (...)`<br>仅插入了 `seg.startMs()`, `seg.endMs()`, `seg.label()`, `seg.confidence()`, `seg.sourceWindow()`, `stitchedJson`。<br>3. `modelName`、`promptVersion`、`totalWindows`、`inferenceDurationMs`、`startedAt`、`completedAt` **完全没有存入任何数据库表**（`durationMs` 仅用于区间是否超长的边界校验）。类注释与实际代码行为直接冲突！ |
| **对应需求与验收条款** | - **需求基线 §2.2**：“候选保留视频身份与 SHA-256、任务输入与标签 schema 版本、模型版本及权重摘要、提示词和推理配置版本、job/attempt、原始输出”。<br>- **技术设计 §3.2**：“模型 revision 与权重摘要、提示词、采样、像素和生成配置版本：复现推理条件与定位性能差异”。 |
| **修法选项** | **选项 A（推荐 - `ai_job` 记录执行元数据，避免散落至每条 segment）**：<br>在 `ai_job` 表中扩充 `execution_metadata JSONB`（或在 `ai_job_attempt` 表中记录），在 `acceptResult` 事务中将 `ActionCandidateResultRequest` 中的执行级 Provenance（模型、提示词版本、总窗口数、推理耗时、开始/结束时间）统一打包为 JSONB 落库。这样既不冗余在每个细分动作片段，又能完整保留整个推理作业的元数据追溯。<br><br>**选项 B（在 `action_candidate` 增加元数据外键或冗余列）**：<br>创建 `action_candidate_run_metadata` 表，通过 `ai_job_id` 一对一关联；或在 `action_candidate` 补充各列。 |
| **风险与兼容性** | 仅新增只读元数据存储，不改动已有公共 OpenAPI 字段和查询返回值，向后完全兼容；需要编写一份整洁的 Flyway 迁移脚本。 |

## 二、次级缺口与口径偏差（Tier 2: 规范与健壮性问题）

### 缺口 ④：`confidence` 实现严格度与需求基线相反（实现比需求更严）

| 维度 | 详细内容 |
|---|---|
| **代码实证与现状** | 1. 需求基线 §2.1 明确写道：“毫秒是存储单位，不承诺毫秒级精度。模型自报置信度不是正确率；**首版不要求 confidence**”。技术设计 §3.1 亦重申此点。<br>2. 但在实现中：<br>- Flyway `V76.sql:16`：`confidence NUMERIC(5,4) NOT NULL`，且带 CHECK 约束 `[0.0, 1.0]`；<br>- Java Record `ActionCandidateSegmentItem.java`：标注了 `@NotNull @DecimalMin("0.0") @DecimalMax("1.0") BigDecimal confidence`；<br>- OpenAPI 规范：标记为必填字段 `required: [start_ms, end_ms, label, confidence]`。<br>3. 结果：如果外部对接的标准 Qwen Worker 未返回置信度，Core API 会直接抛出 `400 Bad Request` 拒收。 |
| **对应条款** | V1.34 需求基线 §2.1、技术设计 §3.1。 |
| **修法选项** | **选项 A（推荐 - 兼容性放宽）**：Flyway 迁移执行 `ALTER TABLE action_candidate ALTER COLUMN confidence DROP NOT NULL`；Java Record 将 `@NotNull` 移除；若 Worker 未提供则存 `NULL`（或设定默认值如 `1.0`）。OpenAPI 契约将 `confidence` 改为可选字段。<br>**选项 B（维持现状）**：修改需求文档，注明“Worker 必须提供置信度数值（若无校准模型则默认回传 1.0）”。 |
| **风险与影响** | 选项 A 是标准的向后兼容变更（放松约束），前端消费已做判空防护，几乎无回归风险。 |

## 三、两个重要的认知共识

1. **AI Worker vs Qwen Worker 的职责定位**：
   - 平台工程内的 `workers/ai-worker` 动作推理仅是占位脚手架（`PLACEHOLDER_PROMPT_VERSION`，生成确定性离散片段，用于平台契约验证与 CI 集成）；
   - 真实的 Qwen3-VL-8B 视觉大模型常驻在 `medication-action-worker`（或独立 4090 节点）。
   - **结论**：在 Core API 和前端跑通占位 Worker 仅证明平台内部调度、契约与解析通过，不代表真实 4090 推理已完成生产验收。这与技术设计 §7.1 第 2 步完全一致。

2. **标签真源演进现状**：
   - 目前 Worker 已改为从任务 payload 动态读取 `allowed_labels`，避免了 Worker 自行造标签；
   - 平台侧 `FALLBACK_LABELS`（7 个 V78 标签）与前端 `ACTION_PALETTE` 仅作为缺失上下文时的最后容灾兜底，**二者均已退居二线，不再作为业务真源**。这是架构收敛的正确方向。

## 四、建议治理路线图（优先级排序）

| 优先级 | 治理专项 | 理由与收益 |
|---|---|---|
| **P0-1** | **缺口 ②：Schema 校验口径对齐** | 不涉及表结构破坏性变更，消灭“派发后 Schema 变更导致合规回传被拒”的潜在致命 Bug，确保前后端守卫口径一致。 |
| **P0-2** | **缺口 ③：Provenance 元数据落库** | 补全 `ai_job` 执行元数据存储，使类注释、契约声明与数据事实达成一致，满足 V1.34 关键追溯验收。 |
| **P0-3** | **缺口 ①：自动派发接线（FR-001）** | V1.34 的最大功能项。通过事件监听与前置准入校验，打通“质检合格+建任务 → 自动派发”的端到端自动化。 |
| **P1-1** | **缺口 ④：Confidence 放宽为可选** | 对齐需求基线 §2.1，降低第三方或轻量模型对接门槛，避免因缺少置信度被拒收。 |
| **P1-2** | **缺口 ⑥：候选查询增加 `clip_asset_id` 过滤** | 增强服务端健壮性，防止多机位或换源场景下候选越界。 |

| **P2** | **缺口 ⑦：前端标签中文名动态读取 Schema** | 优化前端显示，支持零代码适配新增标签。 |

## 五、2026-09-15 当前产品口径修订

本报告前述缺口和路线图保留为 V1.34 的原始审计证据，不因后续文档调整而改写。当前产品目标已在 V1.35 和 [ADR-0004：自动标注与异常人工接管策略](../adr/0004-automatic-annotation-approval-policy.md) 中进一步明确：不只自动派发已有任务，还要在策略启用且质量准入通过时幂等创建/复用任务；完整有效结果初始化未编辑草稿，用户可修改并显式提交，然后按既有 Review 处理。前述历史建议中的默认 confidence=1.0 已否决，缺失值保持缺失。

因此，V1.34 的“人工任务已存在后自动派发”是当前目标的一个基础子集，不等于无人逐条确认的完整闭环。当前代码、契约、占位 Worker 和真实模型质量仍未据此宣称完成；后续追踪以 [V1.35 需求追踪矩阵](../architecture/requirements-traceability.md) 为准。
