# V1.29 数据接入与 AI 主链审计

日期：2026-09-04  
范围：Upload / External Ingest、CaptureGroup、CameraStream、ClipAsset、Media Probe、MediaPipe、AI Worker、CandidateAnnotation、provenance、`hand-landmarks.v1`。  
基线：`V1.29` 为 DRAFT，定义后续“数据组与机器证据为默认路径、人工链按项目需要启用”的方向；当前 runtime 仍以 V1.28 为正式实现基线。本报告不授权删除、迁移或改变 runtime。  
方法：只读检查 Core API、Web、Worker、迁移、OpenAPI/events、合成工具、测试、脚本和部署文档；未运行全量质量门禁，未使用真实视频或外部服务。

## 结论

当前接入/AI runtime 已具备 V1.29 目标默认路径所需的事实边界：平台接收外部采集端已经完整性确认的视频，围绕一个 `CaptureGroup` 绑定 `CameraStream → ClipAsset`，Media Probe 成功后以 MediaPipe 生成只读辅助 `CandidateAnnotation`，并可导出当前、可验证的 `hand-landmarks.v1` 检测事实。AI 没有成为人工质量、正式标注、Review 或 Cleaning 的写入来源。

这不是“runtime 已完成 V1.29 收缩”的结论。现有人工质量、任务、Revision、Review 与 Cleaning 仍是 V1.28 当前实现事实；V1.29 DRAFT 仅要求它们以后按项目 human-ground-truth 需要启用，且本 Task C 不改变它们。`hand-landmarks.v1` 已独立于人工链，符合 DRAFT 的导出边界。

发现一个真实但窄的补调度竞态：**ClipAsset 在 CameraStream 提交前完成 Media Probe** 时已有一次自动调度会因未绑定/未启用而跳过；通常后续 CaptureSession 创建会看到 `INGESTED` 并再次调度，但若 Media Probe 完成恰好发生在 CaptureSession 创建事务已经读取到旧 `UPLOADED` 状态、而 CameraStream 尚未提交的窗口，两边都会错过第二次调度。影响是该 ClipAsset 保持 `INGESTED` 且没有 AI job；不影响媒体事实、人工链或已存在 Candidate。建议只做一个复用既有幂等语义的定向修补，见“最小 patch plan”。

当前没有实际训练开发者/consumer 读取 `hand-landmarks.v1` 的证据；该 CSV 是可供后续消费的检测事实格式，但不是已验证的训练闭环，也不含人工动作 Ground Truth。`hand-pose-evaluation` 只校验操作人员提交的评估证据格式，不能运行模型或计算 precision、recall、PCK、误检或漏检指标。

## 已核对主链

```text
外部 manifest / multipart upload
  → UploadBatch completion 创建 ClipAsset + Media Probe job
  → Media Worker probe result 成功
  → ClipAsset/已绑定 CameraStream 变为 INGESTED
  → after-commit 尝试创建 MediaPipe AI job
  → AI Worker 取得短期输入授权、复核 SHA-256、离线 MediaPipe
  → Core API 在同一事务写 CandidateAnnotation、result inbox、attempt/job terminal state
  → 只读 current view + latest AI evidence → hand-landmarks.v1 CSV
```

### 接入、分组与绑定

- **KEEP**：`ExternalVideoIngestManifestService` 用 `(project, keySource, captureGroupKey)` 的事务 advisory lock 和内容比对实现重放/冲突边界；V2 支持显式声明但缺失的机位，不从文件名或上传顺序推断机位。
- **KEEP**：`UploadBatchCompletionService` 只在完整性检查完成后创建 `ClipAsset`，并以 `auto-media-probe-{clipAssetId}` 触发 Media Probe。`CaptureSessionIngestService` 验证 metadata、项目、CameraSet、每个视频的唯一绑定和外部 manifest 后，冻结 snapshot 并建立 `CameraStream`；数据库还有 `camera_stream.clip_asset_id` 唯一约束。
- **KEEP**：`CaptureGroupViewQueryService` 是对下游公开的只读投影，不泄漏实体或跨模块 Repository。它将 CaptureSession 作为 CaptureGroup，按冻结 CameraSet 成员和已绑定 stream 组装视图；N=1 只是一个视图。
- **KEEP**：本地合成入口也采用 `CaptureGroup → CameraStream #1 → ClipAsset`，没有恢复独立单视频产品路径。

**SIMPLIFY（仅目标默认产品路径）**：将接收、归组、Media Probe、Candidate 和 detection export 作为无需人工链的默认说明/验收路径；不要在本审计删除现有人工事实、入口或 API。是否停止自动派单、阶段推导或旧入口，属于 V1.29 后续 Runtime / human-flow 专项审计，不能从本报告推导。

证据：`UploadBatchCompletionService`、`ExternalVideoIngestManifestService`、`CaptureSessionIngestService`、`CaptureGroupViewQueryService`、`V8__create_capture_session_assembly.sql`、`ExternalVideoIngestManifestContractTests`、`tools/synthetic-upload-client`、`tools/synthetic-capture-group-client`。

### Media Probe、MediaPipe 与 Worker

- **KEEP**：Media Probe 结果由 `MediaJobExecutionService` 在锁定当前 job/attempt、Worker 身份、lease、消息身份、输入/recipe digest、时钟窗口及 Inbox 去重后接收。成功时保存不可变 `MediaReport`，更新 job/attempt，并调用 `ClipAssetMediaIngestService.complete`；失败保留 retry/attempt/lease 语义。
- **KEEP**：`HandPoseAutoSchedulingService` 在媒体事务成功提交后新开事务调用 `HandPoseJobService.queueAfterMediaIngested`；辅助能力的配置、容量或调度失败只记录日志，不回写媒体成功状态。
- **KEEP**：AI job 使用固定自然键（项目、asset、input digest、MediaPipe 算法/版本、模型、sampling/profile）和命名空间 Idempotency receipt，重复 ensure 不会生成重复 job/attempt。它还要求 `INGESTED` 视频、启用手检的已绑定 CameraStream、已验证 MediaReport duration 和批准模型 digest。
- **KEEP**：AI Worker 只经短期授权下载输入并复核 size/SHA-256；固定 10 FPS、最多 2 手、21 landmarks，候选/handedness 是辅助信息。Core API 接收结果时在同一事务插入 Candidate、记录 Inbox、再落 attempt/job 状态；旧 lease/迟到结果不能写回。
- **KEEP**：恢复服务为失联 AI attempt 创建新 capability/message/attempt；没有把 RabbitMQ 当作业务事实数据库。

**KEEP**：DRAFT 明确要求继续保留权限、审计、SHA-256、Outbox/Inbox、job/attempt、lease/heartbeat、有限 retry、迟到结果拒绝与受控恢复；本链路没有可安全删除的上述可靠性机制。

证据：`MediaJobExecutionService`、`ClipAssetMediaIngestService`、`HandPoseAutoSchedulingService`、`HandPoseJobService`、`AiJobExecutionService`、`AiJobRecoveryService`、`workers/ai-worker/src/medication_ai_worker/{processor,api,landmarker}.py`、`workers/ai-worker/README.md`、`contracts/events/ai-hand-pose-result-v2.schema.json`、`AiHandPoseResultContractTests`。

## 调度竞态与最小 patch plan

### 已存在的补调度

`ClipAssetMediaIngestService.complete(..., true, ...)` 无论此时是否能找到 CameraStream，都会在媒体事务 commit 后调度一次。`CaptureSessionIngestService.create` 在保存全部 stream 后，亦会对当时已经是 `INGESTED` 的 asset 再调度；`PlatformLocalCaptureSessionService` 也有同样补调度。这覆盖了“probe 完成早于 CaptureSession 开始”的普通顺序。

### 仍存在的交错

在 PostgreSQL 默认的逐语句可见性下可发生：

1. CaptureSession 创建事务读到 ClipAsset 状态为 `UPLOADED`，因而其 `filter(INGESTED)` 不安排 after-commit 调度；
2. Media Probe 成功事务取得 ClipAsset 锁、将其改为 `INGESTED`；此时 CameraStream 还未提交，`findByClipAssetId` 看不到它；
3. Media 成功事务 commit，after-commit queue 尝试读取 binding，`AssetCatalogQueryService` 返回 `enabledForHandDetection=false`，`HandPoseJobService.ensureEligible` 拒绝且 `HandPoseAutoSchedulingService` 吞掉这个预期 skip；
4. CaptureSession 事务提交已绑定的 CameraStream，但没有第二次 ensure。

因此这是会留下未调度 `INGESTED` ClipAsset 的 race；现有单元测试分别验证“成功媒体完成会调度”“创建时已 INGESTED 会调度”和“after commit”，没有覆盖上述双事务交错。

### 最小 patch plan（仅候选；不在本审计实施）

1. 在 `CaptureSessionIngestService.create` 与 `PlatformLocalCaptureSessionService` 的 **stream 已保存后、事务提交后** 路径，调用现有 `HandPoseSchedulingPort.scheduleAfterMediaIngested(projectId, clipAssetId)`；不要依赖此前 JPA 实体的旧 `asset.getStatus()` 快照。可仅对本次绑定的 asset 调用，不新增扫描器、队列、表或 workflow。
2. 若后续修改需要一个命名更准确的门面，可将该既有 port 调用命名为 `ensureHandPoseScheduled(clipAssetId)`；本 checkout 没有这个同名方法，实际复用点是 `scheduleAfterMediaIngested → queueAfterMediaIngested`。不得复制 job 创建逻辑。
3. 复用 `HandPoseJobService` 的 current eligibility、自然键和 Idempotency receipt；它已使双侧都调度时安全幂等。不要创建新的 job 状态、broker 重试或补偿表。
4. 增加一个真实数据库事务级回归测试：CaptureSession 先读到 `UPLOADED`，并发 Media Probe 成功在 stream commit 前完成；断言 stream commit 后恰有一个 AI job/attempt。再断言普通“Media 在绑定前已完成”和“双侧重复 ensure”仍只有一个 job。该候选修改只能在后续批准后实施。

**UNCERTAIN**：该测试需要以实际隔离级别和锁顺序固定交错；仅 Mockito 顺序测试不足以证明数据库可见性。修补前应先用一个定向 integration test 复现。

## 重复读取与只读 projection

### 事实

- `CaptureGroupViewQueryService.findAll(projectId)` 对每个 CaptureGroup 分别读取 session snapshot、snapshot members、CameraStreams 和 ClipAssets；项目范围导出因此随组数执行重复的 group/view 拼接。
- `CandidateEvidenceQueryService.findByClipAssets` 对所有传入 ClipAsset 批量读取 asset、每 asset latest AI job/attempt/inbox、以及该 job 的 Candidate，避免了导出端逐 asset 查询。
- 该 Candidate projection 目前有两个真实生产消费者：`HandLandmarkTrainingExportService`（当前检测导出）和 `CaptureGroupAnnotationWorkflow`（人工工作流可见的辅助证据）。Web 不直接拼 SQL：它调用 `hand-landmarks.v1` preview/download 和候选 API；synthetic client 调用 Media/AI API；AI Worker 只调用 internal lease/heartbeat/result API。

### 结论与方案

- **KEEP**：Candidate provenance 的“latest job + current asset digest + current attempt + candidates”拼接集中在 `CandidateEvidenceQueryService`；不要给 Web、Worker 或每个业务模块复制这套 SQL。
- **SIMPLIFY（仅在项目范围导出有真实规模/延迟证据时）**：在 `assetcapture` 新增一个只读批量 `CaptureGroupDetectionViewQueryService.findAll(projectId)`，一次读取当前 CaptureGroup、enabled snapshot member、CameraStream、ClipAsset 需要的字段，返回现有 `CaptureGroupFacts/CaptureGroupView` 等价 DTO。`datasetexport` 仍调用此投影和现有 `CandidateEvidenceQueryService`；不持久化 projection、不建新表、不复制 AI SQL、不改变 API/OpenAPI。
- **DEFER**：没有测得项目范围 group 数、导出 P95 或 PostgreSQL query plan 前，不应实施该投影。单事件导出及当前批量 Candidate 查询没有证据表明需要优化。

## CandidateAnnotation 容量边界

- `candidate_annotation` 将每只手的 bounding box 与 21 点 landmarks 放在 PostgreSQL JSONB；每个 job 的 unique key 是 `(ai_job_id, frame_timestamp_ms, hand_index)`，现有索引是 `(ai_job_id, frame_timestamp_ms, hand_index)`。结果接收采用每候选一条 INSERT，且与 Inbox/job terminal state 同一事务。
- 现有 P0 guard 按已验证媒体时长、10 FPS、最多 2 手限制单 job 至 20,000 候选；理论上对应不超过 1,000 秒（约 16 分 40 秒）满密度输入。AI Worker 在提交前也拒绝超过 20,000 candidates。
- 这限制单作业，而非项目日量、保留期、JSONB/索引大小、导出宽度、批量读取延迟或运维恢复成本。项目范围 `hand-landmarks.v1` 会在 repeatable-read 事务中把符合条件的全部 Candidate 读入内存、计算集合摘要并生成整个 CSV byte array；没有分页/流式边界。
- 仓库已有只读离线 `tools/candidate-capacity-review`，其生产测量模板全部 `PENDING`；合成场景的时长、日量、密度、行字节和索引开销都是 `ASSUMED`。工具明确不改变 schema/runtime，也不能作出容量决策。

**KEEP**：P0 单 job 上限、数据库 FK/约束、provenance、Inbox 幂等与恢复语义。  
**DEFER**：Kafka、ClickHouse、Spark、Lakehouse、S3 dense-result runtime、分区迁移、批量预标注 API、容量平台。  
**UNCERTAIN**：在获得授权或合成的代表性测量前，不能断言 PostgreSQL JSONB 足以承载 P1 批量规模，也不能断言应迁移出去。

建议先按 `candidate-capacity-review` 的 measured template 收集：单路平均/P95 时长、相机数、日量口径、真实 candidate density、行和索引尺寸、30/90/365 日保留、典型查询 P50/P95/P99，以及带分区/索引与对象工件读回的对照基准。只有这些证据和明确阈值齐全后，才选择 PostgreSQL 保留、分区或“DB job/summary + versioned artifact”的 P1 方案。

## `hand-landmarks.v1`：训练可用性与评估边界

### 已实现的格式和 provenance

`HandLandmarkTrainingExportService` 以 repeatable-read 读取当前启用、存在且可用的 CameraStream/ClipAsset，再由 `CandidateEvidenceQueryService` 验证：项目/asset/input SHA、算法、模型/profile、current job/attempt/message/result digest、状态、候选集合摘要和 21 点几何。任一 current view/evidence 不可证明会 fail closed；只有 `SUCCEEDED_WITH_CANDIDATES` 写 CSV 行，`NO_JOB`、`QUEUED`、`RUNNING`、`FAILED`、`SUCCEEDED_NO_HAND` 只反映于 preview 计数。CSV 具有 CaptureGroup、stream/camera、ClipAsset SHA、candidate、时间、handedness 和 AI provenance；不含 MP4、人工动作标签、质量、Review、Cleaning 或跨机位时间对齐。

OpenAPI、Web 按项目/单 CaptureGroup 调用同一 preview/download 契约；Core API export contract、Web API/Button 测试和 Python synthetic CSV readback 都验证格式、排序、21 点和 fail-closed 行为。

### 不可宣称的结论

- **不是已验证的开发者训练闭环**：仓库没有 consumer 将 CSV 读入训练代码、没有训练运行、模型比较或训练结果；`requirements-traceability.md` 与 README 同样明确该证据不存在。当前实现还限制 `data-profile=synthetic`，非 synthetic 以 403 拒绝导出。
- **不是 Ground Truth 训练集**：CSV 不含人工动作 label；Candidate/handedness 不能替代人工真值。它适合作为“当前 MediaPipe 检测事实样本”格式，不足以证明任何监督学习训练目标已经满足。
- **没有实际 precision / recall / PCK / 误检漏检评估能力**：`tools/hand-pose-evaluation` 可记录 `HAND_FRAME_RECALL`、`NO_HAND_FRAME_FALSE_POSITIVE_RATE` 等值，却不读取视频、不运行模型、不读取人工参考、更不计算指标；其 synthetic fixture 所有指标均为 `PENDING`。它也没有 PCK 指标或 landmark-to-reference 匹配算法。Worker 单元测试证明结构/时间戳/21 点约束，不能替代真实算法测量。

**KEEP**：CSV/provenance/fail-closed 与“候选非真值”边界。  
**DEFER**：训练服务、DatasetVersion、自动模型训练、评估平台、跨相机对齐和任何将 AI 自动升级为人工结论的流程。  
**UNCERTAIN**：授权样本、人工参考标注、评估协议、阈值、误检/漏检和 PCK 结果均未提供；不能标记 UAT 或算法效果通过。

## 验证建议

1. 为上文并发交错先添加一个可控 integration test；若能复现，再实施最小补调度并运行该测试、现有 `HandPoseAutoSchedulingServiceTests`、`ClipAssetMediaIngestServiceTests`、CaptureSession contract tests 和 AI job contract tests。
2. 保持 synthetic profile，以 N=1/N>1 各跑一次“probe 在绑定前已完成”“probe 与绑定交错”“重复 ensure”；验证一 asset 只有一个 AI job、一个当前 attempt，媒体/Receipt 不被改写。
3. 用 `candidate-capacity-review` 的 measured template 和受控/授权样本完成容量基准；在报告仍为 `DECISION PENDING` 时不引入新存储组件。
4. 若业务要声称算法效果，先定义冻结的人工参考、frame/landmark matching 与 PCK 阈值，使用授权隔离样本产生真实指标和证据；随后才用 `hand-pose-evaluation` 校验并归档该证据。工具 `VALID` 只表示证据格式有效。

## 审计覆盖与未决风险

已核对的调用面包括：Core API 接入/Media/AI/导出服务与迁移；OpenAPI 和 AI result event schema；Web 的 `hand-landmarks` API/事件详情按钮与测试；AI/Media Worker；synthetic upload/CaptureGroup client；Bruno；`start-local`、quality-gate 搜索根和 deployment/production-readiness 文档；Candidate capacity 与 hand-pose evaluation 工具及测试。

未决风险：调度竞态尚无数据库级复现；容量没有实测数据；唯一导出没有实际 consumer 或训练/UAT 证据；算法指标没有授权参考样本和计算实现。以上均不应通过增加通用 workflow、数据平台或新的存储组件来“预防性解决”。
