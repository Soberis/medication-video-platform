# 配药视频数据管理平台需求基线 V1.16

> 文档版本：V1.16  
> 文档状态：当前基线  
> 生效日期：2026-08-10  
> 前一版本：V1.15  
> 生效规则：本版本继承 V1.15；本版本明确修改的条款优先于 V1.15 及其历史继承基线。

## 1. 本次变更与目标

V1.16 把舱内多机位手部姿态候选的产品入口收敛为“少决策、后台持续编排”的视频分析体验。它不放宽
V1.15 的 Phase A `GO`、相机准入、冻结 profile、候选审核或安全门禁；在这些门禁完成前，本文只定义
目标能力，现有 AIJob、Worker、候选查询和页面仍是实现草稿，不得启用给普通用户。

用户只需理解“我的视频能否检测手部姿态”，不需要理解媒体探测、AIJob、RabbitMQ、Worker、lease 或
模型摘要。平台在服务端完成持续、可恢复的编排。

本版本中的“获批舱内相机”是指安装在采集舱/工作区内、由平台以 `CameraStream` 角色和授权事实确认的
非佩戴式固定或机位相机。一次采集的 `CameraSetSnapshot` 决定实际相机数量 `N`，可为 2、4、6、8 或
其他已配置数量；任何前端、API、数据库约束、队列和 Worker 逻辑都不得写死为 3 路。每路视频的分析、
候选、状态和 Overlay 均独立，不根据文件名推断相机，不把不同机位的结果混合，也不在本版本做跨相机追踪
或融合。
V1.15 中针对该试点的 `EGO` 表述在 V1.16 的自动分析范围内由“获批舱内相机”取代。

普通用户的相机名称固定显示为“相机 1、相机 2、相机 3 …”。该号码按同一 `CameraSetSnapshot` 的
`camera_index` 升序生成序号（从 1 开始），只用于页面和用户沟通；内部 UUID、`camera_channel_id` 与
原始 `camera_index` 仍是关联、审计和契约事实，不因显示编号而改变。一个已创建的 CaptureSession 内，
相机显示顺序不得因刷新、上传顺序或检测状态而变化。

```text
上传完成
→ 自动媒体技术检查
→（获批且符合条件时）一键或项目策略发起手部姿态检测
→ 正在准备 / 正在识别
→ 网页播放时查看候选骨架
```

## 2. 产品规则

### 2.1 自动媒体技术检查

1. 当文件上传完整性已由服务端确认、`ClipAsset` 已建立且对象可读时，平台必须自动确保存在对应的
   媒体技术检查；浏览器不得承担“上传成功后再发起检查”的责任。
2. 技术检查至少验证文件可读/可解码、媒体类型、时长、分辨率、帧率和已冻结的大小与摘要。它不替代
   人工质量判断，不改变正式标注、清洗、数据集或导出结论。
3. 同一资产、同一冻结输入只能存在一个活动或已完成的等价检查；重复上传完成通知、页面刷新和重试
   不得产生重复业务事实或泄露底层唯一约束错误。
4. 技术检查失败时，资产仍按既有播放授权规则决定能否人工查看；手部姿态分析必须进入失败或不可用，
   并给出安全、稳定的用户原因码。

### 2.2 手部姿态检测策略

项目必须有一个经审计的 `hand_pose_analysis_policy`，只允许以下值：

| 策略 | 行为 |
| --- | --- |
| `MANUAL`（默认） | 用户在 CaptureSession 详情点击一次“检测全部相机手部姿态”后，平台对该次采集的全部相机路持续编排。 |
| `AUTO_FOR_APPROVED_CAMERA` | 系统为 CaptureSession 的全部配置相机路持续等待媒体结果，并对其中符合全部准入的路自动发起分析。 |

只有 ACTIVE 项目 `ADMIN` Membership 的管理员可在书面 `GO` 后配置或变更该策略；变更只影响之后创建的
分析意图，必须记录操作者、原值、新值、时间和原因。策略不能绕过输入准入、模型审批或人工审核。

`MANUAL` 是默认策略：它减少无意 AI 处理与算力消耗，同时给普通用户保留单一、清楚的动作。获批项目
可选择自动策略，使正常上传流程达到零额外点击。

### 2.3 单一用户动作与状态

CaptureSession 详情的普通用户区域不得出现“检测媒体信息”“AIJob ID”“队列”“Worker”“模型 SHA”或内部
租约信息。在 `MANUAL` 策略且尚未请求时，只显示一个主操作：`检测全部相机手部姿态`。资产详情只显示
该路状态、结果与受控的单路重试，不要求用户逐路发起首轮检测。

对外分析状态固定如下：

| 状态 | 含义与页面表达 |
| --- | --- |
| `NOT_REQUESTED` | 尚未请求；显示“待检测”和主操作。 |
| `ANALYZING` | 已持久化本次 Session 的分析意图，至少一路仍在媒体准备或手部识别；`stage` 只可为 `MEDIA_PREPARATION` 或 `HAND_POSE`。 |
| `READY` | 所有可分析路已完成且至少一条候选可查看。 |
| `PARTIALLY_READY` | 全部相机路已到终态，但只有部分路可查看；必须显示逐路失败/不可用原因和重试入口。 |
| `FAILED` | 本次没有任何可查看结果且处理无法完成；响应必须带安全原因码和 `retry_allowed`。 |
| `INELIGIBLE` | 本次没有符合准入的相机路；响应带稳定 `reason_code`，不显示内部实现细节。 |

页面可按 `stage` 显示“正在准备视频”或“正在识别手部”，并显示 `completed_count / total_camera_count` 和
每路相机的状态。终态不再轮询；页面隐藏或卸载时停止刷新。用户关闭、刷新或切换页面不得取消已持久化的
Session 分析意图。

### 2.4 舱内相机准入与权限

手部姿态分析对 Session 中每一路分别判断；某一路只在同时满足以下条件时可用：

```text
ACTIVE project membership
AND 资产未删除
AND 上传完整性、输入大小和 SHA-256 已冻结
AND 媒体技术检查成功并达到 INGESTED
AND 唯一 CameraStream 绑定存在
AND CameraStream.camera_role 属于预先批准的舱内相机 role
AND 项目、相机和输入属于已授权且隔离的范围
```

相机角色必须在采集/资产建档时由服务端事实绑定和审计；文件名、目录、MIME 类型、客户端声明或 React
页面判断均不是相机准入证明。若既有 role 枚举不能表达“获批舱内相机”，实施前必须先冻结新 role、迁移、
授权和审计契约，不能将历史 `EGO` 枚举误用为佩戴式或固定机位的事实。自动策略只能在上述守卫全部通过后生效。

相机选择或视频列表必须根据接口返回的实际 `N` 路相机动态显示“相机 1 … 相机 N”。每个编号旁可渐进显示
已批准的安装位置/角色，但不得用内部 UUID 或文件名充当用户主标签；点击某一相机只打开该 CameraStream
绑定的视频及其分析结果。相机较多时使用可横向滚动的选择栏或下拉选择，不创建固定数量的 Tab。

### 2.5 结果、Overlay 与人工审核

1. 原始视频不可被检测过程覆盖或改写。正式结果是可追溯的 `CandidateAnnotation` 及其输入/profile 摘要。
2. 每路视频按冻结采样策略逐帧运行 MediaPipe Hand Landmarker。已推理但未拍到手的帧必须如实记录
   `hands = []`；拍到 1 或 2 只有效手时，分别记录每只手的 handedness、类别分数、bbox 和 21 个
   landmark。未推理帧、无手帧和有手帧必须可区分；不得把相邻帧结果复制到未检测帧。
3. 视频详情在该路候选可查看后提供 Overlay 开关，使用候选的图像宽高、时间戳、bbox、左右手、分数和
   21 个 landmark 绘制 bbox、骨架连线、点位及左右手标签。这是截图中“原视频上直接标出手部”的效果：
   只有拍到有效手的帧才出现标注，手离开画面或未检测到时不画。播放器同一时刻只绘制最近且在容忍范围内的
   一帧，不得叠加相邻帧形成双骨架。
4. 骨架在原视频像素坐标系中渲染；不同视频比例、缩放或黑边不得造成关键点偏移。Overlay MP4 可以作为
   后续可选预览工件，但不是候选真值、不是必需产物，也不能替代网页 Overlay。
5. 第一版只做每路视频的二维手部候选和 Overlay；不从多相机关键点推导三维空间轨迹、不输出场景俯视图、
   不进行跨相机手部身份匹配。截图中的空间/三维画面如需实现，必须另立需求、相机标定、同步、误差模型和
   验收标准，不能把它作为 MediaPipe 二维结果的默认承诺。
6. 机器结果只能停留在候选层；仍须按 V1.15 的 `ACCEPT`、`MODIFY`、`REJECT` 和既有复核流程，才可能
   形成正式 `AnnotationRevision`。检测完成绝不自动改变质量、数据集、导出或放行决定。

## 3. 可靠性、失败与可观察性

1. “请求检测”的意图必须由 Core API 持久化；不得由浏览器串联“媒体成功后再调用 AI”来实现。
2. 媒体检查完成、自动策略触发、AIJob 创建、Worker 回传和状态投影必须幂等，可在重复消息、进程重启、
   页面离开和短暂故障后恢复。
3. 同一 Idempotency-Key 加相同请求返回同一分析；相同 key 加不同请求返回稳定冲突。并发同一自然键
   只能产生一个等价分析，调用方得到一致结果。
4. `FAILED` 仅暴露用户可理解的稳定错误码；日志、响应、页面和审计不得暴露预签名 URL、lease capability、
   Worker 身份、存储位置、堆栈或模型部署密钥。
5. 可重试失败允许显式“重试检测”。重试复用冻结输入和完整 profile；输入、模型或 profile 改变时必须
   创建新的分析版本，不能把新结果混入旧分析。

## 4. API 与权限验收范围

实施时必须以版本化 OpenAPI 冻结以下产品契约，不以本文示例代替正式 schema：

| 产品能力 | 最小接口语义 |
| --- | --- |
| 请求批量分析 | `POST /api/v1/projects/{projectId}/capture-sessions/{sessionId}/hand-pose-analysis`；要求 Idempotency-Key；仅创建/确保该 Session 的分析意图和相机路快照。 |
| 查询批量分析 | `GET /api/v1/projects/{projectId}/capture-sessions/{sessionId}/hand-pose-analysis`；返回聚合公开状态、计数及动态相机路列表；每项仅返回公开状态、stage、eligible、reason_code、retry_allowed、更新时间及已获准的候选摘要。 |
| 重试单路 | 对失败且允许重试的 CameraStream 提供受控单路重试命令；它重验该路输入和权限，不重新发起整个 Session。 |
| 候选查看 | 保持候选读取与人工审核的独立权限；不得因可播放而自动获得候选审核或正式标注权限。 |
| 管理策略 | 管理员读写项目策略，变更审计且不得泄露模型、队列或基础设施细节。 |

接口响应不得把 `AIJob`、attempt、message、lease、RabbitMQ、Worker 或模型部署配置当作普通用户 UI 合同。

## 5. 端到端验收

在书面 `GO` 后，以下每项都必须使用合成 MP4 或明确授权、隔离的 Golden Set 证据验证：

| 场景 | 最小验收证据 |
| --- | --- |
| 自动媒体检查 | 每路上传完整性确认后，不依赖浏览器补调，恰好创建/复用一个媒体检查；成功和不可解码失败均有稳定状态。 |
| 手动一键 | 用户只点击一次“检测全部相机手部姿态”；关闭网页后，Session 中各路媒体准备完成仍继续创建并完成相应候选任务。 |
| 动态相机数 | 使用 2、4、6、8 路等合成 CameraSetSnapshot 验证：接口、队列、Worker 和网页均按返回列表处理，不含 `camera_number == 1/2/3` 分支或固定 Tab。 |
| 自动策略 | 获批舱内相机资产在 `AUTO_FOR_APPROVED_CAMERA` 下自动进入所属 Session 的分析；未获批相机、未授权或失败媒体绝不入队。 |
| 幂等与恢复 | 重复 HTTP、重复事件、并发请求、Worker 失联、迟到回传和重试不产生重复候选或错误泄漏。 |
| Overlay | 含无手、1 手、2 手片段的合成视频中：无手帧无 Overlay；有手帧的 bbox、21 点、骨架、左右手标签和时间同步正确；不同宽高比和 contain 黑边无偏移、无双骨架。 |
| 安全与隔离 | 所有候选保留输入/profile 审计；AI 输出不能自动成为正式标注或进入数据集/导出；响应、Outbox、日志和 DLQ 无 capability。 |

## 6. 非目标

本版本不增加实时摄像头推理、自动动作/Step/药品识别、跨视频身份追踪、自动正式标注、自动质量结论、
自动数据集放行、浏览器直连 Worker、模型运行时下载或新的通用工作流引擎。
