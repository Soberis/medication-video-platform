## 1. 产品定位与责任边界

Platform 是一个面向视频数据生产的处理平台。它接收外部采集端上传的视频和必要的接收声明，维护视频归组与媒体事实，运行 Media Probe、MediaPipe 和动作候选分析，在项目确实需要 human ground truth 时提供人工标注与确认，并生成受控的训练数据导出。

Platform 负责：

- 接收 Local Upload 或 External Ingest 提供的视频数据及其显式归属；
- 按 CaptureGroup 维护一次采集记录及其 CameraStream、ClipAsset 成员；
- 生成媒体技术检查、MediaPipe 检测和 Action Candidate 等可追溯事实；
- 在授权、版本、媒体身份和 provenance 校验下支持人工标注及受控导出；
- 维护权限、审计、幂等、重试、租约、心跳和失败恢复边界。

Platform 不负责：

- Hospital、Ward、Patient、Nurse、HIS 等医院业务或身份系统；
- 药品业务、处方业务、护理业务或医院工作流；
- physical camera fleet、物理摄像头资产、摄像头控制、标定或设备管理；
- 采集端运维、工控机控制、机器人、PLC 或其他真实硬件；
- 模型训练、训练效果保证或自动宣布数据合格；
- 从文件名、上传顺序或时间接近度猜测视频归属。

开发、测试和 CI 只使用合成数据；平台不得接触生产患者视频、医院生产账号、生产密钥或生产数据库。原视频、模型文件、令牌、私钥和预签名 URL 不得提交到仓库或写入日志。

## 3. 领域对象与命名

### 3.1 CaptureGroup 是一次采集记录

CaptureGroup 表示上游明确声明为同一次采集的一组视频及其接收事实。它是项目范围、成员边界、媒体事实、AI 证据、人工标注和导出的统一归属。

N=1 与 N>1 使用同一模型：

~~~text
CaptureGroup
└─ CameraStream #1..N
   └─ ClipAsset
~~~

N=1 只表示当前采集记录包含一路视频，不创建第二条 single-video 产品流程。

### 3.2 CameraStream 是视频视角

CameraStream 是 CaptureGroup 内的一个视频视角及其来源、时间基准和接收状态。它不是 Platform 管理的物理摄像头资产，不提供设备注册、设备生命周期、摄像头控制或摄像头 fleet 管理。

来源设备标识、camera index、camera channel、time offset 和 DeclaredSyncStatus 只作为外部来源与接入 provenance 保留。CaptureSession、CameraSet 及 metadata 声明仍是接入事实，不因“无设备管理”而删除。device_time_utc 表示拍摄侧时间，created_at 表示平台记录时间，二者不得混为同一时间。

### 3.3 ClipAsset 是不可变媒体证据

ClipAsset 代表受控对象存储中的一个视频版本及其内容身份。当前有效性必须由媒体状态、对象身份和 SHA-256 等事实证明；换源或重新绑定必须形成新的输入版本，不能改写已经引用的人工 revision 或 AI evidence。

## 4. 唯一主链

当前产品主链固定为：

~~~text
数据接收
  ↓
CaptureGroup
  ↓
Media Probe
  ↓
├─ MediaPipe 手部事实
└─ Action Candidate 动作候选
  ↓
自动生成标注草稿 → 人工可修改 → 显式提交 → AnnotationReview
  ↓
Export Eligibility
  ↓
human-demonstration-hdf5.v2
~~~

其中：

- 数据接收必须使用上游明确的 CaptureGroup 归属，不依据偶然文件特征自动合组；
- Media Probe 建立媒体技术事实，MediaPipe 与 Action Candidate 在媒体可读取后可以独立运行；
- 所有 ACTIVE 项目的媒体就绪视频默认自动派发 Action Candidate，不要求预先创建人工任务、指定负责人或完成人工质量确认；项目提供数据隔离与权限边界，归档项目不再新派发；
- 每份最终标注必须由授权用户显式提交；候选正确时可直接提交整份草稿，无须逐片段点击采纳；修改是可选操作；
- 每个 CaptureGroup 保持一个 AnnotationTask；标注员逐机位独立编辑并提交，或明确排除。单机位提交只确认该路结果，所有预期机位槽位（包括缺失机位）均已提交或排除后，才可创建一份整组 Revision 并统一送审；
- 每个机位保留自己的 ClipAsset、媒体输入版本、人工状态和原始时间轴。机位切换时播放器、播放头、候选、草稿和状态一起切换；不同视频时长不构成同步故障，不得用未经验证的时间偏移搬运区间；
- 只有显式建立的动作对应关系才可跨机位联动。对应可以确认为同一物理动作，也可以明确记录为不确定及原因；不因相同标签、相近时间或候选顺序推断为同一动作；
- Export Eligibility 是导出前的唯一后端权威判定；
- HDF5 是训练数据文件，不是关系数据库、原始视频备份或 AI 运行日志的替代物。

不建立通用 Workflow Engine，不持久化通用 next_action、blockers 或与当前主链无关的工作流状态。

主链表达职责顺序，不要求每条采集记录跑完两个 AI 分支。未启用人工标签的记录可停留在视频与 MediaPipe 证据阶段；由于当前唯一 HDF5 包含人工标签，该记录尚不能导出。纯人工标注不依赖 Action Candidate 成功，Action Candidate 也不是 HDF5 的硬闸门。现役 CaptureGroupView 只读投影和前端派生提示继续保留，不因名称含 View 或 blockers 被当作通用工作流删除。

## 5. 数据接收、媒体与项目工作区

### 5.1 接收与归组

- Local Upload 和 External Ingest 都必须将文件与显式的项目、采集记录和来源声明关联。
- 接收保留 upload batch、capture session、CameraStream、ClipAsset、声明值与服务端复核值。
- 多机位数据必须在同一个 CaptureGroup 中保留其成员边界；单路数据也使用 CaptureGroup。
- 平台不控制上传端的录制、缓存、重传策略和物理设备。
- 已发布的 external ingest compatibility API、历史 migration 和既有接收事实不得因产品概念收敛而自动删除。

上传声明、对象实际 SHA 和服务端复验分别保留；断点续传、幂等、接收关闭、缺失机位与媒体处理状态不能相互替代。metadata 与 ingest manifest 按各自已发布契约承载来源事实，不能假定互为副本。接收尚未闭合的记录不通过超时自动判合格；COMPLETE 与 CLOSED_INCOMPLETE 保留真实收件含义，不等于技术质量 PASS。

### 5.2 Media Probe

Media Probe 只产生媒体技术事实，例如可读取性、时长、帧率、编码和媒体报告。它不伪装成人工质量，也不直接宣布动作标签正确。

缺少已验证时长、媒体无法读取、当前 ClipAsset 不存在或输入身份不匹配时，后续依赖该事实的操作必须明确阻断或保持待处理，不得用默认时长、文件名或 UI 状态补齐证据。

## 6. 两条独立的 AI 证据链

### 6.1 MediaPipe 手部事实

MediaPipe 是几何检测证据链，只能写入 MediaPipe job、attempt 和 CandidateAnnotation 等机器事实，不得写入人工质量、AnnotationRevision、AnnotationReview、Cleaning 或导出批准结论。

逐视图机器状态保持不同语义：

- HAND_DETECTED：检测到一个或多个手部候选；
- NO_HAND_DETECTED：作业成功完成，但当前输入没有检测到手；
- UNKNOWN：结果暂时不能形成可用判断；
- FAILED：机器执行、解码或结果处理失败。

成功但没有手不等于失败。API 查询或读取 MediaPipe 结果失败属于结果可用性/读取故障，不得被改写为 AI job FAILED；只有作业执行失败或服务端明确判定结果失败时才改变作业失败状态。读取失败不能被当作有效空结果，也不能伪造坐标。

每项当前证据至少应能追溯到 CaptureGroup、CameraStream、ClipAsset SHA-256、输入摘要、算法/模型/profile、job/attempt、分析范围和结果摘要。迟到、重复或旧来源结果不得覆盖当前有效证据。

手部采样使用已冻结 profile 的真实 PTS 与固定目标时间网格，选择目标时刻及之后首个实际帧；不按假定帧率补帧。10 fps 是已有 MediaPipe profile 的采样规则，不是动作模型的采样率或检测精度承诺。handedness 仅作辅助元数据，不能作为人工标注、复核、Cleaning 或导出准入条件；21×3 landmarks 不代表经标定的真实世界三维轨迹。

### 6.2 Action Candidate 动作候选

Action Candidate 是机器生成的动作时间段草稿，是辅助人工工作的候选证据，不是人工 Ground Truth，不是质量结论，也不是可直接导出的最终标签。

动作候选规则：

- 派发时冻结不可变 label schema：已有人工任务使用其绑定版本，无任务时使用当前已发布全局版本；不硬编码动作标签，不因后来发布标签而改变运行中的作业；
- 片段保存 start_ms、end_ms、label，使用来源视频原始时间轴和半开区间 [start_ms, end_ms)；
- 必须满足 0 ≤ start_ms < end_ms ≤ 已验证视频时长；
- 单层 PRIMARY_STEP 候选不得重叠；空白表示尚未覆盖，不自动解释为 IDLE、无动作或不合格；
- 候选回传必须校验当前 job、attempt、来源视频、输入版本、schema、标签合法性、窗口完整性和 provenance；annotation_task_id 可为空，人工任务不是机器结果入库条件；
- 越界、非法标签、截断、重叠冲突或来源失效时，不发布为可采纳的完整草稿；保留可诊断的原始失败信息；
- 有效空数组表示本次模型没有给出候选，不证明视频没有动作；
- 模型自报 confidence 不是校准正确率；confidence 可缺失，不补造数值，也不因缺失而判作业失败。字段、时间和来源合法只能证明结果可用，不能证明动作标签正确；
- 原始 AI 输出只保存为候选；自动初始化草稿不生成正式 Revision、不代替提交、不生成 Review。

动作预标注不等待 MediaPipe 成功。配套 HDF5 导出才要求当前 MediaPipe 证据和人工标签同时满足最终准入。

### 6.3 自动候选、独立人工任务与显式提交

媒体处理完成且 ClipAsset 有效时，动作候选与手部检测事实按机位独立生成；AI 状态单独呈现，不推进人工处理状态。每路结果保留自己的视频身份、原始时间戳、帧范围与 provenance。

派发仅依赖 ACTIVE 项目下当前有效、已完成媒体处理的视频和已发布 schema，不等待 MediaPipe。后台有界扫描可在重启后补齐尚未派发的媒体，包括已有的就绪视频；同一输入已有动作作业时不重复创建，不因人工任务创建或全局 schema 更新自动重跑，终态失败使用既有重试机制或授权手动重试。部署可用全局开关暂停自动调度，不配置项目白名单或负责人。

重复事件、重试和不同到达顺序按既有 job/attempt 与幂等机制收敛。有效候选自动呈现为初始草稿；异常给出原因并允许人工从零标注。人工一旦编辑或提交，后到候选不能自动覆盖。

人工 AnnotationTask 在进入人工提交流程时按既有权限准备，不再是 AI 前置条件。最后由授权用户显式提交整份标注，生成不可变 Revision，再沿用现有 Review。人工质量、任务归属与 HDF5 准入保留在各自步骤；自动化不伪造人工质量结论、提交人或审批人，不新增自动批准状态或通用策略引擎。

### 6.4 动作推理与资源边界

首轮沿用已选定的评估起点：RTX 4090 24GB、Qwen/Qwen3.5-4B、BF16、每卡一个串行消费者。15–30 秒窗口、1 fps 基线及 2 fps 对照是待实测配置，不是产品准确率、吞吐、显存上限或无 OOM 承诺。模型与依赖固定版本，模型在仓库外受控准备并记录 SHA-256，运行时只从本地加载。

长视频必须保留真实时间戳、窗口边缘上下文和回映射，不能以假定 30 fps 或静默裁剪修正非法输出；重复动作不能仅凭同名与时间相交自动合并。完整窗口校验失败时报告失败，保留人工入口。平台内合成占位 Worker 只证明契约路径；外部动作 Worker 的真实推理、显存与质量须单独验证。首版不增加 YOLO、训练、模型服务平台或历史任务批量回填。

## 7. 标签 Schema

标签库是全局账号级资源。全局 ADMIN 可发布标签；普通成员只能读取被授权的当前 schema。项目级 GET 可作为任务页面的兼容读取入口，但标签真源仍是全局不可变 schema。

每次发布得到新的不可变 schema 和 schema digest：

- label_id 稳定且机器可用；
- display_name、description 和起止判据面向标注员；
- 新任务绑定创建时的 schema；
- 已有任务、revision、候选和导出历史继续使用原 schema/digest；
- 不编辑、删除、排序或按项目覆盖已经发布的标签语义；
- 不因模型输出自动创建标签；
- Worker、前端和服务端优先读取任务绑定的 schema，不以本地调色板或旧版本硬编码作为业务真源。

派发时存储 job 的 schema 快照，回传按该快照校验。无人工任务是正常场景，不等于缺少 schema；执行期间发布新全局 schema 不改变已有 job 的标签集合。候选进入人工草稿时必须匹配当前人工 schema 与来源视频；不匹配时不静默转换或覆盖，可继续人工编辑。标签显示名称、说明、起止与易混淆判据应可从该版本解析；颜色映射只负责展示。

project-scoped 标签 POST 已在 dev 首轮收缩中退役；全局标签发布 POST 与项目级兼容读取 GET 保留。若仍发现仓库外消费者，必须通过兼容方案恢复或迁移，不得静默绕过契约。

## 8. 人工标注、确认与 Revision

AnnotationTask 是 CaptureGroup 的人工标注处理记录，不是 AI 作业的前置条件。当前授权用户分配入口与提交前的任务准备继续保留。任务页面是视频工作区中的视图；系统自动准备候选草稿，用户可修改，最后显式提交。

每个 CaptureGroup 保持唯一任务及版本历史，不因重复事件或命令重复建单、悄悄改派或覆盖既有结果。系统不设人为的主副机位之分，拍摄组内的所有机位均为等权客观观测；手部骨骼与动作时序在各机位上由 AI 自动检测生成，标注员核对全组各机位的动作起止与画面对应事实后显式提交整组 Revision；复核员对各机位的对应结果进行逐项与联合核验，审核通过后方可完成任务并准入导出。输入变化时由授权管理员显式更新任务输入并返工，旧 revision 与对应事实保留审计。ACTIVE 项目成员均可查看、编辑和提交本项目人工任务；管理员还可复核，包括复核自己提交的内容。assignee 仅保留首次负责人记录，不作为读写限制。成员可以在首次人工提交时为自己准备任务；已有任务直接复用，不改派。为其他成员分配任务及刷新已变化的输入仍需管理员。AI 自动派发不创建人工任务，也不代替人工提交。

同一 AnnotationTask 为当前确认机位集合中的每个 camera_number 保留一份服务端状态，缺失视频的预期机位也占一个槽位。每路人工状态为 PENDING（待处理）、DRAFT（编辑中）、SUBMITTED（该机位已提交）或 EXCLUDED（明确排除）；MediaPipe 与 Action Candidate 的 AI 运行状态独立显示。保存、提交、排除和恢复均校验机位版本与组输入版本，并保留操作者、时间、视频来源及历史。排除不删除或隐藏 ClipAsset；恢复后的机位回到待处理并须重新确认标注。

标注员可以在每路视频自己的原始时间轴上：

- 创建、修改、删除、拆分、合并和撤销动作片段；
- 调整 start_ms 和 end_ms，或使用当前播放时刻设置边界；
- 从任务绑定 schema 中选择合法标签；
- 检查候选覆盖与所有空白，不能把播放过当作人工确认；
- 在无法判断时保留空白，不能补写没有画面证据的动作。

每路可独立保存草稿、提交本机位标注或明确排除。提交本机位只将该路状态设为 SUBMITTED，不创建 AnnotationRevision、不推进其他机位，也不代表整组已复核。排除需记录原因和审计；恢复后回到待处理，先前提交不能被静默复用。页面显示已提交/已排除/待处理的组内进度，AI 状态另行呈现。

整组送审命令必须携带期望任务版本与输入版本。服务端仅在全部预期机位均为 SUBMITTED 或 EXCLUDED、至少一个机位为 SUBMITTED、没有待保存草稿且现有质量准入仍有效时，原子冻结 append-only `annotation-document.v2` 并创建一个 AnnotationRevision。文档逐机位保存 ClipAsset/CameraStream 身份、源哈希与版本、处置、各自时间轴区间及候选 provenance；区间不得套用其他机位的时间戳。每个跨机位动作关联以显式 correspondence 保存：CONFIRMED 表示已核实为同一物理动作；UNCERTAIN 必须给出原因，不确定或未发现对应动作不得被自动判为一致。没有被明确关联的区间不跨机位联动。

整组 Revision 仍须经过现有 AnnotationReview 才能批准，也不自动导出。Review 必须记录已核验的全部机位；批准要求完整覆盖快照中的所有机位。拒绝时可以指定一个或多个待返工机位，未指定机位的已提交/排除决定保留，指定机位重新打开编辑或重新处置，之后生成下一份整组 Revision。保存草稿、打开页面、单路提交或 AI 作业成功均不构成整组提交。

沿用当前权限语义：全局 ADMIN 且具有 ACTIVE 项目 ADMIN Membership 的管理员可以确认自己提交的标注，不要求额外的日常双人确认；非授权用户不得提交或确认。被拒绝的 revision 不被改写，返工形成新的 revision 并保留审计。

如果人工草稿使用了 Action Candidate，revision 必须保留其来源 job/候选关联或等价的可查询 provenance。候选晚到、重新推理、输入变化或 schema 变化都不得静默覆盖页面未提交内容、既有草稿或已提交 revision。

### 8.1 初始化、编辑与失败恢复

- 仅完整校验通过、来源当前有效且任务从未编辑时，自动将候选呈现为待人工检查的初始草稿；此操作不生成正式 revision、不提交质量或 Review。
- “未编辑”同时检查服务端版本和浏览器未保存修改；用户清空草稿也算编辑。候选晚到或版本改变时提示用户，不覆盖现有工作。
- 解析失败、部分窗口失败、来源失效和有效无候选分别反馈。部分结果仅供诊断，首版不允许选择性采纳失败作业；人工仍可从零标注。
- 时间轴支持多机位联动查看与各机位对应事实核对，支持拖动边界，也提供数字输入、设为当前时刻等非拖拽等价操作；各机位保持自己视角的时间戳与帧范围，实事求是一一对应。
- 保留全部空白并支持按时间顺序巡检，不以固定阈值隐藏短空白；长候选内部也可拆分补标。毫秒是存储单位，不承诺模型或播放器具有毫秒精度。
- 折叠、切换机位、离开或刷新不得静默丢失未提交输入。Tab 保持原生导航，快捷键不干扰输入框，按钮提供等价操作。

### 8.2 最小状态与提交边界

复用既有状态，不新增 AUTO_APPROVED、HUMAN_APPROVED 或第二套机器批准对象：

| 阶段 | 当前事实 | 是否可导出 |
| --- | --- | --- |
| AI 处理中 / 草稿待提交 | job 状态与可编辑候选；任务通常为 ASSIGNED | 否 |
| 逐机位处理中 | 每个槽位独立为 PENDING、DRAFT、SUBMITTED 或 EXCLUDED；AI 状态单列 | 否 |
| 全机位已处置 | 所有预期机位已提交或排除、至少一路参与、无未保存修改 | 尚未送审，不可导出 |
| 整组已提交 | 新的 `annotation-document.v2` Revision 冻结各机位区间、处置与动作对应 | 否，等待既有复核 |
| 已复核 | Review APPROVED 且确认覆盖全部机位，任务 COMPLETED | 仍须通过最终导出校验 |
| 指定机位退回 | 保留旧 Revision；仅返回机位重新处理，其余已确认结果保留 | 当前待修改版本不可导出 |

最后提交是必需动作，人工修改是可选动作。现有复核权限保留，符合条件的管理员可以复核自己的提交；本次不将提交与复核合并成一个新 API。自动保存与候选初始化不得调用提交或复核接口。

## 9. Quality、Review 与 Cleaning 语义

以下事实保持区分：

- Media technical quality：媒体/设备技术状态，是媒体有效性的事实；
- CaptureGroup quality review：判断该采集记录是否允许进入人工标签流程；
- AnnotationReview：判断人工 revision 的标签质量；
- Export Eligibility：判断当前记录是否满足最终训练导出全部条件。

Cleaning 不再作为用户必须经过的工作流阶段。它没有独有的数据清洗动作，而是对已有人工质量、组质量、Review、媒体和输入条件的确定性复算。D1 已决定停止新的独立 Cleaning 写入和 recheck 操作；当前 runtime 只保留历史 Cleaning 表、实体、查询和只读展示兼容，不删除字段、migration 或历史数据。

Quality、Review 和 Export 的职责不能因为“简化”而互相伪装：人工 Review APPROVED 不等于媒体技术质量通过，MediaPipe 成功不等于人工标签正确，前端状态也不等于后端最终放行。

## 10. 唯一导出与 Export Eligibility

### 10.1 唯一产品导出

当前唯一用户可见训练导出格式是：

~~~text
human-demonstration-hdf5.v2
~~~

不恢复 hand-landmarks.v1 CSV、human-annotations.v1 CSV、旧事件 manifest、training-data.v2、LIBERO/robomimic、LeRobot、RLDS、Parquet 或其他第二套训练导出。

### 10.2 导出 UI：一个列表、一套选择交互

导出入口位于当前项目的视频工作区，提供当前项目可导出记录列表：

- 默认不选；
- 勾 1 条表示单条导出；
- 勾多条表示多条导出；
- 全选表示本次完整加载的当前项目可选择记录；这些记录仍须通过下载时的后端最终校验；
- 显示已选择 N 条；
- 候选列表独立读取当前项目完整授权范围，不以视频分页列表的已加载页冒充项目全集；
- 下载始终携带明确的 capture_group_id；零选择不能下载；
- 列表加载中不可选择，失败可重试，下载失败不静默跳过失效记录；
- 详情页不另建第二套导出范围或数据集版本概念。

前端“可选择/可导出”只是 UX 初筛与预判。前端不得把已完成、已批准或本地状态直接表述为最终导出成功。

入口要求全局 ADMIN 与 ACTIVE 项目 ADMIN。候选列表通过现有 cursor API 读完项目 CaptureGroup 和 PROJECT 授权范围的人工任务，按 ID 去重；正常显示 COMPLETED 且当前 revision APPROVED 的记录，并标为“可选择”。缺页、失败、取消、游标循环或非 PROJECT 响应不能当作项目全集。关闭弹层终止读取并忽略迟到响应；重新打开重新读取，下载失败保留选择。

此人工条件初筛可能包含后端最终拒绝的记录，不能宣称是最终资格集合的子集。全选不包括打开列表后尚未展示的新记录；用户无需另选“单条/多条/全部”范围。旧 API 省略 ID 的行为仅作兼容保留，当前 UI 始终发送明确 ID。

### 10.3 后端最终 fail-closed 条件

下载时后端重新读取并校验每一条所选记录。最终可导出至少同时满足：

- 当前用户为全局 ADMIN 且具有 ACTIVE 项目 ADMIN Membership，项目仍为 ACTIVE，且选择范围属于当前项目；
- 视频和 ClipAsset 当前有效，对象身份与 SHA-256 可证明；
- Media Probe 与媒体状态有效，存在已验证视频时长；
- 技术质量达到最终批准要求；是否额外要求 stream/session 的 quality_status = PASS、适用哪些视图及如何处理 WARNING/PENDING/REJECT，由 D2 决定，PASS 不能替代其他守卫；
- CaptureGroup 人工质量允许进入标注；
- 当前输入对应的最新整组 Revision 已由授权用户显式提交，AnnotationReview 为 APPROVED，任务为 COMPLETED；不得回退读取旧输入或旧批准结果来补资格；
- Revision 中每个参与机位的标注区间均与其自身当前视频 SHA、输入版本和 provenance 一致；排除机位不得贡献导出样本；
- 当前 MediaPipe 结果来源、job/attempt、model/profile、input/result 摘要有效；
- 该 episode 的已批准区间集合内至少存在一条实际的当前 MediaPipe sample；不要求每帧都有手，也不把“每个区间必须有样本”作为未经批准的新规则；
- 当前运行配置满足 synthetic-only 与其他治理要求；
- 上述必需证据不存在失败、来源漂移、未完成或不可证明状态；可选 Action Candidate 失败不单独阻断导出。

任一所选记录失去资格，整次选择拒绝；不得静默生成部分文件、跳过失效项或生成空的“可训练”文件。Export Eligibility 是组合后的后端权威判断，可以由各模块提供只读事实并在不同阶段复验，不要求集中成一个巨型服务或删除必要的重复校验。前端初筛、人工提交守卫和最终导出校验职责不同，应保留。

D2 未决期间不凭本文放宽或新增 runtime 条件，也不声称技术质量目标已验收。V73 的旧 eligibility 视图已经由 V75 迁移退役；当前收敛不恢复该视图，不能将历史 SQL 当作仍在线的第二真源。迁移执行情况属于具体环境事实，本次未查询数据库。

### 10.4 HDF5 语义与布局

一个合格 CaptureGroup 对应一个 HDF5 episode，单次选择生成一个 HDF5 文件。多机位扩展继续使用 `human-demonstration-hdf5.v2`：`samples` 仍是训练主数据面，保留当前 dual-hand tensor 与 columnar table 两种布局，但每行/每步显式带 `camera_number`，用 `(camera_number, frame_timestamp_ms)` 作为样本键。

~~~text
data/demo_000000
├── attributes：采集组、revision、label schema/digest、输入版本、参与机位数
├── annotations
│   ├── camera_number、segment_id、segment_start_ms、segment_end_ms、label
│   ├── source_candidate_id/source_candidate_segment_index：动作候选 provenance
│   └── correspondences：对应 ID、CONFIRMED/UNCERTAIN 状态、原因及机位/区间成员
├── samples
│   ├── sources/camera_NN：CameraStream、ClipAsset、AI job/attempt、算法、model、profile、input/result provenance
│   ├── camera_number（与每步或每行对应）
│   ├── frame_timestamp_ms
│   ├── segment_start_ms、segment_end_ms、label、image_width、image_height
│   ├── landmarks[K,2,21,3]、hand_mask[K,2]、handedness_score[K,2]（dual-hand tensor）
│   └── candidate_provenance：MediaPipe candidate_annotation_id 到 tensor step/手槽的链接；table 布局则每行直接包含 MediaPipe ID 与 hand_index
└── views/camera_NN（仅 include_raw_candidates=true 时）
    ├── attributes：视频身份、检测状态与可用 provenance
    └── candidates（该参与机位成功的全量检测样本）
~~~

`samples` 关联拍摄组中实际存在、且落入同一 `camera_number` 已批准人工区间 `[start_ms, end_ms)` 的 MediaPipe sample；样本时间戳与区间边界均使用所属机位的原始时间轴，不跨机位套用区间。dual-hand tensor 按 `(camera_number, frame_timestamp_ms)` 分步，同一时间戳出现在两个机位时仍是两个独立样本；不设主副机位偏见，不为未检测到手的帧补造坐标。排除机位不进入 `samples` 或可选的 `views/camera_NN/candidates`。`samples/sources/camera_NN` 保留每路 CameraStream、ClipAsset、MediaPipe job/attempt、algorithm、model、profile、input 和 result provenance；`candidate_annotation_id` 仅标识 MediaPipe 手部样本。动作候选来源 ID 独立保留在 `annotations`，不会与 MediaPipe sample ID 混淆。

开启 `include_raw_candidates` 时，`views/*/candidates` 保留所有参与机位的全量检测样本；`samples` 保留这些机位各自在获批动作区间内的检测样本。动作对应关系及 `UNCERTAIN` 原因以 Revision 的显式 mapping provenance 导出；时间戳仍为每路本地时钟，不隐含精确同步或相同长度。各机位平等保留来源信息与真实时间戳，满足下游多视角学习需求。input SHA、model SHA、样本标签与区间等来源信息继续保留，不因字段值相同而删除。

HDF5 不包含 MP4 字节、对象存储键、预签名 URL、患者身份、机器人状态、控制动作、虚构的 states/actions/reward/success 或模型训练结果声明。

## 11. API、契约与兼容面

### 11.1 当前保留

- CaptureGroup、CameraStream、ClipAsset、媒体检查、MediaPipe、Action Candidate、人工任务、Revision、Review 和 HDF5 所需的现有 API；
- external-video-ingest-v1 与 external-video-ingest-v2 兼容面，除非完成仓库外消费者审计并获得明确退役决定；
- 全局标签 schema GET/POST；
- 项目级标签 schema GET，直到任务页面不再消费；
- 已发布的 OpenAPI、事件 schema、Worker 回传契约和历史兼容事实；
- legacy annotation-tasks 与 project label library redirect，直到外部 bookmark 和消费者完成确认。

### 11.2 目标收敛

- project-scoped 标签 schema POST 进入退役流程，不在本阶段删除；
- Action Candidate 的 schema、provenance 和版本必须以派发时冻结的作业上下文为准；草稿与已提交 Revision 必须可区分；
- Export Eligibility 只保留一套后端权威判定；
- 不新增通用 workflow API、DatasetVersion、导出历史中心、后台导出队列或第二套范围概念。

任何 API、事件、HDF5 layout 或 JSON Schema 变更都必须同步更新公开契约、兼容性测试、实现和验收记录。当前文档修改只定义目标语义，不宣称相关 runtime、Worker 或契约已经完成。

## 12. 模块、异步与可靠性约束

Platform 使用一个 Java 21、Spring Boot、Spring Modulith Core API。核心领域模块包括 iamproject、assetcapture、mediaprivacy、annotationreview、qualitycleaning、datasetexport、aicandidate 和 governance；integration 只承载 CVAT、S3、RabbitMQ、OIDC 等端口与适配器，不拥有业务真值。

模块只能写自己拥有的表。跨模块写入通过公开应用服务或版本化领域事件；跨模块读取通过公开查询接口或只读投影。Python Worker 只处理媒体和 AI 作业并回传结果，不直接写业务表。

以下可靠性边界是产品数据可信度的一部分，必须持续保留：

- ai_job 与 ai_job_attempt：作业事实和单次执行事实分开；
- inbox、outbox：消息去重和事务性派发；
- lease、heartbeat：执行所有权与存活证明；
- retry、退避、死信和受控恢复；
- idempotency：重复请求、重复投递和重复结果不产生第二份业务事实；
- 最小 provenance：ClipAsset/input 身份、任务 schema 版本、模型版本、job/attempt；只有模型制品和视频身份需要的 SHA-256 必须保留，result digest 仅在实际用于去重或审计时保留；不对代码文件、每个字段或每次查询重复计算哈希；
- 原始输入、执行 attempt、错误原因和追加式审计；
- 导出 fail-closed 与来源漂移拒绝。

Redis 不作为事实数据库，RabbitMQ 不保存最终业务状态，对象存储不承载关系型业务状态。耗时、跨进程或需要重试的工作使用受控异步作业；可以在单个 Core API 事务内可靠完成的操作不额外引入消息或缓存。

当前界面规则：

- 视频是主要工作入口；列表展示当前项目的采集记录，详情以播放器和当前机位为主；
- 多机位使用紧凑切换，明确当前视角和缺失原因；每路独立保留播放头、候选、草稿与状态，切换不丢修改，也不暗示未经证实的同步播放；
- 每路标注具有待处理、编辑中、已提交、已排除四种人工状态；AI 检测状态单独显示，不以 AI 完成代替人工提交。排除保留视频、理由和审计记录，可恢复并重新确认标注；缺失机位也必须提交明确排除决定；
- 当前机位可保存草稿、提交本机位标注或排除此机位；顶部显示整组已提交/已排除/待处理数量。单路提交不完成其他机位，也不生成整组 Review 结果；
- 仅当全部预期机位均已提交或排除、至少一个机位参与、无未提交修改并满足现有准入条件时，才允许提交整组复核；
- Review 逐机位检查已提交标注、手部检测证据或排除理由，并确认跨机位动作对应。通过是一次整组决定；退回可指定机位，已保留的其他机位提交及过往 Revision/Review 不得静默覆盖；
- 视频时长不同本身不显示为同步错误。只有存在明确对应关系的动作才允许跨机位联动定位；不确定对应关系须保留原因，不自动判为一致；
- 任务是视频工作区中的视图和待办，不另建并行产品页面；
- 标注面板按需展开；候选仅在任务从未编辑且来源有效时初始化。服务端版本和浏览器未保存修改都须检查，所有自动化路径遵守同一防覆盖规则；
- 候选冲突、部分失败、来源失效或任务已有编辑时，不静默覆盖，允许人工从零标注；
- 结果状态用准确文字表达，不能只靠颜色，也不能把查询失败猜成作业失败；
- 技术 ID、模型参数、历史和审计渐进披露；真实阻断、权限提示、失败原因和未提交修改始终可见；
- 状态中文映射属于 presentation 层，重复 formatter 计划合并，但不改变服务端事实；
- 当前项目导出列表是唯一导出交互；不在行、详情或任务页面扩散第二套导出入口；
- legacy redirect 暂时保留，不再新增旧页面、旧文案或旧组件依赖。

页面简化的目标是减少重复判断和点击，不是隐藏草稿来源、人工接管、失败恢复或最小 provenance。

### 16.1 验收分层

文档验收检查本文自包含、入口、分类清单、需求追踪和摘要一致性。实现验收按受影响链路运行合成测试及契约检查；真实模型集成验收另需锁定环境和运行证据。历史测试通过数不作为 V1.35 验收结果。

### 16.2 人工减负试验

先用合成片段验证解析、时间映射、重复/快速动作、空白、遮挡和错误恢复；再比较“从零标注后提交”和“自动草稿、可选修改后提交”两种路径。使用相同标签判据和独立质量复核；合成样本仅证明流程，不能证明真实模型准确率。

| 指标 | 固定口径 |
| --- | --- |
| 人工成本 | 人工总分钟 / 视频总分钟，包含检查、补标、修改、提交、复核返工和 AI 阻塞等待 |
| 节省比例 | 1 − AI 辅助组单位视频人工耗时 / 纯人工组单位视频人工耗时；至少 30% 为试点目标，非保证 |
| 草稿可用率 | 完整有效草稿数 / 符合动作处理准入的记录数；同时报告空结果、失败、人工修改比例和样本量，不等同于标签正确率 |
| 最终标签质量 | 报告漏标、误标、类别与边界误差；预先固定质量容差，不以平均耗时掩盖质量下降 |
| 模型诊断 | 同类片段一对一匹配的 precision/recall、时间 IoU、边界误差；未匹配片段计入漏检/误检 |
| 资源稳定性 | 冷启动与热启动分开；报告解码到解析的端到端耗时、峰值显存、失败率、OOM、样本量和不确定性 |

按人员、批次和难度分组并交叉分配，避免同一操作的切片或机位泄漏到调参集和评估集；按完整视频或批次统计，不把相邻帧当独立样本。匹配阈值、边界容差与质量可接受差异在试验前确定；样本不足不标记通过。1366×768、1440×900、1920px 及既有窄屏回退需覆盖播放器、面板、未保存保护和键盘操作，不新增视觉体系。
