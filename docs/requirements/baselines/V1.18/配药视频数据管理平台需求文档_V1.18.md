## 1. 唯一产品主线

平台对接但不控制医院边端设备或采集系统。边端负责固定相机采集医护人员配药动作、本地缓存、分段和上传时机；平台接收视频和元数据，并在云端完成唯一的数据生产主线：

```text
边端对接接收
→ 视频与数据管理
→ 单视频 MediaPipe 手部预标注
→ 配药动作标注与复核
→ 数据清洗
→ 可用数据
→ 后续数据集构建与导出
```

平台不向边端发送采集、停止、缓存、删除或上传触发命令。相机是舱内固定相机，数量为动态 N 路；医护人员不佩戴相机。

当前产品语言统一使用“配药动作标注”。历史代码、表、API 或文档中的 `EgoAnnotation`、`EGO` 仅是内部兼容标识，不表示第一人称或佩戴式视频；新页面、需求、技术设计和用户文案不得再把它展示为“Ego 标注”。

## 2. P0/P1 范围与权限

### 2.1 优先级

| 范围 | P0 | P1 或以后 |
| --- | --- | --- |
| MediaPipe | 单个已入库视频发起、查看状态和 Skeleton Overlay | 显式多选批量预标注；项目自动预标注策略 |
| 数据管理 | 分页、稳定排序、来源/时间/相机/状态筛选、播放 | 复杂跨项目报表与任意条件分析 |
| 标注清洗 | 配药动作 schema、任务、revision、复核、清洗和可用数据 | 新标签体系、外部标注工具集成、训练运行 |
| 数据集 | 清洗通过的候选查询和可追溯性 | 冻结、导出和模型训练的新增演进 |

P0 的完成定义是“一条视频从接收，到手部候选，再到人工配药动作标注、复核和清洗结论”的可验证闭环。批量和自动策略不得阻塞该闭环。

### 2.2 权限

项目 `MEMBER` 和 `ADMIN` 均可在有权访问、`INGESTED`、未删除且相机已启用手部检测的单个视频上发起一次幂等手部预标注，并查看候选和 Overlay。`ADMIN` 额外负责模型、`enabled_for_hand_detection` 相机设置、P1 批量或自动策略、删除和运维恢复。所有实际权限仍以 Core API 的项目 Membership、资产归属和状态守卫为准，隐藏按钮不能替代服务端授权。

## 3. 多相机归组与稳定编号

多相机归组必须由上游显式提供，平台禁止通过文件名相似、采集时间邻近、上传顺序或 `camera_number` 猜测归属。

每个上传 manifest 必须携带唯一 `capture_group_key`。上游已有稳定 `external_capture_session_id` 时，该值作为 `capture_group_key`；没有时，上游必须在 manifest 提供稳定、不可复用的 `platform_capture_group_key`。一个组至少定义：来源系统、来源设备、采集开始时间、预期相机编号集合和视频条目。

`camera_number` 必须为正整数，并在同一 `capture_group_key` 内唯一、建立后稳定。预期相机集合为 `[1,2,3,4]` 而相机 2 缺失时，页面必须显示“相机 2 缺失”；不得因缺失、上传到达顺序、检测状态或删除而重编号其他相机。

`video_id` 是产品 API 的 `clip_asset_id` 别名：数据库不新建第二个视频 UUID，所有产品路由以 `video_id` 表达但映射至既有 `clip_asset_id`。

## 4. 三层状态与结果语义

平台不得用一个字段串联上传、媒体和 AI 事实。状态分层如下：

| 层 | 正式枚举/事实 | 含义 |
| --- | --- | --- |
| Asset | `UPLOADED`、`INGESTING`、`INGESTED`、`INGEST_FAILED` | 上传后的媒体入库状态 |
| Hand job | `NOT_REQUESTED`、`QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED` | 单视频预标注生命周期；`NOT_REQUESTED` 是无 job 的查询投影 |
| Hand result | `UNKNOWN`、`HAND_DETECTED`、`NO_HAND_DETECTED` | 成功分析的语义结果，独立于 job 状态 |
| 用户显示 | 上传中、待检测、检测中、已完成、失败 | 由 Asset 与 Hand job 投影，不向用户暴露内部枚举 |

只有 Hand job 为 `SUCCEEDED` 时才可将 Hand result 置为 `HAND_DETECTED` 或 `NO_HAND_DETECTED`。`SUCCEEDED + NO_HAND_DETECTED` 表示任务已完整执行但未发现有效手部，绝不等同于失败。

每个成功或失败的手部 run 必须保存摘要：`total_video_frames`、`inference_frame_count`、`frames_with_hand`、`frames_without_hand`、`left_hand_detection_count`、`right_hand_detection_count`、`invalid_landmark_count`、`processing_duration_ms`、输入和模型摘要。无手帧不要求逐帧写 PostgreSQL 行。

## 5. 候选、标注与清洗

MediaPipe 只产生 `CandidateAnnotation` 和 run summary。候选可在播放器 Overlay 中辅助标注，但不会自动创建正式标注、通过复核、通过清洗或进入可用数据。

正式配药动作标注由人工创建 versioned schema 下的 revision；退回后必须创建新 revision，旧 revision 不覆盖。清洗独立判断媒体、元数据、标注完整性、时间范围、schema 一致性和质量结论。只有人工标注、复核和清洗满足相应守卫的数据才可进入可用数据视图。

## 6. 算法评估与调参

MediaPipe 基线为离线 Hand Landmarker `VIDEO` 模式，每路独立、10 FPS、最多两只手、三个置信度阈值暂为 0.5。它是待评估基线，不是效果承诺。

在明确授权、隔离的评估样本上记录以下指标；无证据的数值必须为 `PENDING`，不得伪造阈值：

| 指标 | 当前阈值 |
| --- | --- |
| 有手帧召回率 | `PENDING` |
| 无手帧误检率 | `PENDING` |
| 21 点有效率 | `PENDING` |
| 左右手正确率 | `PENDING` |
| 快速运动/遮挡场景可用率 | `PENDING` |
| Overlay 时间误差 | `PENDING` |
| 每分钟视频处理耗时 | `PENDING` |
| Worker 中断恢复 | 必须通过 |
| 原视频不被改写 | 必须通过 |
| AI 候选不自动转正式标签 | 必须通过 |

评估记录必须绑定样本版本、模型摘要、profile 摘要、指标和参数调整说明。允许在授权样本上调整 ROI、采样率和阈值；更换模型时另建对照记录。评估不作为阻塞合成测试视频检测或网页 Overlay 的额外启用门禁。

## 7. 容量与候选存储决策

10 FPS、两只手的理论上限为每分钟 1,200 条 hand candidate。以 1,000 个 10 分钟视频估算，可能产生约 12,000,000 条候选。现有 PostgreSQL `candidate_annotation` 仅作为当前 P0 单视频闭环的真值存储，不默认承诺长期承载全部密集帧级结果。

进入 P1 批量预标注前，必须按平均/P95 视频时长、平均相机数、日视频量、候选密度、30/90/365 日保留期和查询模式完成容量评审。评审结论在以下两种方案中明确选择：

1. 经分区、索引、保留策略验证后继续使用 PostgreSQL 存储 dense candidate；或
2. PostgreSQL 保存 job、summary、索引和人工处置事实，帧级密集结果保存为版本化 S3 JSONL/Parquet 工件。

未完成容量评审前，P1 批量和自动预标注保持关闭。

## 8. 验收与实施顺序

1. 冻结并验证 `external-video-ingest-v1` 接入契约；
2. 验证显式归组、稳定相机编号和单视频云端接收；
3. 完成 P0 单视频手部预标注、run summary 和 Overlay；
4. 完成配药动作标注、revision、复核和清洗闭环；
5. 在授权评估样本上记录效果、耗时和参数调整；
6. 完成容量评审后才决定 P1 批量、自动策略和 dense result 存储。

开发、测试和 CI 只使用合成或明确授权且隔离的数据；不得接触真实患者视频、生产账号、密钥或生产数据库。
