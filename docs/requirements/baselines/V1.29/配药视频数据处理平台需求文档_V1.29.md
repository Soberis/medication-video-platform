# 配药视频数据处理平台需求基线 V1.29

状态：DRAFT  
发布日期：2026-09-04  
主题：数据组主线收敛与 Runtime Simplification

界面命名与交互以 [2026-09-05 视频工作区体验补充](./v1.29-video-workspace-ux.md) 为准：导航使用“视频”，聚合范围解释为“采集记录”。本页历史领域用词不作为界面文案。

## 1. 背景与调整原因

V1.28 将产品收敛为唯一 `CaptureGroup` 路径和 `hand-landmarks.v1` 导出，但仍把人工质量、标注、复核和 Cleaning 描述为每个数据组的默认线性流程。最新业务定义更窄：平台接收外部采集端上传的视频数据，完成归组、媒体检查、MediaPipe 分析、必要的人工训练数据处理和导出。

因此，V1.29 将默认主线收敛为“数据组与机器证据”，把人工链定位为按项目实际需要启用的 human ground truth 能力。此 DRAFT 只冻结目标边界，不授权删除、迁移或改变现有 runtime、API、数据库、Worker、MediaPipe 参数、业务状态或审计记录。

## 2. 产品定位

本平台是视频数据处理平台，不是医院业务系统。它以 `CaptureGroup` 归属的一组外部视频为中心，提供受控接收、媒体事实检查、MediaPipe machine evidence、可选人工标签和受控导出。

## 3. 系统责任边界

平台负责：

- 接收外部采集端上传的 manifest 与视频，按上游明确归属建立数据组；
- 维护数据组、`CameraStream`、`ClipAsset`、媒体检查、AI job/Candidate 及其可追溯性；
- 在授权和 provenance 校验下导出当前检测事实；
- 仅在项目需要人工 ground truth 时提供人工质量、标注、复核及标签适用性校验。

平台不负责医院业务、患者、药品业务、摄像头控制、设备管理、采集侧运维、医院工作流，且不得从文件名、上传顺序或时间接近度猜测视频归属。

## 4. CaptureGroup / 数据组定义

`CaptureGroup` 是由上游明确声明为相关的一组视频数据及其接收事实，不是固有的“配药事件工作流容器”。它是数据组身份、成员边界和后续事实的统一归属；`N=1` 与 `N>1` 使用同一模型：

```text
CaptureGroup
└─ CameraStream #1..N
   └─ ClipAsset
```

数据组必须保留项目隔离、稳定 ID、上游 `capture_group_key`/来源（如有）、声明与实际成员、收件关闭/缺失事实、`ClipAsset` 内容 SHA-256、受控对象引用、`CameraSet`/`CameraStream`/`DeclaredSyncStatus` 等低层接入和来源事实。来源相机标识是外部数据 provenance，不构成设备管理产品。

## 5. 核心对象

| 对象 | 当前职责 |
| --- | --- |
| `CaptureGroup` | 数据组身份、成员边界与接收事实的统一归属 |
| `CameraStream` / `ClipAsset` | 每路视频与不可变媒体字节身份 |
| `MediaProbe` / `MediaReport` | 媒体技术检查事实，不伪装成人工质量 |
| AI job / attempt / `CandidateAnnotation` | MediaPipe 运行及候选检测证据 |
| `QualityReview` / `CaptureGroupQualityReview` | 仅供需要人工标签的视图选择和标签输入准入 |
| `AnnotationTask` / `AnnotationRevision` / `AnnotationReview` | 仅供正式 human ground truth 的任务、不可变修订与可信度复核 |
| `CaptureGroupCleaning` | 仅供人工标签的确定性适用性/排除原因校验，不修改原视频 |

## 6. 当前主链

```text
External Ingest / Upload
→ CaptureGroup
→ CameraStream / ClipAsset
→ Media Probe
→ MediaPipe Candidate
→ Automated / Human Quality
→ Optional Annotation / Review
→ Export
```

Media Probe 与 MediaPipe 是媒体和机器证据准备；人工质量、Annotation、Review 与 Cleaning 不再被定义为每个 `CaptureGroup` 或 `hand-landmarks.v1` 的必经关卡。若项目声明需要人工标签，才可按受控策略使用视图选择、任务、append-only revision、独立 Review 和确定性标签适用性校验。

## 7. MediaPipe machine evidence 边界

MediaPipe 只能产生 `CandidateAnnotation` 与 job/attempt 事实，不能写入或推断人工质量、正式 `AnnotationRevision`、Review 或 Cleaning 结论。`HAND_DETECTED`、`NO_HAND_DETECTED`、`UNKNOWN` 与 `FAILED` 都是逐视图机器/技术证据，不是数据组级业务结论。

每次 evidence 必须关联当前 `CaptureGroup`、`CameraStream`、`ClipAsset` SHA-256、输入摘要、算法/模型/profile、job/attempt、分析范围与结果摘要。迟到、重复或失败的结果必须保持可解释，不得覆盖已被人工决定引用的证据。

## 8. Annotation / Review 的可选定位

仅当项目明确需要人工动作标签或其他 human ground truth 时，才创建或继续处理 `AnnotationTask`。任务仍必须保持每组唯一性、权限、幂等、revision append-only 和可追溯性；Review 只审查具体人工 revision 的可信度，不能评价原视频或 MediaPipe 结果。

人工质量与组级视图选择只用于标签输入，不得成为纯接收、MediaPipe evidence 或检测事实导出的前置条件。历史人工事实继续保留，不因本 DRAFT 被删除、改写或降格。

## 9. Export 定位

`hand-landmarks.v1` 继续是当前公开的 MediaPipe detection evidence export。它只读取当前启用且可用的 `CameraStream`、`ClipAsset` 和当前 Candidate evidence，并在项目授权、21 点结构、媒体身份或 provenance 无法证明时 fail closed。

新增的 `human-annotations.v1` 是可选人工训练标签导出：只输出当前输入、任务已 `COMPLETED` 且 `AnnotationReview` 已 `APPROVED` 的 `annotation-document.v1` segments，并带当前主视图 `ClipAsset` 身份/SHA-256、schema、revision 与 review provenance；不输出 MP4。

两者保持独立：MediaPipe 导出不等待人工链，人工标注导出不把 machine evidence 当作 label，也不恢复旧 manifest 或 `training-data.v2` 产品路径。两种导出都不代表已有训练 consumer、模型训练成功或真实 UAT；未来新增字段必须另行冻结契约、准入与审计。

## 10. 必须保留的可靠性与治理边界

无论 Runtime Simplification 如何推进，以下约束必须保留：项目权限与用途限制、追加式审计、媒体与 AI provenance、内容 SHA-256、幂等键、Outbox、Inbox 去重、job attempt、lease、心跳、有限 retry、迟到结果拒绝、失败原因、受控恢复和 fail-closed 导出校验。Worker 仍不得直接写正式人工标签、Review、Cleaning 或冻结数据集。

## 11. Runtime Simplification

| 分类 | V1.29 DRAFT 定位 | 处理规则 |
| --- | --- | --- |
| Current Runtime | 外部接收、数据组、媒体检查、MediaPipe Candidate、`hand-landmarks.v1`、现有人工链与其审计事实 | 保持运行和可追溯；DRAFT 不改变其行为 |
| Default Product Path | 接收、归组、检查、MediaPipe evidence、导出 | 不要求先完成人工链 |
| Optional Human-label Path | 人工质量、视图选择、任务、revision、Review、标签适用性校验 | 仅项目需要 human ground truth 时启用 |
| Historical / Retired | 旧单视频产品路径、旧事件 manifest、`training-data.v2`/已退役的旧导出路径、CaptureSync runtime、DatasetVersion 产品路径 | 仅迁移和审计参考，不恢复兼容性承诺 |
| Audit Before Change | 自动派单、阶段推导、旧文案/入口、无消费者的 runtime 与历史实体 | 必须先完成后续代码、契约、测试与数据影响审计；不得仅凭本 DRAFT 删除 |

“Historical”描述的是产品承诺，不等于可直接删除数据库迁移、事实记录、契约证据或代码。Current Runtime 与目标默认路径不同：现有人工链在冻结和审计完成前仍是当前实现事实。

## 12. 后续审计要求

任何 runtime 收缩前必须逐项审计调用方、公开 API/OpenAPI、事件 schema、数据库迁移和现存数据、Worker、Web、synthetic 场景、测试、脚本与 runbook；结论必须区分“停止默认创建”“保留历史读取”“可删除”，并证明权限、审计、provenance、幂等、retry、lease、inbox/outbox 不被削弱。不得以文案修改或未运行的检查宣称 runtime 已移除。

## 13. DRAFT → CURRENT 冻结条件

V1.29 只有在以下条件全部满足后才可标记 `CURRENT`：

1. 三项后续审计完成，明确每个保留、收缩或移除项的调用方、数据迁移、契约和回退影响；
2. 新的可选人工标签策略及其权限、审计、幂等和数据保留规则经业务与技术评审批准；
3. 受影响的 OpenAPI、事件 schema、文档、测试、synthetic 验收、runbook 与实际实现完成一致性验证；
4. 确认 `hand-landmarks.v1` 仍独立于人工链并对 provenance 失败 fail closed；
5. 没有以删除历史 migration、事实或审计证据替代真实的兼容性和保留决策。

在此之前，V1.28 仍是上一正式运行时基线；当 V1.29 与 V1.28 描述冲突时，本 DRAFT 是后续变更的需求方向，不表示当前代码已改变。

## 14. 后续阶段建议

1. Runtime 断舍离审计：确认哪些自动派单、工作流推导和旧入口可停止默认使用，哪些只能保留历史读取。
2. CaptureGroup / 人工流程审计：将数据组事实与按项目启用的 human-label 流程逐项拆分，冻结最小命令和守卫。
3. Ingest / AI 主链审计：核对接收、绑定、Media Probe、MediaPipe 调度、Candidate provenance 与 `hand-landmarks.v1` 的端到端可靠性。

## 15. NON-GOALS

- 不建设医院业务、患者、药品、摄像头控制、设备管理、采集侧运维或医院工作流；
- 不新增自动质量结论、自动标签、自动 Review、自动 Cleaning 或训练成功声明；
- 不恢复旧事件 manifest、`training-data.v2`、独立单视频任务/清洗、DatasetVersion 或 CaptureSync runtime；
- 不新增通用工作流引擎、持久化 `next_action` / `blockers`、新的 Worker、队列或数据库事实；
- 不删除历史媒体、人工事实、迁移、审计、provenance 或 runtime，除非后续专项审计和批准明确授权。
