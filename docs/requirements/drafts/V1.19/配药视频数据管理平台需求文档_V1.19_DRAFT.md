## 1. 版本定位

V1.19 的唯一核心目标是：

> 建立固定多相机 Capture 的公共时间轴和同步逐帧数据基础，使多路原始视频能够稳定转换为可复现、可追溯的结构化数据，并为后续正式训练数据构建提供统一输入。

V1.18 已建立的主线继续有效：

```text
Video
→ MediaPipe CandidateAnnotation
→ 人工 AnnotationRevision
→ Review
→ Cleaning
→ 可用数据候选
```

V1.19 在此基础上增加：

```text
Capture (= CaptureSession)
→ Camera 1 … Camera N
→ 公共 Capture 时间轴
→ Sync Frame
→ 每路 Camera 的 Per-view Frame Slot
→ AI Candidate / 人工 Annotation
→ 版本化 Canonical Structured Artifact
→ 正式训练数据候选
```

V1.19 不重新实现或替代 V1.18 的视频接收、单视频手部预标注、人工标注、复核、清洗和数据集治理能力。

## 2. 范围与优先级

### 2.1 V1.19 核心 P0

核心 P0 只闭合以下数据生产链，不以复杂多机位播放器或 DatasetVersion 深度集成为完成前提：

```text
Capture
→ 公共时间轴
→ Per-view Frame Slot
→ 不可变 Sync Revision
→ Canonical Parquet
→ Artifact Provenance
```

| 能力 | 核心 P0 完成范围 |
| --- | --- |
| Capture 身份 | 复用现有 `CaptureSession`、`CameraSetSnapshot`、`CameraStream` 和 `clip_asset_id` |
| 固定相机矩阵 | 动态 N 路；稳定展示编号；显式表达缺路，不因缺失重编号 |
| 公共时间轴 | 以版本化同步规则从可靠媒体时间或获批准的上游时基生成离散同步位置 |
| Per-view Frame Slot | 对每个同步位置和预期相机表达 `PRESENT`、`MISSING` 或 `INVALID` |
| 同步质量 | 保存不可变同步修订、算法/参数摘要、误差、计数、耗时和失败原因 |
| AI 状态 | 区分源帧、同步位置和 AI inference sample；区分 `NOT_RUN` 与 `NO_DETECTION` |
| Canonical Artifact | 生成版本化、带摘要的 Parquet 结构化工件；相同冻结输入可复现 |
| Artifact Provenance | 从结构化行追溯到 Capture、Camera、源视频、源帧、同步修订和所含 AI/人工引用 |
| 验收 | 使用合成 Golden Capture 覆盖缺路、缺帧、异 FPS、未推理和原视频不可变 |

### 2.2 P0 后半段与 P1

| 能力 | 阶段 | 启用条件 |
| --- | --- | --- |
| Capture 同步摘要与最小查询 | P0 后半段 | 核心 P0 的 revision、摘要和 artifact 已经闭合 |
| 简单多机位同步查看 | P1 | 浏览器解码、seek、UI 对齐误差和可访问性验收有测量证据 |
| DatasetVersion 深度集成 | P1 | Canonical Artifact 与 provenance 稳定，既有 DatasetVersion 回归和准入规则完成评审 |

P1 只在核心 P0 完成后启用，不得为了同步开发同时改造后端、Worker、Parquet、DatasetVersion 和完整多路播放器。

### 2.3 V1.19 以后

相机标定、跨相机时间精校、跨视角手部关联、多视角几何、三维重建、新模型训练和自动训练流水线均不属于 V1.19。它们不得反向扩大本版本的模型、数据或 UI 范围。

## 3. 术语与唯一身份

| 产品术语 | 现有正式事实 | V1.19 规则 |
| --- | --- | --- |
| `Capture` / `capture_id` | `CaptureSession` / `capture_session_id` | 产品别名；不得新建第二个 Capture ID |
| `Video` / `video_id` | `ClipAsset` / `clip_asset_id` | 产品别名；不得新建第二个视频 UUID |
| Camera | `CameraChannel` 与冻结的 `CameraSetSnapshotMember` | 相机身份和布局以平台冻结配置为准 |
| `camera_number` | `camera_index + 1` | 面向用户的 1 基展示号；不得覆盖内部 0 基索引 |
| Camera Stream | `CameraStream` | 一次 Capture 中一个预期机位与一个视频资产的绑定 |
| Sync Frame | 公共时间轴上的离散位置 | 由 `capture_id + sync_revision_id + sync_frame_index` 唯一定位 |
| Per-view Frame Slot | 某 Sync Frame 下某个预期 Camera 的槽位 | 由 `capture_id + sync_revision_id + sync_frame_index + camera_number` 唯一定位 |
| Canonical Structured Artifact | 新增的版本化 Parquet 工件 | 是同步结构化证据；本身不等于正式训练标签 |

外部上传已有的 `capture_group_key`、`external_capture_session_id`、上游 manifest，以及平台已有的 `CaptureSession`、`CameraSetSnapshot`、`CameraStream` 均继续复用。Capture 身份必须来自上游显式身份或平台已经冻结的正式归组事实。

禁止通过文件名相似、上传顺序、文件排序、视频长度、相机编号、总帧数或采集时间接近推断 Capture 归属。

## 4. 用户与权限

- 持有项目 `ACTIVE` Membership 的 `MEMBER` 和 `ADMIN` 可以读取其项目内 Capture、同步摘要和获准返回的 Frame Slot；跨项目资源按既有安全策略拒绝或隐藏。
- 只有项目 `ADMIN` 可以显式发起同步、选择获批准的同步 profile、重试失败作业或请求生成 Canonical Artifact。
- 数据集冻结、导出和短期下载继续使用既有管理员审批和治理门禁；同步成功不得自动触发冻结或导出。
- 页面隐藏按钮不能替代 Core API 的 Membership、项目归属、状态、用途和审计守卫。
- 普通用户响应不得暴露对象存储 key、预签名 URL、队列、Worker、Parquet row group 或内部租约信息。

## 5. 固定多相机业务事实

所有视频来自配药舱或操作区域内固定安装的摄像头。产品范围不存在护士佩戴摄像头、Ego Camera、wearable camera 或第一视角采集。

一个 Capture 可以包含动态 N 路固定相机，N 不得写死。预期相机来自冻结的相机配置或版本化上游 manifest。例如：

```text
Expected cameras: [1, 2, 3, 4, 5]
Actual cameras:   [1, 3, 5]

Camera 1 = PRESENT
Camera 2 = MISSING
Camera 3 = PRESENT
Camera 4 = MISSING
Camera 5 = PRESENT
```

不得把实际视频重新编号为 1、2、3。相机缺失、视频已绑定但未入库、媒体损坏和局部缺帧是不同事实，必须分别表达。

## 6. 公共 Capture 时间轴

同属一个 Capture 不代表多路视频已经逐帧同步。开始时间接近、时长相同、FPS 相同、总帧数相同或同时上传均不能单独证明同步。

公共时间轴至少包含：

```text
capture_id
sync_revision_id
sync_frame_index
capture_timestamp_ns
time_basis_source
```

- `sync_frame_index` 是一次不可变同步修订中的 0 基连续离散位置；新同步修订可以产生不同映射，但不得原地改写旧修订。
- `capture_timestamp_ns` 使用整数纳秒作为交换和工件单位；该字段的单位不代表采集精度。系统必须同时保存时基来源、换算规则和可证明的精度或不确定度，不得伪造高精度公共时钟。
- 上游具有可靠公共时钟时，应保存其来源和 Capture 时间原点；只有稳定相对时基时，允许时间原点没有可信 UTC，但换算规则必须版本化。
- 服务器接收时间不得代替媒体 PTS 或 Capture 同步时间。

G0 已冻结时间换算规则的形状，但没有冻结具体 timeline rate：

```text
capture_timestamp_ns(i) =
    origin_ns
    + ROUND_HALF_EVEN(i × timeline_step_numerator_ns / timeline_step_denominator)
```

- revision/profile 必须保存精确的有理数 rate 或 step 分子、分母；只有时间步能够被整数纳秒精确表达时，才可只保存单个 `timeline_interval_ns`；
- 每个位置从 `origin + exact rational offset` 独立换算，禁止重复累加已舍入的整数 interval；G0 中 30 Hz 重复累加会随时长产生确定性漂移；
- `ROUND_HALF_EVEN` 同样用于 `(raw_pts - pts_origin) × time_base` 和获批准的 offset/drift/anchor 有理数换算；原始 `raw_pts`、`time_base_num/den`、`pts_origin` 和同 PTS ordinal 必须进入冻结输入/工件 manifest；
- `timeline_rate` 的具体值仍为 `PENDING`。G0 比较了 10、25、30 Hz，但没有训练用途或标注边界证据支持把任一候选提升为生产常量。

## 7. Per-view Frame Slot

一个 Sync Frame 对每个预期 Camera 恰好有一个 Frame Slot。逻辑键为：

```text
capture_id
+ sync_revision_id
+ sync_frame_index
+ camera_number
```

每个槽位至少表达：

```text
camera_number
camera_stream_id
video_id
source_frame_index
source_pts_ns
frame_state
sync_error_ns
```

`source_frame_index` 只作源视频内的辅助定位；正式时间映射以经过探测的 PTS 或等价可靠媒体时间为准。不得使用 `frame_index / nominal_fps` 作为默认正式时间。

nearest mapping 在误差相同时固定选择较早的 `source_pts_ns`，再按较小的
`source_frame_index`、较小的 `source_pts_ordinal` 消歧。允许误差边界采用包含关系：
`abs(sync_error_ns) <= allowed_tolerance_ns` 才可为 `PRESENT`；具体 tolerance 值仍为
`PENDING`。

每路 stream 的相对 `source_pts_ns` 不天然等于 Capture 时间。同步前必须具有可信的公共 clock，
或冻结以下 stream → Capture 映射：

```text
scale = 1 + drift_ppm / 1_000_000
mapped_capture_time(source_frame) =
    anchor_capture_ns
    + ROUND_HALF_EVEN((source_pts_ns - anchor_source_ns) × scale)
```

只有一个可靠锚点时仅使用 offset，`drift_ppm = null`；至少两个可靠锚点才可提供 drift。
Frame 选择先把 Capture target 反向映射到 source time，再按 PTS 找最近帧，最后把选中帧正向
映回 Capture time。`sync_error_ns` 冻结定义为：

```text
mapped_capture_time(source_frame) - target_capture_timestamp_ns
```

不得用 `source_pts_ns - capture_timestamp_ns` 替代。没有可信 common clock/anchor 映射时，
Capture 不具备同步条件；禁止把各 stream 的首帧默认视为同时发生。

### 7.1 Frame State

| 状态 | 含义 | 必须满足 |
| --- | --- | --- |
| `PRESENT` | 允许误差内存在可解码、可定位的源帧 | 源视频、源帧、PTS 和误差均可追溯 |
| `MISSING` | 预期相机缺路，或该同步位置没有符合允许误差的源帧 | 不得静默用前后帧填补，不得压缩时间轴 |
| `INVALID` | 存在候选媒体数据，但帧损坏、时间戳非法或解码校验失败 | 保存稳定原因码，不得与 `MISSING` 混用 |

缺路时，该 Camera 在该同步修订的所有 Sync Frame 上仍保留 `MISSING` 槽位。局部缺帧也不得删除槽位、改变 `camera_number` 或压缩 `sync_frame_index`。

## 8. 同步规则、状态与摘要

V1.19 第一阶段只做时间对齐，不做视觉内容对齐。同步依据按优先级使用：

1. 可验证的上游公共硬件时间或统一 Capture clock；
2. 版本化且来源明确的 offset/drift/anchor 映射；
3. 经媒体探测证明稳定的 PTS 时间基准；
4. 获批准并记录误差的 nearest-frame mapping。

若最近源帧映回 Capture 时间后的误差超过同步 profile 允许误差，该槽位必须为 `MISSING`，不得为了填满矩阵强行配帧。任何 nearest-frame mapping 必须记录 `sync_error_ns`、方法、算法版本和 profile 摘要。G0 A.1 已批准参数化规则形状：精确有理数 timeline、可信 stream → Capture 映射、Capture 域误差、确定性 tie-breaker 和 tolerance 包含边界。`timeline_rate`、实际 reference 来源以及 warning/allowed/reject tolerance 的生产值没有获准，不能据此发布生产同步 profile v1。

Capture 同步投影为：

```text
NOT_SYNCHRONIZED
SYNCHRONIZING
SYNCHRONIZED
FAILED
```

只有已接受的不可变同步修订具备明确算法/版本、时基、允许误差、输入摘要、工件摘要和质量摘要时，才能显示 `SYNCHRONIZED`。脚本执行结束不等于同步成功。

每次同步至少保存：

```text
camera_count_expected
camera_count_received
sync_frame_count
present_frame_count
missing_frame_count
invalid_frame_count
per_camera_present_count
per_camera_missing_count
max_sync_error_ns
p95_sync_error_ns
sync_algorithm
sync_version
sync_profile_sha256
processing_duration_ms
```

没有可靠数据的统计必须为空或 `PENDING`，不得虚构为 0。

## 9. AI inference 与手部状态

以下三种对象必须分开：

```text
源视频 Frame
同步 Frame Slot
AI Inference Sample
```

V1.18 MediaPipe Hand Landmarker 保持单视频、`VIDEO` mode、10 FPS、最多 2 hands、每手 21 landmarks。V1.19 不要求对每个原始视频帧执行 AI。

每个 Frame Slot 的手部检测投影为：

| 状态 | 含义 |
| --- | --- |
| `HANDS_DETECTED` | AI 成功运行且产生至少一个有效 Candidate |
| `NO_DETECTION` | AI 成功运行，但没有有效手部 Candidate |
| `FAILED` | 该 inference 未得到可信结果 |
| `NOT_RUN` | 该源帧没有运行 AI inference |

`NOT_RUN` 绝不等于 `NO_DETECTION`。未推理的帧不得伪造 Candidate、模型摘要或无手结论。Frame Slot 为 `MISSING` 或 `INVALID` 时，手部状态只能为 `NOT_RUN`，除非后续版本为失败前已执行的独立证据定义新契约。

## 10. Candidate、人工标注与可用训练数据

V1.19 不改变 V1.18 的事实边界：

```text
AI → CandidateAnnotation
Human → AnnotationRevision
```

AI Candidate 只能辅助人工标注，不得自动创建或推进 `AnnotationRevision`、Submit、Review Approved、Cleaning PASS、usable 或 training ground truth。

只有满足以下条件的数据才能成为正式训练数据候选：

```text
正式 AnnotationRevision
+ Review APPROVED
+ Cleaning PASS
```

没有 Candidate 的视频仍可经人工标注进入正式流程。

`AnnotationRevision.sync_revision_id` 是可空的条件引用，而不是所有标注的强制字段：

- 既有 V1.18 单视频标注和以后仍在单视频时间轴创建的标注保持为空，不需要知道 CaptureSyncRevision；
- 只有在同步多机位视图中创建、编辑或投影的标注，才记录实际使用的 `sync_revision_id`；
- 同步修订变化不得原地改写既有 AnnotationRevision；需要基于新同步映射修正标注时创建新 AnnotationRevision，并保留旧 revision；
- DatasetVersion 使用同步结构化数据时，必须同时冻结实际采用的 `sync_revision_id` 和 `annotation_revision_id`，不能依赖当前指针推断。

## 11. Per-view 边界与三维非目标

V1.19 只表达“同一 Capture、同一同步时间点、不同 Camera View”，不做跨相机手部或人员身份关联。

不得持久化或推断：

```text
global_hand_id
cross_camera_hand_id
person_id
cross-camera ReID
```

V1.19 不执行多相机三角测量、3D Hand Pose、真实空间坐标恢复或 cross-view fusion。MediaPipe landmark 的 `z` 仍是模型定义的 normalized/relative z，不得宣称为毫米、厘米、真实深度或真实世界 Z。

## 12. 数据存储分层

| 层 | 责任 | 禁止事项 |
| --- | --- | --- |
| 原始 MP4 | 不可变原始视频证据，保留 SHA-256 与对象血缘 | AI、Overlay、同步、标注、清洗或数据集流程不得覆盖原文件 |
| Manifest | Capture、来源系统/设备、预期相机、文件大小/摘要和上游身份事实 | 不承载 dense frame-level AI 或同步行 |
| PostgreSQL | 业务真值、作业/Attempt、不可变同步修订、摘要、索引、人工标注、复核、清洗、数据集/工件元数据、审计 | 不默认成为无限增长的 dense frame warehouse |
| S3-compatible storage + Parquet | 版本化的同步逐帧与训练数据结构化工件 | 不承载关系型业务状态，不静默覆盖既有版本 |

V1.19 正式区分 Transactional Data 与 Dense Analytical Data。任何进入 PostgreSQL 的逐帧数据都必须经过容量和查询证据证明，不能因为实现方便默认全量入库。

## 13. Canonical Structured Artifact

V1.19 的 Canonical logical row v1 冻结为“一行 = 一个 Camera 在一个 Sync Frame 的 Frame Slot”，可执行逻辑契约为 [`synchronized-frame-v1.schema.json`](../../../../contracts/schemas/synchronized-frame-v1.schema.json)。主键语义和稳定排序均为：

```text
capture_id
+ sync_revision_id
+ sync_frame_index
+ camera_number
```

逻辑行冻结包含：

```text
schema_version
capture_id
capture_group_key
sync_revision_id
sync_frame_index
capture_timestamp_ns
camera_number
camera_stream_id
video_id
source_frame_index
source_pts_ns
source_pts_ordinal
frame_state
frame_reason_code
sync_error_ns
hand_detection_state
ai_job_id
candidate_count
candidate_artifact_ref
annotation_revision_id
model_sha256
profile_sha256
artifact_created_at
```

逻辑契约已冻结字段存在性、可空规则、状态组合、稳定排序以及
`capture_id = capture_session_id`、`video_id = clip_asset_id`、
`camera_number = camera_index + 1`。G0 的 Arrow/Parquet 物理类型只完成 Python 侧候选验证；
分区、压缩、dictionary、row group、writer/runtime 和跨语言兼容仍为 `PENDING`，不得把本机
小样本中体积最小的组合直接提升为生产布局。主 Frame Slot 表不得为了“包含所有东西”把所有
`21 × N` landmarks 无界展开；dense Candidate 使用受版本控制的嵌套列或独立工件 Schema。

artifact manifest 至少冻结 `input_manifest_sha256`、同步 profile 摘要、逻辑摘要、writer/runtime、
每路原 MP4 SHA-256、时基、`raw_pts`、`pts_origin`、同 PTS ordinal，以及获采用的
`anchor_source_ns/anchor_capture_ns/drift_ppm/method/source/anchor_count`；文件名和上传顺序不进入
Camera/Video 身份推断。映射字段属于冻结输入 provenance，任一变化必须改变 input manifest
摘要并创建新 revision。

Canonical Structured Artifact 只证明结构和血缘。没有正式人工标签、复核通过和清洗通过时，它不得被标为可用训练标签。

## 14. Provenance 与版本化

任一结构化行必须能够追溯：

```text
Structured Row
→ CaptureSession
→ CameraSetSnapshotMember / CameraStream
→ ClipAsset
→ Source Frame / PTS
→ Original MP4 SHA-256
→ Capture Sync Revision
```

包含 AI 时继续追溯：

```text
→ AIJob / Attempt
→ Model SHA-256
→ Profile SHA-256
→ Sampling Rule
```

包含人工标签时继续追溯：

```text
→ AnnotationTask
→ AnnotationRevision
→ Review
→ CleaningRun / CleaningResult
→ Label Schema Version / Digest
```

P1 版本化 Canonical Dataset Artifact 必须冻结数据集/Schema 版本、Capture 集合、源视频摘要、同步算法/修订、模型/profile 血缘、人工 revision、复核/清洗证据、工件 SHA-256 和创建时间。相同版本不得静默覆盖；任一冻结输入变化必须创建新版本。该 DatasetVersion 深度集成不阻塞核心 P0 的 Artifact Provenance。

## 15. API 与 P1 Web 产品要求

V1.19 优先提供 Capture、同步摘要、时间轴和 Frame Slot 的项目内读取能力。产品概念对应以下能力，最终路径由技术设计基于现有 `/capture-sessions` API 冻结：

```text
List Captures
Get Capture
Start/Get Capture Synchronization
Get Capture Timeline
Get Capture Frame Slots
```

Frame Slot 查询必须有服务端有界分页和稳定排序，不允许浏览器拉取完整 Parquet 后再筛选。大规模工件生成、下载和排障信息仅向获授权管理员或数据工程流程开放。

P1 Web 保持“视频管理 → 配药动作标注 → 复核 → 清洗”的主线，并在现有 Session 辅助视图上增加简单同步信息：

- 一次配药采集及预期相机矩阵；
- Camera 1…N 的 present/missing/invalid 状态；
- 当前同步状态、修订和质量摘要；
- 统一 playhead 下的多机位查看；
- 无对应帧时明确显示 gap，不静默复用前后帧；
- 技术 ID、PTS、模型摘要和 Parquet 细节默认折叠。

普通用户不需要理解 `sync_frame_index`、row group、对象 key、队列或 Worker internals。

## 16. 非功能、安全与容量要求

- 原始 MP4 在同步、AI、Parquet、标注、清洗和数据集流程前后 SHA-256 必须一致。
- 开发、测试和 CI 只使用合成数据；授权样本必须隔离，禁止真实患者视频、生产账号、生产密钥和生产数据库进入开发环境。
- 同步与工件生成是耗时跨进程工作，必须具备幂等创建、Attempt、租约、至少一次投递吸收、受控重试、结果摘要校验和审计。
- Worker 不得直接写业务数据库；正式同步修订和工件注册只能由 Core API 的拥有模块提交。
- 所有对象引用、下载能力和短期授权遵循现有隐私、安全、保留和审计规则。
- 容量评审至少输入 sessions/day、相机数、时长、源 FPS、同步时间轴频率、Frame Slot 密度、候选密度、保留期、查询窗口、Parquet 大小和 Worker realtime factor。
- API 性能目标、同步误差阈值、timeline rate、Parquet row group 和保留期没有测量证据时保持 `PENDING`，不得伪装成批准常量。

## 18. 实施顺序

严格按以下顺序交付，每一阶段必须可运行、可测试、可回退后再进入下一阶段：

1. **G0 — Golden Capture 设计验证**：先用合成 Capture 测量时间轴频率、reference、tolerance、舍入、Parquet 物理布局和 Worker 容量；该验证不创建生产表或正式 API。
2. **S1 — 领域与 Contract 冻结**：冻结 Capture、Camera、Timeline、Sync Frame、Per-view Frame、缺路/缺帧语义，以及经 G0 验证的参数化 SyncProfile 形状和 Canonical logical Schema。具体生产参数由版本化 profile 批准，不硬编码。
3. **S2 — 同步索引**：从已有 `CaptureSession + CameraStream + MP4` 生成版本化同步映射。
4. **S3 — Canonical Parquet**：生成版本化、可校验的 Canonical Structured Artifact。
5. **S4 — Provenance**：关联 `MP4 → Frame → Sync Revision` 及工件包含的 Candidate/Annotation 引用。
6. **S5 — P0 后半段最小同步查询**：Core API 有界读取 `Capture → Timeline → Camera Frame Slots`，用于验收、排障和后续消费者。
7. **S6 — P1 Web**：核心 P0 完成后，在现有 Session 辅助视图提供简单多相机同步时间轴查看。
8. **S7 — P1 DatasetVersion**：核心 P0 完成后，既有 DatasetVersion 同时冻结实际采用的 sync revision 与 annotation revision；只有 `Review APPROVED + Cleaning PASS` 数据可进入正式训练数据候选。

不得并行铺开多个未闭环阶段，也不得用 V1.19 文档阻塞 V1.18 最终收口。

## 19. 明确不做

V1.19 不包含：

- 新模型训练或自动训练 pipeline；
- 自动动作识别模型；
- 显式批量/自动手部预标注策略的范围扩张；
- 相机内外参管理、畸变标定或 RGB-D；
- 多相机三角测量、3D Hand Pose 或真实空间坐标；
- global hand identity、person tracking 或 cross-camera ReID；
- 视频生成、增强或修改原始 MP4；
- AI Candidate 自动成为 ground truth；
- 自动 Review、自动 Cleaning PASS、自动数据集冻结或自动导出。

## 20. 最低验收场景

1. **完整多相机**：3 路固定 Camera 生成稳定公共时间轴和完整 Frame Slot 矩阵。
2. **缺 Camera**：Expected `[1,2,3,4,5]`、Actual `[1,3,5]`；2、4 始终为缺路且其他机位不重编号。
3. **局部缺帧**：Camera 3 在某同步位置为 `MISSING`；其他 Camera 和 `sync_frame_index` 不受影响。
4. **无效帧**：存在媒体位置但解码或 PTS 校验失败时为 `INVALID`，不伪装成 `MISSING`。
5. **不同 FPS/VFR**：例如 30 FPS 与 25 FPS，按 PTS 与允许误差生成时间轴，不按数组 index 对齐。
6. **跨相机 offset/drift**：通过可信 anchor 把目标 Capture 时间反向映射到 source time，选帧后正向映射计算 Capture 域误差；无可信映射时拒绝同步。
7. **AI 仅运行 10 FPS**：未运行 AI 的 Frame Slot 为 `NOT_RUN`，不显示 `NO_DETECTION`。
8. **人工正式标签**：Candidate 不会自动创建或推进正式 label、Review、Cleaning 或 usable。
9. **Canonical Artifact**：相同冻结输入和 profile 生成相同逻辑行、Schema、排序与内容摘要；输入变化生成新版本。
10. **原视频不可变**：流程前后所有原始 MP4 SHA-256 一致。
11. **项目隔离**：项目成员只能读取本项目 Capture、同步修订和 Frame Slot，跨项目请求不泄露资源存在性。
12. **失败恢复**：同一业务作业重试使用同一个 job 和新 Attempt；迟到/重复结果不覆盖已接受修订。
13. **Artifact Provenance**：任一结构化行可追溯至原视频、源帧和同步修订；包含 AI 或人工引用时可继续追溯相应事实。
14. **可空标注引用**：既有/新建单视频 AnnotationRevision 无需绑定 sync revision；同步多机位标注记录其实际使用的 revision。

## 21. V1.19 P0 完成定义

V1.19 核心 P0 完成时，系统必须能用合成 Capture 验证：

```text
Capture X
Expected cameras: [1, 2, 3, 4, 5]
Actual cameras:   [1, 3, 5]

统一 Capture timeline
├── Camera 1 → synchronized frame slots
├── Camera 2 → missing frame slots
├── Camera 3 → synchronized frame slots
├── Camera 4 → missing frame slots
└── Camera 5 → synchronized frame slots
```

系统生成版本化 Canonical Parquet；其中 `capture_id + sync_revision_id + sync_frame_index + camera_number` 稳定，缺路和缺帧不会导致重新编号或压缩时间轴。每条结构化行至少可追溯：

```text
Original MP4
→ Capture
→ Camera
→ Source Frame
→ Capture Sync Revision
```

如果该行包含 AI Candidate 或人工标注引用，还必须继续追溯相应 AIJob/Attempt、AnnotationRevision、Review 和 Cleaning 事实。复杂多机位同步播放和 DatasetVersion 深度集成不阻塞核心 P0 完成；它们按 P1 独立验收。

核心 P0 所适用的 OpenAPI、事件/Parquet Schema、兼容性测试、Flyway 测试、模块边界测试、单元/集成/E2E 和安全测试通过后，且核心参数已经由 Golden Capture 验证并获批准，才可判定核心 P0 完成。V1.19 草案是否整体晋升为正式基线，须在评审时明确采用“仅冻结核心 P0、P1 保持后续范围”或“等待 P1 一并冻结”的版本策略。

## 22. 设计冻结前待确认

G0/S1 当前状态如下。只有标为 `FROZEN` 的项目获得了本轮证据；其余值在未获批准前不得固化
进生产代码或宣称达到生产质量。

| 决策 | 状态 | G0/S1 结论 |
| --- | --- | --- |
| timeline 的有理数表示与舍入形状 | `FROZEN` | 精确 rate/step 分数；按 index 独立 `ROUND_HALF_EVEN`，不重复累加舍入 interval |
| 公共时间轴 `timeline_rate_hz` 生产值 | `PENDING` | 10/25/30 Hz 均已测，但训练用途和标注边界未给出，不能选择“最佳值” |
| reference/time mapping rule | `FROZEN` | 每路必须有可信 common clock 或显式 anchor 映射；无可信映射拒绝同步；具体 reference 来源由 profile 选择 |
| reference stream/clock 生产选择 | `PENDING` | 真实边端共同 clock、指定 reference 缺路和降级均无证据 |
| nearest tie-break 与 tolerance 边界 | `FROZEN` | 同误差选 earlier PTS → frame index → PTS ordinal；`<=` 为允许边界 |
| 参数化 tolerance rule | `FROZEN` | 使用映回 Capture 时间后的 `sync_error_ns`；`abs(error) <= allowed_tolerance_ns` |
| warning/reject/allowed tolerance 生产值 | `PENDING` | 10/15/20 ms 只得到合成覆盖率，不等于业务容忍度或真实同步误差 |
| offset/drift/anchor 计算形状 | `FROZEN` | offset-only 和两锚点合成 drift 的正反仿射映射已验证；单锚点 drift 必须为 null |
| offset/drift/anchor 生产来源与最低可信等级 | `PENDING` | 本轮未验证真实边端来源、多锚点拟合残差或测量误差 |
| Canonical logical row v1、状态/空值、排序与 provenance | `FROZEN` | 七个 Golden Case、逻辑摘要、乱序输入和可执行 JSON Schema 验证通过 |
| Canonical Parquet 物理类型/分区/压缩/row group | `PENDING` | Python 小样本已比较，但缺目标规模、Java/跨语言和对象存储证据 |
| Frame Slot 查询窗口、页大小和响应体上限 | `PENDING` | row-group 有界读取可行；API 场景和目标 P95/P99 未测 |
| 工件、临时输出和失败输出保留期 | `PENDING` | 本轮未测治理和容量需求 |
| Worker realtime factor、并发、超时、租约和重试 | `PENDING` | 仅本机低分辨率原型链路测量；未包含网络、对象存储、Core API、RabbitMQ 和故障恢复 |
| 多机位 Web 浏览器/硬件解码/UI 对齐误差 | `PENDING` | P1，本轮未执行 |

S1 领域与逻辑 Contract 已 `READY`。生产 `timeline_rate`、reference 来源和 tolerance 数值仍未
冻结，因此正式生产同步 profile v1 继续 `PENDING`；这不再阻塞后续 B/S2 实现参数化 pipeline，
但实现不得硬编码示例值。G0 使用的 `30 Hz + 20 ms` 仅是明确标记为
`G0_MEASUREMENT_ONLY_NOT_APPROVED` 的 `TEST/G0` profile；生产 profile 未获批准时，不开放真实
生产同步。
