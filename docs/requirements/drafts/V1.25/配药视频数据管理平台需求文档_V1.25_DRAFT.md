# 配药视频数据管理平台需求文档 V1.25（多机位 CaptureGroup 工作流草案）

> 文档版本：V1.25-DRAFT.2<br>
> 文档状态：**DRAFT — 仅供评审，不授权编码、数据库迁移、API/契约变更或真实设备接入**<br>
> 起草日期：2026-08-27<br>
> 前一正式基线：[V1.24 配药视频数据管理平台需求基线](../../baselines/V1.24/配药视频数据管理平台需求文档_V1.24.md)（FROZEN）<br>
> 生效规则：本草案只定义下一版本方向；在成为正式基线前，不改变 V1.24、已发布契约、现有代码、数据库、导出字段或运行行为。

## 1. 版本定位与目标

V1.24 仍是当前唯一正式基线，单视频主线保持：

```text
视频接收
→ Media Probe
→ INGESTED
→ 单视频 MediaPipe Candidate
→ 人工 QualityReview
→ QUALIFIED 自动创建并分配唯一 AnnotationTask
→ 人工 AnnotationRevision
→ Review
→ Cleaning
→ training-data.v2 / training_data.parquet
```

V1.25 只定义下一版本的多机位业务模型：一次真实配药事件对应一个
`CaptureGroup`，通常包含约 3–5 路固定机位，但必须支持动态 `N` 路；一机位也是有效的
特殊情况。V1.25 的目标主线是：

```text
一次真实配药事件
→ 一个 CaptureGroup
→ 每路独立接收、Media Probe、MediaPipe
→ 逐视图人工质量判断
→ 持久化的人工组质量结论
→ 一个 CaptureGroup AnnotationTask
→ 一个 CaptureGroup AnnotationRevision
→ 一个主/锚点视图提供正式时间基准
→ Review
→ 事件级 Cleaning
→ 可用训练数据
```

MediaPipe 仍只产生 `CandidateAnnotation`；自动结果不能成为 Ground Truth，不能自动通过
QualityReview、组质量、Review 或 Cleaning。授权、项目隔离、审计、来源追踪和模型/profile/run
provenance 继续是硬约束。

## 2. CaptureGroup 身份与对象

`CaptureGroup` 表示一个真实配药事件，而不是把多路视频当作多个独立事件。
在现有模型足够表达该事件时，`CaptureSession.capture_session_id` 是唯一的组身份，
`CaptureGroup` 只是业务名称；不再创建第二个竞争性的 group ID 或 group 真值。
上游 `capture_group_key`/版本化 manifest 是显式归组证据，必须保留来源和版本，不能由文件名、
上传顺序、服务器接收时间或时间接近度推断归组。

| 业务概念 | V1.25 语义 | 事实来源/所有权 |
| --- | --- | --- |
| `CaptureGroup` | 一次真实配药事件；`capture_group_id` 默认映射 `capture_session_id` | `assetcapture` 的 `CaptureSession` |
| `CaptureGroupView` | 组内一路机位视图的读取投影，不预设新表 | `CameraSetSnapshotMember` + `CameraStream` + `ClipAsset` |
| `camera_number` | 事件内稳定的显示编号；缺号不重排 | 冻结的 CameraSetSnapshot |
| 组质量事实 | 人工提交、追加写入、可审计的 `CaptureGroupQualityReview` | `qualitycleaning`，引用组/视图只读事实 |
| 视图质量 | 复用逐 `ClipAsset` 的 `QualityReview` | 现有 V1.24 质量事实 |
| 组任务/修订 | 一个组任务和一份组修订；主视图只提供时间基准 | `annotationreview`，需新增版本化关系 |
| 候选 | 每路 MediaPipe 的辅助观测 | `aicandidate`，不是动作标签 |

正式实现前必须确认 `CaptureSession` 确实只代表一个真实事件；若某来源无法满足，先冻结
显式映射契约，不以隐式规则补救。

## 3. 最小业务流程

```text
显式 CaptureGroup / CaptureSession
→ 冻结的 CameraSetSnapshot 与预期机位
→ 每路视频接收并形成收件事实
→ 每路 Media Probe
→ INGESTED / 媒体失败
→ 每路 MediaPipe Candidate
→ 自动事实与人工查看提示
→ 逐视图 QualityReview
→ 人工 CaptureGroupQualityReview
→ 一个组 AnnotationTask
→ 选择主/锚点视图作为时间基准
→ 一个组 AnnotationRevision
→ Review
→ 事件级 Cleaning
→ 只输出满足资格的视图/训练行
```

## 4. 功能需求

### 4.1 显式归组与稳定视图身份

- 组成员必须由显式 `capture_group_key` 或版本化 manifest 绑定；缺少显式身份时进入未分组/待人工归属，不能猜测。
- 每路保留 `video_id`、稳定 `camera_number`、可用的 source/camera identity、采集时间及其可信来源、服务器接收时间和媒体状态。
- 预期相机集合来自冻结的 CameraSetSnapshot；预期数量是动态 `N`，不得写死 3、4、5。
- 缺少相机 2 时仍显示相机 2 缺失，不能把相机 3 重编号为 2。
- 同组同机位摘要不同的上传不能静默覆盖；重试沿用现有幂等、摘要和冲突审计事实。

### 4.2 收件完整性与媒体/质量分层

收件状态只回答“预期文件是否已收到并最终确认”，不回答媒体质量或人工质量：

```text
RECEIVING  预期上传集合尚未最终确认
COMPLETE   所有预期相机文件都已收到并最终确认
INCOMPLETE 收件已最终确认，但至少一个预期相机文件缺失
```

组完成必须由版本化 manifest 的完成标记、边端组完成消息或等价的不可变接收事实表达。
任意超时只能产生运维提示，不能单独成为 `INCOMPLETE` 的权威依据。当前
`external-video-ingest-v1` 只有预期相机声明、没有组完成语义时，先补充契约再实现本状态。

如果五路文件都已收到并最终确认，之后 Cam2 Media Probe 失败仍为：

```text
组收件 = COMPLETE
Cam2 媒体状态 = 失败
```

只有实际缺少预期文件时，最终收件才为 `INCOMPLETE`。Media Probe、MediaPipe 和人工质量
结论不得回写收件完整性。现有 V1.24 `CaptureSession.assembly_status` / `quality_status`
仍保持各自的技术投影语义，不等同于本节三态 receipt，也不等同于 V1.25 的人工
`CaptureGroupQualityReview`。

### 4.3 每路独立处理与保守自动证据

每路独立执行：

```text
接收完整性
→ Media Probe
→ INGESTED / 媒体失败
→ MediaPipe Candidate
```

可记录的客观事实包括：可读性、解码、时长、编码/分辨率、处理状态、手部检测/无手、含手帧数、
无手帧数、候选数、landmark 有效性、confidence、模型/profile/run provenance 和稳定原因。

自动层只提供 `facts + human-attention hints`，不建立独立自动质量状态机或可配置规则引擎。
允许提示“媒体不可读”“长时间未检测到手部”“手部覆盖偏低”“候选不可用”“MediaPipe 失败”
或“时间证据不足”，但不能在正式人工动作区间产生前断言“关键配药动作被遮挡”。
`NO_HAND_DETECTED`、候选为零、候选读取失败和 AI 失败都是证据，不是“真实没有手”的证明。
自动层不得写入人工 QualityReview、组质量，不得自动拒绝组、删除数据、创建动作标签或阻断人工入口。

### 4.4 逐视图人工质量

复用现有逐 `ClipAsset` 的 `QualityReview`：

| 结果 | 语义 |
| --- | --- |
| `QUALIFIED` | 人工确认该视图可继续下游 |
| `NEEDS_REVIEW` | 人工暂不能可靠决定，保持阻断 |
| `REJECTED` | 该视图不参与下游，但保留视频、Candidate、组/相机绑定、原因、审核人、时间和审计 |

`REJECTED` 不等于删除；第一版不新增持久化 `EXCLUDED` 状态。只有未来出现“单独视频合格、
但只在某一组排除”的真实用例，才另行设计组范围纳入事实，并标为 SHOULD/DEFER。

### 4.5 持久化的人工组质量

组质量是业务事实，不能只存在于易失的前端计算。第一版增加最小的
`CaptureGroupQualityReview` 持久化事实（具体表/接口在实现前冻结），至少包含：

```text
capture_group_id（默认 capture_session_id）
result
reason
reviewer
revision/version
decided_at
本次决定所依据的视图集合或输入版本摘要
```

组只使用以下 canonical vocabulary：

| 结果 | 语义 |
| --- | --- |
| `QUALIFIED` | 人工确认事件可用，至少一条视图为 `QualityReview.QUALIFIED`，且没有影响目标用途的未解决问题 |
| `QUALIFIED_WITH_EXCLUSIONS` | 人工确认缺失/拒绝一条或多条视图后，剩余视图仍足以支持事件；至少一条视图为 `QUALIFIED` |
| `NEEDS_REVIEW` | 组决定尚未完成，或接收、视图、时间证据仍有疑问 |
| `REJECTED` | 人工确认剩余视觉证据不足或事件不可用 |

没有任何 `QualityReview.QUALIFIED` 视图时，组不得为 `QUALIFIED` 或
`QUALIFIED_WITH_EXCLUSIONS`。第一版由服务端呈现事实、由人作组决定，不硬编码最低相机数或覆盖阈值。

### 4.6 一个组任务、一份组修订

V1.25 多机位路径不得为同一事件创建 Cam1、Cam2、Cam3 等重复动作任务。目标是：

```text
CaptureGroup
→ 一个 AnnotationTask（属于组）
→ 一个或后续追加的 AnnotationRevision（属于组）
```

仅当人工组质量为 `QUALIFIED` 或 `QUALIFIED_WITH_EXCLUSIONS` 时，才按 V1.25 版本化契约
幂等地创建并分配恰好一个组任务；重复事件返回原任务，`NEEDS_REVIEW`、`REJECTED` 和每路
候选结果都不能创建任务。任务创建/分配的权限、事务边界、事件和审计在实现前冻结。

选择一个主/锚点视图只为确定正式时间基准；主视图不是业务事件或标注的拥有者，其他合格视图
是支持证据。正式 action label 和区间始终来自人工 `AnnotationRevision`，Candidate 不得生成或修改它。

当前 V1.24 的 `ClipAsset.QUALIFIED → 一个视频 AnnotationTask` 只对冻结单视频路径继续有效。
若现有数据库/API 不能表达组任务和组修订，实现前最小的增量方向是：在现有任务/修订关系上增加
可选 `capture_group_id`（V1.24 行保持为空）和显式 `primary_view/anchor_view` 引用，并为每组
任务建立唯一约束；具体字段、权限、事件、审计和兼容迁移必须单独版本化。本草案不实施迁移。

### 4.7 Review、Cleaning 与导出方向

- Review 以组任务的正式 `AnnotationRevision` 为对象，带有组身份、主视图、参与的合格视图、拒绝/缺失视图和相关候选证据；Review 仍必须由人通过。
- Cleaning 在配药事件级回答“该组标注是否能用于训练”，检查组质量事实、正式修订、Review、参与视图、媒体完整性和拒绝/缺失原因；Cleaning 仍必须通过。
- 示例：Cam1/Cam3/Cam4 为 `QUALIFIED`、Cam2 为 `REJECTED`，组可为 `QUALIFIED_WITH_EXCLUSIONS`；Review 通过后 Cleaning 可只使用 Cam1/Cam3/Cam4，Cam2 仍保留并可审计。
- 现有 V1.24 `training-data.v2` / `training_data.parquet` 可继续服务单视频历史路径；不得为了容纳多视图而丢失组/视图关系。若需要，未来另行冻结版本化的 `training-data.v3`，至少保留组 ID、修订 ID、主视图、参与视频/相机、逐视图质量、组质量、候选 provenance 和 Cleaning provenance。
- 默认不复制 MP4，不创建 DatasetVersion 或数据集平台。任何未来训练切分都必须把同一 CaptureGroup 的所有视图和派生行放在同一 split。

### 4.8 删除与保留

```text
质量 REJECTED ≠ 软删除 ≠ 物理清除
```

普通质量流程只停止视图下游参与并保留原视频、候选、绑定和审计。物理 purge 仍由独立的管理员/保留策略流程负责，Cleaning 不得静默删除原始媒体。

## 5. 同步与相机身份

同步只表达证据可信度，不承诺帧级精度，使用：

```text
RELIABLE / APPROXIMATE / UNRELIABLE
```

`RELIABLE` 也不自动表示已校准或逐帧对齐。无可靠证据时，以主视图时间轴作为正式标注基准，
其他视图仅作参考；不伪造 offset、不插帧、不自动对齐、不建立 CaptureSync runtime。
`camera_number` 是事件内稳定显示编号，`camera_channel_id` 等来源身份在可用时保留；编号不能因缺路而改变。

## 6. 继承、替代与历史边界

### INHERITED（继承 V1.24）

- CandidateAnnotation 不是 Ground Truth；正式动作标签只来自人工 AnnotationRevision。
- AnnotationRevision 追加写入、不可变、可审计；Review 和 Cleaning 是强制闸门。
- 自动结果不能静默通过 QualityReview、组质量、Review、Cleaning 或导出。
- 项目隔离、权限、来源追踪、模型/profile/run provenance、审计和保留销毁规则继续有效。

### SUPERSEDED FOR V1.25 MULTI-CAMERA（仅替代多机位路径）

- “每个合格 ClipAsset 各有一个动作任务”不再是多机位业务模型；多机位事件只有一个 CaptureGroup 任务。
- “每路视频就是一个真实配药事件”被替代为“一组视图共同表示一个事件”。
- 单视频专属的 Cleaning 归属和导出关系被替代为事件级 Cleaning 与保留组/视图关系。
- 以上替代不回写、不改造、不否定 V1.24 单视频历史行为和证据。

### HISTORICAL / DEFERRED（不约束 V1.25）

V1.22 三维多视角设计、CaptureSync runtime、相机标定平台、三角测量、跨相机 ReID/手部身份跟踪、
3D 手部重建、DatasetVersion/复杂导出平台、通用 AI Evaluation 平台、工作流引擎和微服务扩张
继续保留为历史或延后方向，不得被本草案重新激活。

## 7. V1.25 MVP 边界

### MUST

- 显式 CaptureGroup 身份（默认复用 `capture_session_id`）和动态 `N` 路视图读取；
- RECEIVING / COMPLETE / INCOMPLETE 收件事实及版本化组完成信号；
- 每路独立 Media Probe、MediaPipe 证据和复用的逐视图 QualityReview；
- 可审计的 `CaptureGroupQualityReview` 四态人工事实；
- 一个 CaptureGroup AnnotationTask、一个 CaptureGroup AnnotationRevision 和主视图时间基准；
- 组上下文 Review、事件级 Cleaning，以及组/视图身份的下游追溯和防泄漏 split。

### SHOULD

- 更丰富的多视图对照缩略图和同步证据展示；
- 组范围“合格但仅本组排除”的独立纳入事实；
- 更多可解释自动提示和更强的时间证据。

### DEFER

- 片段级排除/剪切、可配置质量规则引擎、最低相机数策略平台；
- 帧级同步、自动对齐、标定、三角测量、3D、跨相机追踪和 AI 动作识别；
- DatasetVersion、复杂导出/训练平台、批量 Worker/Queue、通用工作流引擎和微服务拆分。

## 8. 冻结前验收与生效规则

正式基线或编码授权前，至少需要合成/明确授权数据证明：显式归组、动态 N 路收件和缺路、组完成与媒体失败分离、每路独立 MediaPipe 证据、逐视图和组级人工审计、单组单任务/单修订、主视图时间基准、Review/Cleaning 闸门、拒绝不删除以及同组 split 不泄漏。

| 版本 | 状态 | 关系 |
| --- | --- | --- |
| V1.24 | **FROZEN** | 当前唯一正式基线；单视频自动任务桥、人工修订、Review、Cleaning 和现有导出保持不变 |
| V1.22 | DRAFT / DEFERRED | 历史三维/同步方向，不被本草案恢复 |
| V1.25 | **DRAFT** | 本文提出的多机位 CaptureGroup、持久组质量、组任务/修订和事件级 Cleaning 方向 |

本文件不加入 `docs/requirements/requirements-manifest.json`，不更新当前需求入口，不修改
V1.24 或历史文件，也不修改任何代码、数据库、OpenAPI、事件 Schema、Worker 或导出契约。
