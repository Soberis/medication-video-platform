# 配药视频数据管理平台需求文档 V1.25（多机位 CaptureGroup 工作流草案）

> 文档版本：V1.25-DRAFT.1<br>
> 文档状态：**DRAFT — 仅供评审，不授权编码、数据库迁移、API/契约变更或真实设备接入**<br>
> 起草日期：2026-08-27<br>
> 前一正式基线：[V1.24 配药视频数据管理平台需求基线](../../baselines/V1.24/配药视频数据管理平台需求文档_V1.24.md)（FROZEN）<br>
> 生效规则：本草案不改变 V1.24、任何已发布契约、现有代码、数据库、导出字段或运行行为；未进入正式基线前不得据此实现新功能。

## 1. 版本定位与冻结边界

V1.24 继续是当前唯一正式基线，主线保持：

```text
视频接收
→ Media Probe
→ INGESTED
→ 单视频 MediaPipe Candidate
→ 人工质量判断
→ 人工 AnnotationRevision
→ Review
→ Cleaning
→ training-data.v2 / training_data.parquet
```

V1.25 只讨论下一版本的多机位数据管理方式：将一次配药事件作为一个明确的
`CaptureGroup`，管理约 3–5 路固定机位视频，并允许在部分机位缺失时保留其余有效视角。
本草案不恢复 V1.22 的三维重建、标定平台或复杂同步产品，也不修改 V1.24 的单视频闭环。

在本草案中，`CaptureGroup` 是面向业务的多机位逻辑聚合名称。实现时应优先复用已有的
显式 `CaptureSession`、`capture_group_key`、`CameraSetSnapshot` 和 `CameraStream` 事实，
不得为了产品命名再创建第二个、相互竞争的分组真值或 ID。

## 2. 核心对象与唯一身份

| 对象 | 定义 | 必须保持的事实 |
| --- | --- | --- |
| `CaptureGroup` | 一次明确声明的配药事件及其多机位视图集合 | 必须有显式来源的分组身份；不是文件名、上传顺序或时间接近度的推断 |
| `CaptureGroupView` | 一个机位在该事件中的一路视频视图（逻辑视图投影，不预设新表或第二套实体） | 包含 `video_id`、稳定 `camera_number`、来源/相机身份（如有）、采集时间元数据和媒体状态 |
| `camera_number` | 面向用户的固定机位编号 | 在同一组内唯一且稳定；缺失机位不能导致其他机位重新编号 |
| `capture_group_key` | 上游稳定事件 ID 或版本化 manifest 中的显式分组键 | 作为归组证据保存来源和版本，不由平台从文件派生 |
| `CaptureSession` | 现有接入侧会话事实 | 继续作为实现锚点；`CaptureGroup` 不替换或另造 Session 真值 |
| `CameraSetSnapshot` | 本次事件预期机位及其冻结配置 | 用于说明预期相机集合；后续配置变化不能回写既有事件 |

同一 `CaptureGroup` 的正常目标为约 3–5 路固定相机，但模型必须支持动态 `N` 路。
生产相机数量、允许的最少有效视角和覆盖要求必须由已批准的 CameraSet/项目规则明确，
不能由浏览器或某次上传结果临时猜测。

## 3. 最小业务流程

```text
显式 CaptureGroup / CaptureSession
→ 预期 CameraSetSnapshot
→ 多路视频接收
→ 每路 Media Probe + MediaPipe Candidate
→ 组级完整性与时间证据
→ 人工逐视图质量决定
→ CaptureGroup 质量结论
→ 一份逻辑动作标注 + 多路支持视图
→ Review
→ Cleaning（验证并过滤已确认排除视图）
→ 仅输出保留视图的可用训练数据
```

所有自动结果都是 `evidence + recommendation`，不是最终人工质量结论。人工决定、
正式 `AnnotationRevision`、Review 和 Cleaning 继续是唯一的业务事实链。

## 4. 功能需求

### 4.1 显式 CaptureGroup 与机位视图

**V25-FR-001 — 一次事件一个明确分组。** 平台必须把一次配药事件表示为一个
`CaptureGroup`，并记录其显式分组来源、项目归属、预期 CameraSet/机位集合以及录制和接收
上下文。一个分组可以包含动态数量的 `CaptureGroupView`，但后来到达的新文件不能隐式并入
其他事件。

**V25-FR-002 — 禁止隐式归组。** 文件名、对象键、上传顺序、服务器接收时间、时长、FPS、
相近拍摄时间、相机编号或内容相似性，均不得单独或组合成为 CaptureGroup 的分组依据。
缺少稳定 `capture_group_key` 或版本化上游 manifest 时，视频必须进入未分组/待人工归属
状态，而不是被平台猜测加入某个 CaptureGroup。

**V25-FR-003 — 视图身份完整。** 每个视图必须保留：

```text
video_id
camera_number
source_identity / camera_identity（如有）
capture timing metadata + its source/trust information
media status
```

平台必须区分采集时间、帧时间和服务器接收时间。缺少可信采集时间不能被展示为已完成
跨机位对齐。

### 4.2 多机位接收、缺路与重复上传

**V25-FR-004 — 动态机位范围。** 系统应以约 3–5 路固定相机作为常见部署，数据模型和
查询不得写死为 3、4 或 5 路；`N` 的实际边界由 CameraSet、容量和验证证据单独批准。

**V25-FR-005 — 缺路不自动否定分组。** 所有预期机位到达时，逐一记录其媒体和检测状态；
某机位缺失、媒体失败或候选缺失时，必须保留该机位的预期身份和原因，不能自动将整个
CaptureGroup 标为 `REJECTED` 或删除其他视图。

**V25-FR-006 — 延迟到达可追溯接入。** 机位晚到时，只要上传明确声明同一
`capture_group_key`/manifest 且服务端仍允许接收，可以加入原 CaptureGroup，并记录迟到事实、
接收时间和组状态变化。不能因为时间接近而把迟到视频加入其他组；已经完成人工决定后，
迟到视图必须通过受控的重新评审/新版本进入，不能静默改变已批准结果。

**V25-FR-007 — 重试幂等且不静默覆盖。** 相同上传重试必须复用现有上传幂等和摘要校验，
不产生重复逻辑视图。相同 CaptureGroup、相同机位但摘要不同的文件不能按文件名或最后到达
顺序自动覆盖；应保留上传尝试和冲突证据，交由人工或受控管理员选择。

### 4.3 自动预检查与证据

**V25-FR-008 — 每路独立检查。** 每个视频独立运行现有能力可覆盖的：

- 媒体完整性、可读取性和完整解码检查；
- 时长、编码、分辨率等基础媒体元数据检查；
- 现有 MediaPipe 手部检测及 Candidate 证据；
- 该视图与 CaptureGroup/CameraSet 的显式绑定检查。

每路结果必须保留检查时间、算法/模型/profile 身份、输入摘要、状态和稳定原因；
`CandidateAnnotation` 仍是辅助结果，不是动作标签或 Ground Truth。

**V25-FR-009 — 组级证据单独记录。** 平台可以汇总预期/已到达/失败/迟到机位数量、
机位覆盖和时间元数据质量，但只能输出证据和建议，例如“可人工确认”“存在缺路”“时间
证据不足”。组级汇总不得把接收时间邻近、MediaPipe `handedness` 或候选数量提升为真实
事件关联或质量通过结论。

**V25-FR-010 — 自动建议不替代人工结论。** 自动检查可以给出 `usable`、`needs review`
或 `exclude` 的建议，但不能仅因 MediaPipe `NO_HAND_DETECTED`、AI `FAILED`、单路缺失或
媒体质量问题自动删除、自动否定整个 CaptureGroup，或阻断人工质量判断。人工决定可以覆盖
自动建议，并必须记录覆盖原因和审计事实。

### 4.4 人工逐视图质量判断

**V25-FR-011 — 视图级人工决定。** 人工审核者必须能够分别把每个机位视图标为：

```text
USABLE       可用于本 CaptureGroup 的人工标注/训练数据
NEEDS_REVIEW 证据不足或存在待确认问题，暂不纳入有效视图
EXCLUDED     本视图不参与该组后续数据，但保留原始事实
```

`EXCLUDED` 必须有稳定原因或说明；`NEEDS_REVIEW` 不能被解释为已可用于训练。

**V25-FR-012 — 人工覆盖可审计。** 视图决定和组级结论必须记录审核者、时间、当前版本、
原因、自动建议和实际决定。自动建议只能预填或提示，不能覆盖人工决定，也不能以颜色或
MediaPipe 状态代替决定文字。

**V25-FR-013 — 保守处理部分可用。** 缺失、遮挡、媒体失败或时间证据不足时，平台优先
保留可解释的 `NEEDS_REVIEW`/`EXCLUDED` 事实，不在第一版引入跨机位复杂的局部片段裁剪、
自动补帧或隐式时间修正。

### 4.5 CaptureGroup 质量结论

**V25-FR-014 — 组级结论复用正式术语。** CaptureGroup 只允许出现以下主要结果：

| 结果 | 含义 |
| --- | --- |
| `QUALIFIED` | 满足已批准的最少有效视角与覆盖规则，且没有需要排除的非必要问题视图 |
| `QUALIFIED_WITH_EXCLUSIONS` | 满足最少有效视角与覆盖规则，同时明确排除了一个或多个缺失/失败/低质量视图 |
| `NEEDS_REVIEW` | 视图决定、组完整性、时间证据或覆盖条件仍有未解决疑问 |
| `REJECTED` | 人工确认没有足够有效视图支持该事件，或事件本身不能用于目标数据 |

`QUALIFIED_WITH_EXCLUSIONS` 是组仍可用的明确结果。比如 Cam1、Cam3、Cam4 为 `USABLE`，
Cam2 为 `EXCLUDED` 时，只要满足事先批准的最低视角/覆盖规则，CaptureGroup 应保持可用，
而不是因缺一路自动失败。

本节的组级 `QUALIFIED` / `QUALIFIED_WITH_EXCLUSIONS` 仅表示未来 `CaptureGroup` 的读取/质量投影，
不等同于 V1.24 单个 `ClipAsset` 的 `QualityReview.QUALIFIED`，也不直接触发逐视频自动
`AnnotationTask`。正式进入组标注前，必须先冻结锚点任务或 group annotation intent 契约。

**V25-FR-015 — 最低视角规则显式化。** “足够有效视图”必须来自 CaptureGroup 使用的
CameraSet/项目规则或事先冻结的研究 profile，至少包含最低有效视图数量和必要覆盖要求。
本草案不为所有医院场景硬编码一个数字；规则尚未批准时不得自动将组标为 `QUALIFIED`。

**V25-FR-016 — 组结论不抹掉视图事实。** 组级 `QUALIFIED`、`NEEDS_REVIEW` 或
`REJECTED` 不能覆盖每个视图的独立媒体、候选、人工决定和排除原因。组被判定不可用时，
其原始视频和排除事实仍按数据生命周期保留。

### 4.6 一次逻辑动作标注，多路支持视图

**V25-FR-017 — 动作只标一次。** 同一 CaptureGroup 的同一配药动作不应要求标注者对每个
摄像头重复创建相同动作标签。目标模型是：

```text
一个 CaptureGroup
→ 一份逻辑动作标注
→ 多个明确的支持 CaptureGroupView
```

**V25-FR-018 — Ground Truth 仍来自人工 revision。** 正式动作标签和动作时间段必须来自
人工 `AnnotationRevision`；Candidate、MediaPipe、机位完整性和自动建议均不能生成、修改、
Review 或 Cleaning 通过正式 Ground Truth。`AnnotationRevision` 仍追加写入、不可变且可审计。

**V25-FR-019 — 视图证据保持视角性。** 每个支持视图可以保留自己的 MediaPipe landmarks、
帧时间、媒体摘要和检测 provenance。多路视图共同支持一个逻辑动作，不意味着它们共享
`handedness`、手部身份或未经验证的跨机位时间映射；无法可靠对应的视图应退出支持集合，
而不是修改人工标签来迁就它。

**V25-FR-020 — 与 V1.24 兼容。** 现有 V1.24 单视频 `AnnotationRevision`、Review、Cleaning
和 `training-data.v2` 不因本草案重写。若未来实现需要将 revision 关联到 CaptureGroup，
必须先提出独立的版本化关系/契约和迁移方案，不能在页面或导出工具中通过复制标签伪造组级事实。

### 4.7 Cleaning 与数据生命周期

**V25-FR-021 — Cleaning 遵循视图排除决定。** Cleaning 根据已确认的人工视图决定和批准规则
过滤/记录 `EXCLUDED` 视图，并让剩余有效视图继续参与组级数据；Cleaning 不把技术失败、
`NO_HAND` 或自动建议直接改写为 `EXCLUDED`。若组级排除命令与原因需要持久化，必须先冻结
版本化契约。清洗过程必须保留原始视频、原始 Candidate、人工决定、原因和清洗版本。

**V25-FR-022 — 排除不是删除。** 普通媒体质量差、遮挡、缺手、缺路和时间证据不足等问题，
默认处理为 `EXCLUDED` 或 `NEEDS_REVIEW`，而不是 `DELETED`。若排除后不再满足最低视角/覆盖
规则，组应失去可用资格并记录原因，但不物理删除任何原始对象。

数据生命周期必须明确区分：

| 生命周期 | 含义 | 是否参与该组训练数据 |
| --- | --- | --- |
| `USABLE` | 经人工/清洗确认可支持该 CaptureGroup | 是，须继续满足组级资格 |
| `EXCLUDED` | 保留事实但不参与该组当前标注/训练输出 | 否 |
| `SOFT_DELETED` | 按既有资产治理流程从普通产品视图隐藏 | 否；不等于物理删除 |
| `PHYSICALLY_PURGED` | 经独立留存、隐私和管理员流程不可逆清除 | 不存在可供输出的对象 |

`EXCLUDED` 与 `SOFT_DELETED` 不是同一状态；物理清除仍是独立的生命周期/管理员治理问题，
不属于正常 Cleaning 动作。

### 4.8 训练数据完整性与泄漏控制

**V25-FR-023 — CaptureGroup 是最小切分单位。** 同一 CaptureGroup 的全部有效视图、
同一事件的动作标注及其派生训练行，必须进入同一个 train/validation/test split。禁止按
`video_id`、camera_number、帧或动作片段随机切分同一组。

**V25-FR-024 — 排除视图不输出。** `EXCLUDED`、未完成 `NEEDS_REVIEW` 和不满足组级资格的
视图不得生成可用训练行；剩余视图如果属于同一 CaptureGroup，仍必须使用该组已经确定的
同一 split。输出和审计证据必须能回查 CaptureGroup、视图、人工 revision、Review 与 Cleaning。

## 5. 非目标与明确 DEFERRED

本草案不授权、不隐含以下能力：

- 3D pose reconstruction；
- 三角测量；
- Camera calibration platform；
- 跨相机 hand identity tracking 或跨事件人员识别；
- 自动生成动作 Ground Truth；
- AI 驱动的自动删除或物理清除；
- 通用 workflow engine、通用状态管理框架或跨领域编排平台；
- DatasetVersion platform、复杂数据集构建或新导出平台；
- 微服务拆分、独立多服务业务编排或为多机位预先扩张运行时。

下一版本只保持以下聚焦范围：

```text
多机位 CaptureGroup 管理
→ 每路自动质量证据
→ 人工逐视图排除
→ 一份逻辑动作标注 + 多视图支持
→ 可审计的视图级 Cleaning
```

## 6. 验收与冻结前置条件

在形成新的正式基线或授权实现前，至少需要合成/明确授权数据上的以下证据：

1. 显式 `capture_group_key`/manifest 归组，证明不依赖文件名、顺序或时间邻近；
2. 3–5 路常见配置和动态 `N` 的全部到达、缺一路、迟到一路、同摘要重试、不同摘要冲突；
3. 每路 Media Probe、MediaPipe 成功/无手/失败与组级完整性、时间证据的分层展示；
4. 自动建议被人工覆盖、视图 `USABLE/NEEDS_REVIEW/EXCLUDED` 和组四种结果的审计记录；
5. Cam2 排除后 Cam1/Cam3/Cam4 仍可用的最低视角/覆盖规则证据；
6. 一次逻辑动作只产生一份人工 Ground Truth，同时保留每路 Candidate 和媒体 provenance；
7. Cleaning 排除坏视图但不物理删除，且排除后资格变化可解释；
8. 同一 CaptureGroup 的所有训练行保持在同一 split，没有跨视图数据泄漏；
9. V1.24 当前单视频主线、契约、导出字段和质量门禁完全回归通过。

未通过证据验证的阈值、时间精度、视角数量和覆盖结论必须保持 `PENDING`，不得写成生产
保证。真实医院数据接入仍需独立的临床、隐私、数据治理和现场验证批准。
