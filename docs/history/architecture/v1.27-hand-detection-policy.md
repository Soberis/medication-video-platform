# V1.27 手部检测政策

> 状态：V1.27 POLICY / CURRENT（手部检测语义）
> 适用范围：`CaptureGroup` 下每个机位视图的 MediaPipe/手部检测证据
> 核心原则：**AI provides evidence. Human makes final decisions.**

本文是 V1.27 正式需求基线和单一 CaptureGroup 产品路径的手部检测政策补充。它定义检测状态、人工决策边界、界面措辞、审计和证据保留要求；不改变 `CaptureGroup`、`QualityReview`、`CaptureGroupQualityReview`、Annotation、Review 或 Cleaning 的所有权和闸门。

参考：[V1.27 需求基线](../../requirements/baselines/V1.27/配药视频数据管理平台需求文档_V1.27.md)、[V1.27 单一 CaptureGroup 产品路径](./v1.27-single-capture-group-workflow.md)、[多机位质量评审历史参考](./multi-camera-quality-review-workflow.md)、[安全、隐私与保留销毁](../../architecture/security-privacy-retention.md)。

## 1. 基本规则

1. 手部检测状态是**逐机位的 AI 证据**。同一 `CaptureGroup` 的机位互相独立，不产生自动的组级“有手/无手”结论。
2. 四个状态都不是人工质量结论、正式动作标签、Review 结论或训练资格结论。`HAND_DETECTED` 也不代表动作可见或视频已合格。
3. `NO_HAND_DETECTED`、`UNKNOWN` 和 `FAILED` 都不得自动删除视频、自动排除机位、自动拒绝 `CaptureGroup` 或阻断人工入口。
4. 系统可以展示证据、提示人工关注和提供服务端已授权的恢复动作；系统不得替代专业判断。
5. 机位排除和事件拒绝必须明确指出作用范围。排除一个机位不等于拒绝整个事件，质量拒绝也不等于删除数据。

## 2. 手部检测状态

| 状态 | 正式语义 | 不代表什么 |
| --- | --- | --- |
| `HAND_DETECTED` | 检测作业在其声明的分析范围内成功完成，并在至少一个已分析帧中发现手部证据。 | 不代表动作完整、视角可用、质量合格或可以直接生成 Ground Truth。 |
| `NO_HAND_DETECTED` | 检测作业在其声明的分析范围内成功完成，但未发现手部证据。 | 不代表现实中没有手；遮挡、取景、采样范围和模型能力都可能造成该结果。 |
| `UNKNOWN` | 当前没有足够完整、可靠的检测证据作出正面或负面判断，例如尚未运行、结果缺失或覆盖范围不足。 | 不得当作 `NO_HAND_DETECTED`，也不得当作视频不可用。 |
| `FAILED` | 已尝试执行检测，但作业因解码、输入、Worker、超时或其他技术原因未成功完成。应保留可重试性和稳定失败原因。 | 不得当作 `NO_HAND_DETECTED`；也不单独证明媒体或事件不可用。 |

`NO_HAND_DETECTED` 只有在分析范围和检测完成事实可证明时才能使用。分析未完成时使用 `UNKNOWN` 或 `FAILED`，具体取决于“证据不足”还是“已知执行失败”。检测状态必须与媒体接收、Media Probe、逐视图人工质量和组质量分层展示。

## 3. 决策规则

### 3.1 单机位事件

单机位事件仍按事件内唯一的 `CameraStream → ClipAsset` 视图处理。出现 `NO_HAND_DETECTED` 时，系统必须把它交给人工确认，不得自动删除或自动判为不可用；V1.27 不新增 `CaptureGroupView` 数据库实体。人工可作出以下决定：

| 人工判断 | 业务含义 | V1.27 当前语义 |
| --- | --- | --- |
| 视频仍足以完成工作 | 继续使用该机位进行标注。 | 逐视图 `QualityReview.QUALIFIED`，随后遵循既有任务、Revision、Review 和 Cleaning 闸门。 |
| 该机位不应参与标注 | 只排除该机位的下游参与，保留视频、检测证据、绑定、理由和审计。 | 逐视图 `QualityReview.REJECTED`；不新增持久化 `EXCLUDED` 状态。 |
| 证据不足或仍需检查 | 暂不作最终判断，保持人工复核。 | `QualityReview.NEEDS_REVIEW` 或既有等价的未决状态。 |

`HAND_DETECTED`、`UNKNOWN` 和 `FAILED` 同样不能跳过人工质量判断。`UNKNOWN`/`FAILED` 可以触发服务端授权的重试或恢复，但恢复成功前不得把它们改写成“未检测到手部”。

若单机位被人工排除，不能因为“剩余机位为零”就自动生成事件拒绝。事件级 `CaptureGroupQualityReview.REJECTED` 仍需要单独的人工确认，且必须满足第 3.3 节。

### 3.2 多机位事件

每个机位独立查看、独立判断、独立记录。一个机位的检测状态不得传播为其他机位的状态，也不得直接传播为组级阻断。

示例：

| 机位 | AI 检测状态 | 人工处理后的结果 |
| --- | --- | --- |
| Camera 1 | `HAND_DETECTED` | 保持可用，继续作为标注或支持视图候选。 |
| Camera 2 | `NO_HAND_DETECTED` | 人工确认后，仅排除 Camera 2；视频和证据继续保留。 |
| Camera 3 | `HAND_DETECTED` | 保持可用，继续作为标注或支持视图候选。 |

预期结果是：**只排除 Camera 2，Camera 1 和 Camera 3 仍可用**。如果剩余视图经人工确认足以进入标注，组可以使用现有 `CaptureGroupQualityReview.QUALIFIED_WITH_EXCLUSIONS`；该组结论仍是人工提交的，不是由检测状态自动生成的。

对于 `UNKNOWN` 或 `FAILED` 的机位，其他机位可以继续处理。该机位应由人工选择等待、恢复、继续查看或排除；不能因为局部状态自动拒绝整组。组质量提交、收件前置条件、权限和审计遵循 V1.27 当前基线及其保留的 CaptureGroup 领域事实。

### 3.3 整个 `CaptureGroup` 拒绝

只有同时满足以下条件，才允许作出事件级拒绝：

1. 所有可评估的机位都已被判断为不能为标注提供足够视觉证据，且没有任何剩余可用机位；“所有机位都是 `NO_HAND_DETECTED`/`UNKNOWN`/`FAILED`”本身不足以满足该条件。
2. 有权限的人工审核人明确确认：该事件无法产生训练数据。
3. 提交时记录事件级理由、受影响的机位集合、所依据的证据版本，并形成追加式审计记录。
4. 仍满足现有 `CaptureGroupQualityReview` 的收件、权限、并发和版本守卫。

满足上述条件后，才可提交 `CaptureGroupQualityReview.REJECTED`。该结论表示事件不能进入人工标注，不表示物理删除；视频、机位绑定、检测候选、理由和审计仍按正常保留/销毁流程处理。

## 4. UI wording 与展示要求

### 4.1 AI 状态标签

界面必须把四态标为 AI 证据，推荐使用以下措辞：

| 状态 | 推荐主标签 | 推荐辅助说明 |
| --- | --- | --- |
| `HAND_DETECTED` | 检测到手部（AI 证据） | 在已分析范围内发现手部证据；仍需人工判断机位质量。 |
| `NO_HAND_DETECTED` | 未检测到手部（AI 证据） | 在已分析范围内未发现手部证据；请人工判断视频是否仍可用于标注。 |
| `UNKNOWN` | 手部状态未知（证据不足） | 当前没有足够可靠的检测证据，不能作出有手或无手结论。 |
| `FAILED` | 手部检测失败（技术状态） | 检测作业未成功完成；请使用服务端提供的恢复动作或人工查看。 |

机位选择器和工作台详情应显示具体机位，例如“Camera 2 · 未检测到手部（AI 证据）”，不得把它简化成“事件无手”。检测状态可以作为低权重辅助证据，但不得伪装成流程阶段、人工质量结论或训练资格结论。

### 4.2 人工操作措辞

对 `NO_HAND_DETECTED`，当前动作区可以使用：

- 主提示：“请人工判断该机位是否仍可用于标注”；
- 继续选项：“继续使用该机位进行标注”；
- 排除选项：“排除该机位，不参与标注（保留视频与证据）”；
- 未决选项：“暂不决定，保留待复核”。

事件级危险确认必须明确写成：“确认事件无法产生训练数据”。只有在用户确实执行事件级人工确认后，才能显示事件拒绝结果。不得使用“AI 判断没有手”“自动排除”“删除无手视频”或“事件无效”等措辞；“无法产生训练数据”只能描述已确认的人工事件结论。

`Current Action` 仍是唯一主操作区。检测结果不得自动提交质量、自动跳过机位、自动聚焦下一项或在没有真实服务端守卫时显示 blocker；`UNKNOWN`/`FAILED` 的重试按钮也必须以实际 capability 为准。

## 5. 审计要求

复用现有 `audit_event` 和 Candidate/job provenance，不建立平行日志。以下事实必须可追溯：

| 场景 | 至少记录 |
| --- | --- |
| 每次检测完成或失败 | `tenant/project`、`capture_group_id`、机位/视图和 `ClipAsset` 身份；四态结果或技术失败状态；AI job/attempt；`algorithm_key`、`algorithm_version`、`model_sha256`、`profile_sha256`；输入版本或 `input_sha256`；分析覆盖/结果摘要；失败原因和是否可重试；系统身份、UTC 时间和 `request_id/trace_id`。 |
| 每次重试或恢复 | 原检测尝试、新尝试、触发原因、操作者或系统身份、结果和幂等/关联信息。旧证据不得被覆盖。 |
| 每次逐视图人工决定 | 操作者、角色和项目授权；目标组/机位/资产；人工选择的结果（继续、排除或保持未决）；排除/未决理由；决定时引用的检测结果、媒体版本和证据摘要；时间、当前版本和请求关联信息。 |
| 每次组级质量决定 | `capture_group_id`、人工组质量结果、明确的受影响机位集合、每路人工质量快照、理由、审核人、时间、输入/View Set 版本及显式确认事实。组拒绝必须能够证明“无剩余可用机位”和“人工确认无法产生训练数据”。 |

AI 记录的 `actor_type` 必须表明这是系统/Worker 事实；人工记录必须表明真实操作者，不能把 AI 结果写成 `reviewer`。审计只追加、不可覆盖或删除；重复回传、迟到结果和并发失败都应保留可解释的处理轨迹。日志和审计不得记录预签名 URL、令牌、原始视频内容或可恢复的敏感对象地址。

## 6. 证据保留要求

1. 无论状态是 `NO_HAND_DETECTED`、`UNKNOWN` 还是 `FAILED`，都保留原始视频、`CameraStream`/`ClipAsset` 绑定和对应 `CaptureGroup` 关系，直到既有保留/销毁流程允许处置。
2. 保留每次检测尝试的不可变结果或稳定摘要：状态、分析范围和覆盖、计数/候选摘要（如有）、输入摘要、模型/profile/run provenance、完成时间、失败原因和重试属性。
3. 人工决定必须引用当时看到的证据版本。检测重跑产生新 attempt/版本，不得静默改写已被人工决定引用的旧证据；后续重新纳入视图必须按现有组质量和修订链规则产生新的事实。独立的 `hand-landmarks.v1` 导出按当前 job/evidence 读取，不把旧 Review/Cleaning 快照当作当前检测结果。
4. 机位被排除或 `CaptureGroup` 被拒绝后，仍保留支持审计和复核所需的媒体引用、候选、绑定、理由和决定链；质量拒绝不等于软删除或物理清除。
5. 不为本政策复制 MP4 或另建临时事实库。复用既有受控对象版本、摘要和授权查看路径；访问必须满足项目权限、用途和隐私状态，原始内容不得写入普通日志。
6. 具体保留期限、legal hold、备份到期和物理销毁继续以安全/隐私基线、医院书面政策和既有销毁审批为准。本政策的最低要求是：在依赖该证据的人工质量、组质量、标注、Review、Cleaning/导出和审计义务完成前，不得因检测为“无手”或失败而提前清除。

## 7. 实现边界与兼容性

- 本文不新增数据库字段、状态机、工作流引擎、队列、Worker 或自动质量规则，也不改变现有人工闸门。
- AI 结果继续只能进入 `CandidateAnnotation`/候选证据；不得写入 `QualityReview`、`CaptureGroupQualityReview`、正式 `AnnotationRevision`、Review 或 Cleaning 结论。
- 现有事件契约继续将 AI job 的 `FAILED` 与 `hand_result` 的 `UNKNOWN`/`HAND_DETECTED`/`NO_HAND_DETECTED` 分开表达。当前 `/hand-landmarks/v1` 只读导出在服务端通过公开的 CaptureGroup view 和 Candidate evidence 查询边界，枚举所有启用且可用的当前视图；它不读取 View/Group Quality、AnnotationRevision、Review、Cleaning 或 v3 eligibility。仅当前 `SUCCEEDED_WITH_CANDIDATES` 产生 CSV 行，其余状态在 preview 计数中体现。
- `training-data.v3` 仍然受人工 Review 和确定性 Cleaning 闸门约束；`hand-landmarks.v1` 的独立 detection evidence export 不改变任何人工质量、正式标注、Review 或 Cleaning 结论。未来若对外暴露新的统一 AI 状态字段，必须另行版本化契约并补充兼容性测试。
- 本政策不定义最低相机数、遮挡阈值、动作可见性阈值或自动拒绝规则。任何新的自动判断都必须先经过独立需求、契约、权限、审计和人工验收。

## 8. 一句话验收标准

**AI 只能告诉系统“这一路检测到了什么或没能检测到什么”；人决定这一路是否可用于人工业务流程，只有在人确认所有机位都不可用且事件无法产生训练数据后，才拒绝整个 `CaptureGroup`。这项人工决定不构成独立 `hand-landmarks.v1` detection evidence export 的前置条件。**
