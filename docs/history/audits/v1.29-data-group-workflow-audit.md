# V1.29 数据组与人工流程简化审计

状态：AUDIT / Phase 1
日期：2026-09-04
范围：仅审计。本文不修改现有 API、数据库、Worker、UI、迁移或历史材料。

## 结论

V1.29 应将 `CaptureGroup` 定义为“一组由上游明确归属的相关视频数据”，而不是“配药事件工作流容器”。当前的 `CaptureGroup → CameraStream → ClipAsset`、媒体事实、MediaPipe provenance、审计、幂等、重试和 lease 都是数据产品的必要基础，应保留。`hand-landmarks.v1` 已经正确地从当前视频和 Candidate evidence 独立导出，不能让人工流程重新成为它的前置条件。

当前人工链的合理边界是**可选的 human ground truth**：仅当项目确实要产出人工动作标签时，才需要质量判断、一个 group-owned task、不可变 revision、人工 Review 和标签适用性的确定性校验。现有实现把这些节点作为所有 CaptureGroup 的默认线性流程，并在 Web 中重复推导“下一步”；这是 V1.29 最主要的收缩点。结论不是删除已有事实，而是停止把它们当成每组视频或 MediaPipe 导出的必经仪式。

本结论以 V1.29 DRAFT 的后续变更方向为准；V1.28 当前代码与文档仍是运行时审计证据。DRAFT 不授权改变现有行为或删除任何 runtime、migration、事实记录、provenance、audit、idempotency、retry 或 lease；以下“收缩/停止新建”均须在后续专项审计和批准后实施。

## 1. CaptureGroup 的最小必须字段

这里的“必须”指数据组身份、边界和可追溯性，不把所有当前 `capture_session` 列都改写成新的产品字段。应继续用现有低层接收事实承载，避免一次重建模型。

| 类别 | 最小字段/事实 | 原因 |
| --- | --- | --- |
| 租户与身份 | `project_id`、稳定的 `capture_group_id`，以及上游提供的 `capture_group_key` + `key_source`（若有） | 项目隔离、幂等归组与外部回查；key 不可由文件名、上传顺序或时间接近度猜测。 |
| 成员边界 | 声明的机位集合/编号、实际收到的 `CameraStream` 成员及其 `ClipAsset` 绑定 | 能回答哪些视频属于同一组，缺少的成员也可被审计，N=1/N>1 使用同一模型。 |
| 收到的媒体身份 | 每个 `ClipAsset` 的内容 SHA-256、大小/类型、可用/软删除状态和受控对象引用 | 保证 MediaProbe、Candidate 与导出仍绑定到同一字节，而非仅绑定文件名。 |
| 上游声明与接收证据 | manifest/schema/source identity、声明 capture time/timezone（如上游提供）、服务器接收时间、明确关闭信号或收件结束事实 | 区分上游声明和平台观察，支持迟到/缺失视频处理，不推断归属。 |
| 保留的低层事实 | frozen `CameraSet`/成员快照、`CameraStream`、`DeclaredSyncStatus` | 这是相机视图身份和同步声明，不等于建设医院/设备管理产品。 |

`device_id`、`camera_set_id`、`metadata_*`、`sync_group_id`、`assembly_status` 等当前 `CaptureSession` 字段不应在本 Phase 删除或篡改：其中有接入/provenance 价值。V1.29 的最小产品读模型只需暴露上述能说明数据组、成员与媒体字节的事实；其余字段按排障、审计或来源契约按需显示。

## 2. 纯旧配药业务语义字段

以下不是视频数据组、MediaPipe detection 或导出本身的必要概念；应从新的默认路径和新文案中退出，历史事实仍保留。

| 旧语义 | 现有载体 | V1.29 处理 |
| --- | --- | --- |
| “配药事件”、`medication-event`、`配药动作`、`primary_step` | Web 路由/文案、`AnnotationLabelSchema`、`annotation-document.v1` segments | 改称数据组/可选人工标签；仅在项目明确选择动作标签 schema 时出现。 |
| Primary View 是动作时间基准 | `AnnotationTask.primary_*`、`AnnotationRevision.primary_*`、Cleaning `primary_interval` | 只在人工动作区间标签存在时保留；不是每个多视频数据组的固有属性。 |
| “所有 received view 均需人工质量 → group quality → 自动派单” | `CaptureGroupQualityReviewService` 与 quality-qualified event listener | 不再作为检测数据组的默认门槛；转为可选标签集准入策略。 |
| Review 后自动进入 event Cleaning | `CaptureGroupAnnotationWorkflow.reviewRevision` | 只服务标签可信度与标签 eligibility，不为 `hand-landmarks.v1` 创造资格。 |
| 训练数据 manifest / event eligibility | V69 的历史视图，已由 V75 删除 | 已非当前产品；不得以 V1.29 名义恢复。 |

“Camera”、“来源设备”和同步声明不在本表：它们是外部采集数据的来源事实。V1.29 不建设医院/设备管理，并不等于丢弃上游给出的来源标识。

## 3. 可由事实推导、不得重复持久化的状态

| 状态/显示 | 权威输入 | 审计结论 |
| --- | --- | --- |
| 数据组成员完整/缺失 | declared member set、实际绑定 `CameraStream`、明确 receipt close | `RECEIVING/COMPLETE/INCOMPLETE` 可以作为不可变收件结论/历史事实保留；列表“已收 X/Y、缺失哪些”应查询推导，不再另建 workflow state。 |
| 媒体是否可用于检测 | `ClipAsset` 可用性、MediaProbe/stream 状态 | 查询投影；不可复制成 group-level “ready”。 |
| 手部检测导出是否可产生行 | 当前 enabled/available view、Candidate execution status、provenance 校验 | 由 `HandLandmarkTrainingExportService` 即时计算；不持久化人工 eligibility。 |
| 当前人工标签可否继续 | 可选 label policy、当前 task/revision/review、当前媒体和质量事实 | 服务端在命令时校验；不创建 `next_action`、`blockers`、通用 stage 或第二状态机。 |
| 页面“下一步” | 上述已读事实和当前调用者权限 | 可作一次性的展示提示，但不是持久化业务事实。当前 Web 的六阶段 `deriveMedicationEventWorkflow` 覆盖 receipt、view quality、group quality、annotation、review、cleaning，已接近重复的 workflow inference。 |

## 4. per-view Quality 是否必要

**有条件必要，且所有 scope 只限人类标签集。** 一路视频可能损坏、错误场景、敏感、遮挡或不可用；若它要作为人工标签的主视图或参与标签语义，单独的人工排除理由是有价值的 truth。当前 `QualityReview` 的 actor、原因、版本、幂等与审计因此不能删。

它不应成为 MediaPipe evidence 或 `hand-landmarks.v1` 的前置条件：当前导出服务已不读取它，AI Worker 也没有依赖它。对于“只接收、检测、导出”的 CaptureGroup，根本不创建 per-view Quality；媒体技术可用性继续来自 MediaProbe/资产事实，而非把技术检查伪装成人工质量。

## 5. CaptureGroup Quality 是否重复人工判断

**当前形式存在重复，应收缩为可选标签集的聚合准入记录。** `CaptureGroupQualityReview` 重新快照每路 Quality，要求所有收到视图已人工 resolved，再生成 `QUALIFIED` 或 `QUALIFIED_WITH_EXCLUSIONS`，并以 quality-qualified event 自动派 task。它的独特价值不是再次判断画面，而是人工确认“本次标签集使用哪些视图、排除哪些视图、允许哪个主视图”。

V1.29 不应把它当成每组视频的独立人工关卡。最小方案是：在首次创建人工标签任务时，提交一次不可变 `labeling_input`/included-excluded view set（可复用当前 `confirmed_view_set` 和 digest）；只有项目声明需要人工标签时才产生。若仍保留 `CaptureGroupQualityReview` 实体以兼容既有事实，停止新增一个与 per-view decision 重复的“事件质量”表单和自动派单语义。

## 6. AnnotationTask 是否只在需要人工动作标签时产生

**是。** 当前监听器在任意 admitting group quality 后自动创建一个 task，这是 V1.29 与“可选 human labels”冲突最直接的地方。`AnnotationTask`、Revision 链、label schema digest、primary view 和 assignee 的完整性机制，对可审计的人工动作标签是必要的；对纯 MediaPipe landmarks export 没有消费者，也不会被 export 读取。

后续实现应将 task 创建改为“显式请求/已配置 label policy 时创建”，而非在数据组接收或 Candidate 完成时自动创建。仍保留 `(project_id, capture_group_id)` 的唯一性、revision append-only、权限、idempotency 和已有 task 的重开事实；不要为此引入通用 workflow engine。

## 7. Review 是否只服务人工标签可信度

**是。** `AnnotationReview` 的 `APPROVED/REJECTED`、独立审核要求、返工 revision 与审计，能说明人工标签是否可信、是否需要修订；这是 ground truth 的真实价值。它不评判原视频、MediaPipe 运行结果或设备，不应成为检测证据导出的条件。当前 `hand-landmarks.v1` 的服务实现和 V1.28 规范已经遵守此边界。

因此，Review 应只在有正式 human label revision 时出现。无人工标签的 CaptureGroup 不应显示“待 Review”或被视作未完成。

## 8. Cleaning 是否可收缩为 eligibility / exclusion reasons / deterministic validation

**可以，且应如此命名和实现。** 当前 `CaptureGroupCleaningService` 已是纯确定性逻辑：验证 approved review、admitting group quality、合格主视图、非空/非重叠 action intervals、参与/排除视图，输出 `PASS/REJECT`、reason codes、executed checks、input fingerprint 与审计；它不改写原媒体。其保留价值是 human-label output 的可复验 eligibility，而不是“清洗视频”。

建议把新产品语义收缩为 `LabelEligibility`（或等义读模型）：

- 输入：一份指定 revision、其 review、included/excluded views 和不可变 source/candidate provenance；
- 输出：`eligible`、机器可读 exclusion/reason codes、确定性 validation checks、fingerprint 和 evaluated-at；
- 范围：仅有人工标签的导出/下游使用；不触发对原视频的删除、修改或“修复”；
- 不适用于：`hand-landmarks.v1`。当前检测导出仍按其自身 provenance fail closed。

保留现有 Cleaning 历史、rule-set digest、input fingerprint、重算的 idempotency 和审计；收缩的是未来语义和入口，不是证据链。

## 9. Event List、Task List、Workbench 是否重复

**列表不重复，表单不能重复。** 数据组列表回答“有哪些视频数据”；任务列表回答“需要我处理哪些人工标签”。二者是不同发现入口，当前 V1.28 要求它们都进入同一个 CaptureGroup 详情页，实际路由也如此。保留两个列表是较小且合理的实现。

重复发生在：数据组列表为每一行额外拉取 task 和 group-quality，再用浏览器猜测当前动作；详情工作台也以同一批事实再推导六阶段流程。V1.29 应：

1. 数据组列表只显示接收、媒体/检测摘要和“是否有可选 human label”；
2. 任务列表只显示已存在的人工标签工作；
3. 两者继续打开同一数据组详情，但详情按事实区块和显式可用命令展示，不再制造第二个工作流或重复提交表单。

## 10. 前端是否承担过多 workflow inference

**是，当前为展示而写的推导已超过必要复杂度。** `medication-event-workflow.ts` 枚举六阶段、权限和读失败分支，`CaptureGroupListView` 又通过并发查询补足 task/quality，目的虽是避免把未知错误报成“没有任务”，但它使浏览器承担了“下一步/阻塞”的主要解释职责。代码注释声明它不是领域状态机，然而用户看到的仍是完整 workflow。

最小收缩方向不是把逻辑搬到新的引擎，而是：服务端继续为每个写命令做权威 guard；前端只显示独立事实与 API 已返回的 `can_*` 能力，操作失败后呈现服务端错误。若保留“建议下一步”，只在详情页用无持久化、best-effort 的单条提示，不在列表和详情分别推导，不把未知读状态解释成业务状态。

## 最小领域链（V1.29 目标）

```text
CaptureGroup
  └─ CameraStream
      └─ ClipAsset

并列事实：
  ├─ Media Facts
  │   └─ 收件、媒体探测、资产完整性/可用性、来源与同步声明
  ├─ AI Evidence
  │   └─ MediaPipe Candidate + job/attempt/model/profile/input/result provenance
  ├─ Optional Human Labels
  │   └─ 仅按项目标签需求创建：included/excluded views、task、append-only revision
  ├─ Optional Review
  │   └─ 仅审查 human-label revision 的可信度，批准或返工
  └─ Export Eligibility
      ├─ hand-landmarks.v1：当前 view + 当前 Candidate provenance，独立于人工链
      └─ human-label 输出（如未来明确需要）：review + deterministic LabelEligibility
```

## 分阶段建议与未决风险

1. 先在 V1.29 基线/契约中冻结“纯数据组、检测导出、可选人工标签”三条边界；不要先删除实体或 migration。
2. 再停止默认自动派发 AnnotationTask，并将 group-quality/cleaning 新入口限定为 human-label policy；同时更新 Web、OpenAPI、synthetic scenarios、contract tests 和 runbook。
3. 最后缩减 UI 的阶段推导和配药文案；保留事实查询、权限、审计和失败可见性。

未决风险：当前公开契约、Web tests、synthetic E2E 和部署 smoke 都假定“admitting group quality → task → Review → Cleaning”的主链，改造必须成组完成，不能只移除一个 API 或页面。V1.29 DRAFT 已将人工链降为可选，但仍明确要求先完成后续审计和批准；在 DRAFT 冻结为 CURRENT 并完成 runtime 一致性变更前，不应把本审计结论当作已生效的运行时行为。
