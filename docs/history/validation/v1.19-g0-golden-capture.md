## 1. 结论

G0 的七个合成场景、逻辑 Frame Slot 矩阵、PTS/anchor 映射、确定性摘要和 Parquet 有界读取均已建立
可重复的自动化证据。本轮足以冻结：

- Capture/Video/Camera 继续复用现有身份；
- Sync Frame 与 Per-view Frame Slot 的逻辑粒度和稳定排序；
- `PRESENT/MISSING/INVALID` 与 `NOT_RUN/NO_DETECTION` 的互斥语义；
- 原始 PTS/time base/origin/ordinal 血缘要求；
- 有理数时间按 index 独立 `ROUND_HALF_EVEN`，禁止累加已舍入 interval；
- nearest 同误差按 earlier PTS → frame index → PTS ordinal 消歧，tolerance 边界为包含关系；
- 每路 stream 到 Capture 时间的可信 anchor/offset/drift 仿射映射、正反映射顺序，以及无可信
  映射时拒绝同步；
- `sync_error_ns = mapped_capture_time(source_frame) - target_capture_timestamp_ns`；
- Canonical logical row v1、逻辑摘要和 artifact SHA 双摘要。

具体 timeline rate、reference 来源、tolerance 数值、正式生产同步 profile v1、Parquet 物理布局和
Worker 生产容量继续 `PENDING`。这些值已被限定为版本化 profile/部署参数，不阻塞 S1 领域与
逻辑 Contract。A.1 后 `S1 CONTRACT = READY`，可开始后续 B/S2 的参数化 pipeline；生产 profile
未批准时只能使用 `TEST/G0` profile，不得处理真实生产同步。本报告没有开始 B/S2。

### 3.1 A.1 跨相机时间映射

冻结的选择顺序为：

```text
Capture target
→ 精确有理数反向映射到 source target
→ nearest source PTS + 固定 tie-break
→ 选中 source frame 正向映射到 Capture time
→ 计算 Capture 域 sync_error_ns
→ 应用 profile tolerance
```

Case F 证明逐路 `source_pts_ns=0` 并不表示同时发生：Camera 2 的首帧映射到 Capture 80 ms，
所以 Capture 0 ms 处不是 `PRESENT`。Case G 在 4 秒、30 Hz 对照下，240 slots 全部
`PRESENT`，绝对误差 P95 为 3.566667 ms、max 为 3.966667 ms；这些是已知 `+1000 ppm`
合成真值下的离散选帧误差，不是生产相机 drift 分布。

移除 Camera 2 映射的负例稳定返回
`TRUSTED_STREAM_TO_CAPTURE_MAPPING_REQUIRED`。这冻结“不具备同步条件”的行为，禁止把不同
stream 的首帧默认视为同时发生。单锚点 Case F 的 `drift_ppm=null`；只有两锚点合成 Case G
才提供 drift，未把未知漂移伪装为 0。

## 4. 时间轴、误差和 Slot 密度

Case C 在 20 ms tolerance 下的候选结果：

| timeline rate | Frame Slot 密度 | slots | P95 / max absolute sync error | 源帧复用 |
| --- | ---: | ---: | ---: | ---: |
| 10 Hz | 20 rows/capture-second | 40 | 20 / 20 ms | 0 |
| 25 Hz | 50 rows/capture-second | 100 | 13.333333 / 13.333333 ms | 0 |
| 30 Hz | 60 rows/capture-second | 120 | 20 / 20 ms | 10 |

这不是“25 Hz 最佳”的证据。G0 没有训练 sampling、动作边界、标注可容忍误差或关键 Camera
角色要求，无法在低误差、时间分辨率和数据密度之间做业务选择。

在 Case C 的 30 Hz timeline 中：10/15/20 ms 分别得到 90/110/120 个 `PRESENT` slots；
20 ms 只是刚好覆盖 30↔25 FPS 的理论半帧最坏情况。Case E 的真实 gap 在 10/15/20 ms 下均保留
18 个 `MISSING`，证明 nearest 不会越过 tolerance 强行填满。合成理想 FPS 的误差分布不能代表
真实相机 clock offset/drift/residual，因此 tolerance 数值仍为 `PENDING`。

tie-break 对照在 100 ms 目标点面对 80 ms 与 120 ms 两个 25 FPS 帧时稳定选择 80 ms，保存
`sync_error_ns=-20,000,000`。包含边界下，绝对误差恰好 20 ms 为 `PRESENT`；15 ms profile 下同一
候选为 `MISSING`。

## 5. 舍入规则

30 Hz 的精确 step 是 `100,000,000/3 ns`，不能由单个整数 `timeline_interval_ns` 无损表达。
一小时（最后索引 107999）对照：

| 方法 | 最后时间点误差 |
| --- | ---: |
| 每个 index 从精确有理数独立 `ROUND_HALF_EVEN` | ≤ 0.333334 ns |
| 重复累加 floor interval `33,333,333 ns` | -35,999.666667 ns |
| 重复累加 ceil interval `33,333,334 ns` | +71,999.333333 ns |

因此冻结“保存精确 rate/step 分数，并按 index 独立 half-even”的规则。具体 rate 没有冻结；如果
选择的 rate 可被整数纳秒精确表达，仍可派生 interval，但 revision/profile 不能假设所有 rate 都
满足此条件。

## 8. 冻结状态与风险

S1 领域/逻辑 Contract：

| 对象/规则 | 状态 |
| --- | --- |
| Capture | `FROZEN`：`capture_id = capture_session_id`，不建立第二身份 |
| Camera | `FROZEN`：来自冻结 snapshot；`camera_number = camera_index + 1`，缺路不重编号 |
| Sync Revision | `FROZEN`：冻结输入/profile/算法的一次不可变结果；重算创建新 revision |
| Sync Frame | `FROZEN`：revision 内连续 0 基 index + 有理数规则生成的 capture timestamp |
| Per-view Frame Slot | `FROZEN`：每个 Sync Frame × 每个 expected Camera 恰好一行 |
| `PRESENT/MISSING/INVALID` | `FROZEN`：互斥、状态空值与 reason 规则进入 logical schema v1 |
| `NOT_RUN/NO_DETECTION` | `FROZEN`：`NO_DETECTION` 必须有成功 inference provenance；缺失/无效只能 `NOT_RUN` |
| Canonical Artifact schema | `FROZEN`：logical row v1；Parquet physical layout 未冻结 |
| Provenance | `FROZEN`：行 → Capture/Snapshot/Stream/ClipAsset/raw PTS/raw SHA/sync revision；AI/人工引用条件延伸 |
| `AnnotationRevision.sync_revision_id` | `FROZEN` 为 nullable；仅同步多机位场景引用，单视频 revision 保持空 |
| SyncProfile 参数化契约 | `FROZEN`：精确 timeline rate、可信 time mapping、Capture 域 tolerance、rounding/tie-break 均由 profile/冻结输入提供，不硬编码 |
| production sync profile v1 | `PENDING`：rate/reference 来源/tolerance 数值缺业务与真实边端证据，未批准正式生产值 |

| 项目 | 可冻结 |
| --- | --- |
| timeline rule | YES（参数化精确有理数规则；生产 rate 值 `PENDING`） |
| reference rule | YES（每路要求可信 stream → Capture 映射；生产来源选择 `PENDING`） |
| tolerance | YES（参数化 Capture 域误差与包含边界；生产数值 `PENDING`） |

风险分级：

- `BLOCKER`：无。A.1 已关闭“逐路首帧被误当成同时发生”的同步数学门禁。
- `HIGH`：生产 profile 尚未批准；缺真实边端共同 clock/anchor/drift 来源与误差数据，因此不得
  开放真实生产同步。缺目标规模和跨语言 Parquet 证据，物理布局与生产容量不能承诺。
- `MEDIUM`：`INVALID` 仅做逻辑故障注入，尚缺稳定损坏媒体/解码检出矩阵；有界读取只验证本地
  PyArrow row-group statistics，尚未验证对象存储 range read/API P95/P99。
- `LOW`：小型合成 MP4 不代表真实 codec、分辨率、B-frame、音轨或长时稳定性。

阶段结论：`V1.19 G0 = PASS`；`V1.19 S1 CONTRACT = READY`。本轮未开始 B/S2；下一阶段可以按
参数化 Contract 开始 B/S2，但生产 profile 未批准时必须限 `TEST/G0`，不得开放真实生产同步。
