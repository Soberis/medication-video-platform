# V1.26 配药事件工作台设计

> 状态：CURRENT / DESIGN FROZEN<br>
> 对齐需求：[V1.26 需求基线](../requirements/baselines/V1.26/配药视频数据管理平台需求文档_V1.26.md)<br>
> 继承参考：[V1.25 CaptureGroup 技术设计](./capture-group-multicamera-workflow-technical-design.md)与[V1.25 多机位质量评审流程](./multi-camera-quality-review-workflow.md)

## 1. 范围与继承

V1.26 完整继承 V1.25 的 CaptureGroup 身份、收件、视图、质量、任务、Revision、Review、Cleaning、导出、权限、审计和 provenance 语义。本文只定义产品信息架构和事件工作台展示，不改变模块所有权、数据库事实、API 授权或领域状态机。

## 2. 产品信息架构

```text
项目
├─ 视频管理
│  └─ 配药事件列表（CaptureGroup）
│     └─ 配药事件工作台
│        └─ 1..N 个机位视图
└─ 配药动作标注
   └─ 任务待办
      └─ 深链到对应事件和当前操作
```

`/projects/:projectId/capture-groups` 是“视频管理”的发现入口。`/videos` 和 `/assets/:id` 只承担 V1.24-compatible 历史兼容、管理或诊断；属于 CaptureGroup 工作流的资产应进入对应事件工作台。

## 3. 工作台信息层级

页面从上到下固定为：

1. Header：事件身份、拍摄时间、机位数量、当前业务阶段。
2. Workflow rail：六个业务阶段，突出当前阶段和真实阻断。
3. Focused video workspace：当前机位视频和与判断直接相关的辅助证据。
4. Current Action：唯一常驻动作中心；桌面端与视频区组成约 70% / 30% 的主工作区，可按目标视口调整。
5. Progressive details：技术、历史、provenance、审计和危险操作。

页面先回答对象、阶段和下一动作，之后才展示技术细节。常规完成状态保持安静；失败和真实阻断才提高视觉权重。

## 4. 六个业务阶段

```text
接收 → 机位质量 → 事件质量 → 配药动作标注 → 人工复核 → 训练资格检查
```

Media Probe、media status、technical quality、MediaPipe 和 Candidate 是支持业务判断的证据，不是额外工作流节点。Candidate 失败或 `NO_HAND_DETECTED` 只有在服务端真实业务守卫阻止操作时才能呈现为 blocker。

## 5. Current Action

每个上下文最多一个视觉主操作，且必须同时满足服务端状态和 capability：

| 当前事实 | 主操作示例 |
| --- | --- |
| `receipt_state=RECEIVING` 且允许 finalize | 结束接收 |
| 当前机位质量未决且允许提交 | 判断当前机位质量 |
| 机位质量已决、事件质量未决且允许提交 | 确认事件质量 |
| 任务 `ASSIGNED` 或返工且允许编辑/提交 | 进入或继续配药动作标注 |
| revision 已提交且 `can_review` | 进入人工复核 |
| Review `APPROVED` | 查看训练资格检查 |
| 流程已完成 | 查看结果或获准的导出上下文 |

无授权动作时，面板显示服务端可证明的等待原因或 blocker，不显示不可执行 CTA。Overview、Inspector、Quality、Annotation 和 Review 区域不得再各自保留竞争性的“下一步”卡片。

## 6. N=1 与 N>1

- `N=1`：直接显示视频，只在标题附近显示低权重“机位 1”，不渲染切换轨道。
- `N>1`：使用紧凑、键盘可操作的机位选择器；默认只显示机位身份和选择所需的质量/可用性摘要。
- media、technical quality、Candidate、mount、ID、同步声明和时间偏移进入选中机位的渐进详情，不在每个选择项永久展开。

## 7. 辅助证据边界

媒体和 AI 事实保持可见、可追溯，但视觉层级低于当前业务阶段和人工操作。Candidate 只能辅助 Revision，不得变成质量、Review 或 Cleaning 结论。技术失败应精确说明影响哪一路视图，不把局部失败泛化成整个事件失败。

## 8. Cleaning 语义

Review 是人工闸门。Review `APPROVED` 后，Core API 使用冻结规则确定性执行 Cleaning / 训练资格检查并记录结果与 provenance。管理员 recheck 重新读取当前权威事实并执行同一规则，不提供人工选择 PASS、WARNING 或 REJECT 的能力。

## 9. 前端工作流推导

当前实现应从现有 `receipt_state`、质量事实、事件质量、`task.status`、`can_select_primary`、`can_submit`、`can_review`、`can_recheck_post_cleaning` 等服务端事实推导展示。

推荐在 CaptureGroup feature 内实现一个纯展示 helper，例如：

```text
deriveMedicationEventWorkflow(facts) -> {
  stage,
  steps,
  primaryAction,
  blocker
}
```

该 helper 不持久化状态、不授予权限、不触发副作用，也不是通用状态机。V1.26 不增加 `CaptureGroup.next_action`、`CaptureGroup.blockers`、工作流表或 `WorkflowEngine`。未来只读聚合读模型保持 DEFERRED，直到真实 UAT 证明其必要性。

## 10. 可访问性

- 页面只有一个 `h1`，各区域使用连续的语义标题层级。
- 机位选择、流程节点和主操作均可使用键盘，焦点清晰可见。
- 当前阶段、完成、等待和阻断不能只靠颜色表达。
- 异步提交、刷新、成功和错误反馈可被辅助技术感知。
- muted text 保持足够对比度；图标按钮具有可访问名称。
- 主操作名称包含明确对象和动作，不使用孤立的“处理”或“继续”。

## 11. 非目标

- 后端 `WorkflowEngine`、持久化 `next_action` / `blockers`。
- CaptureSync、标定、3D、DatasetVersion 平台。
- 全机位自动播放、多视频编辑器。
- 新的全局状态管理或前端状态机框架。
