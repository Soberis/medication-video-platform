# V1.27 AI Evidence Pipeline Audit

> 状态：READ ONLY AUDIT
> 审计日期：2026-09-01
> 审计范围：Upload → CaptureGroup → ClipAsset → Media Probe → MediaPipe hand detection → CandidateAnnotation → AnnotationRevision → Review → Cleaning → training export
> 变更边界：本审计文档本身只新增审计内容，不修改 production code、database schema、API implementation 或 workflow；同批次其他任务的变更另行审查。

## 1. 结论摘要

当前平台已经具备一条可运行的 AI 辅助证据链：

1. Upload 完成后创建 ClipAsset，并自动安排 Media Probe。
2. Media Probe 成功后将 ClipAsset 置为 INGESTED，并在事务提交后安排 hand-pose AI job。
3. Python Worker 使用 MediaPipe Tasks Hand Landmarker 在 VIDEO 模式下处理视频，结果通过受控 API 回 Core API。
4. Core API 将 AI 输出写入 ai_job、ai_job_attempt 和 candidate_annotation；CandidateAnnotation 只作为候选证据，不能直接成为正式标注、Review 或 Cleaning 决定。
5. CaptureGroup 工作流建立一条组级 AnnotationTask/AnnotationRevision/Review/Cleaning 链，并在导出前执行人工闸门和确定性准入检查。

这条链在“AI 不能替代人工决定”“输入/模型/算法有摘要和幂等约束”“导出必须经过人工 Review 与 Cleaning”方面是安全且边界清楚的。但按 V1.27 的证据保留政策，当前还不是完整的一等证据血缘：

- AI job 和 candidate 只直接绑定 project、ClipAsset，不直接绑定 CaptureGroup、CameraStream 或 camera/view。
- Media ingest 会独立触发 hand-pose scheduling；如果此时尚未有 CameraStream 绑定，AssetCatalogQueryService 将 enabledForHandDetection 视为 false，自动排队会被跳过。本次静态检查未确认 CameraStream 绑定完成后的等价自动补排，因此链路对绑定与媒体完成的先后顺序敏感。
- Review/Cleaning 保存的是按 ClipAsset 汇总的 candidate evidence JSON，而不是不可变的具体 candidate 行、attempt、result message/digest 和 input snapshot。
- v2 Parquet 与 v3 JSON 导出都不能单独携带完整链路；它们需要依赖当前数据库的间接查询或 JSON 快照。

因此，当前判断是：

> 当前 pipeline 足以支持 P0 的“AI provides evidence. Human makes final decisions.”闭环；但如果要求 training export 从导出物本身稳定证明“原始视频 → 具体机位 → 当时被人工查看的具体 AI attempt/candidate → AnnotationRevision → Review → Cleaning”，答案是否定的。核心缺口是 evidence identity/snapshot，而不是 MediaPipe 推理本身。

## 5. MediaPipe 在哪里实现？

### 5.1 推理实现

真实推理在：

workers/ai-worker/src/medication_ai_worker/landmarker.py

关键行为：

- ALGORITHM_KEY = MEDIAPIPE_HAND_LANDMARKER，版本为 v1。
- 通过 MediaPipe Tasks Hand Landmarker 配置 RunningMode.VIDEO，num_hands = 2，detection/presence/tracking threshold 均为 0.5。
- 使用 PyAV 读取视频的第一个 video stream。
- 要求 frame PTS 严格递增，并将 PTS 转成毫秒。
- 按 10 FPS 采样并调用 detect_for_video。
- 每个有效手部候选写出 frame timestamp、图像宽高、hand index、handedness、score、bbox、21 个 landmarks 和 valid landmark count。
- 没有检测到手的帧不写 candidate row；NO_HAND_DETECTED 由完整分析后的 run summary 表达。
- handedness 是辅助元数据；未知 handedness 不会覆盖有效几何结果。

Worker 不直接写 Core API 数据库。processor.py 负责读授权输入、校验 SHA/size、执行推理并通过 API 提交结果；模型必须有 SHA-256，运行时不下载模型。

### 5.1.1 v2 result 的精确候选结构与坐标语义

结果消息的完整 envelope 以 [`ai-hand-pose-result-v2.schema.json`](../../contracts/events/ai-hand-pose-result-v2.schema.json) 为准。其顶层固定包含：
`schema_version`、`message_id`、`job_id`、`attempt`、`lease_token`、`input_sha256`、`model_sha256`、
`profile_sha256`、`started_at`、`completed_at`、`outcome`、`analysis_complete`、`hand_result`、
`total_video_frames`、`inference_frame_count`、`frames_with_hand`、`frames_without_hand`、
`left_hand_detection_count`、`right_hand_detection_count`、`invalid_landmark_count`、
`processing_duration_ms`、`failure_reason` 和 `candidates`。每个 `candidates[]` 元素严格包含：

```json
{
  "frame_timestamp_ms": 100,
  "image_width": 1280,
  "image_height": 720,
  "hand_index": 0,
  "handedness": "RIGHT",
  "handedness_score": 0.91,
  "bounding_box": { "x": 0.1, "y": 0.2, "width": 0.02, "height": 0.04 },
  "landmarks": [
    { "x": 0.1, "y": 0.2, "z": -0.01 }
  ],
  "valid_landmark_count": 21
}
```

`landmarks` 实际必须有恰好 21 个点；示例为节略展示，不代表可发送单点数组。点对象只含 `x`、`y`、`z`，三值必须为有限数；bbox 只含 `x`、`y`、`width`、`height`，宽高必须为正有限数。`valid_landmark_count` 固定为 21。`image_width`/`image_height` 是解码帧像素尺寸；`hand_index` 是该帧检测结果中的 0/1 槽位，不是左右手身份。

Worker 直接保留 MediaPipe Tasks `result.hand_landmarks` 的坐标：`x`、`y` 是归一化图像坐标，`z` 是 MediaPipe hand-landmark 的相对深度；它们不是像素坐标，也不是 `world_landmarks` 或跨相机三维坐标。当前代码不做像素换算、范围裁剪或世界坐标转换；bbox 是同一候选原始 `x/y` 的有限 min/max 包络。`frame_timestamp_ms` 是视频容器 PTS 乘以 stream time base 后四舍五入到毫秒，并要求严格递增，因此是 source-local 容器时间，不是合成帧序号或墙钟时间。

持久化顺序为 `ClipAsset → ai_job → ai_job_attempt → Worker → PUT /api/v1/internal/ai-jobs/{jobId}/attempts/{attempt}/result → AiJobExecutionService`；Core API 在同一事务中校验结果后写入 `candidate_annotation` 和 `ai_job_result_inbox`。`candidate_annotation` 的逻辑唯一键仍是 `(ai_job_id, frame_timestamp_ms, hand_index)`；相同 `message_id` 与相同 result digest 的重放直接幂等返回，不新增候选。`SUCCEEDED_WITH_CANDIDATES`、`SUCCEEDED_NO_HAND`、`FAILED` 和 `RUNNING` 是读取侧对原始 `outcome`/`hand_result`/执行状态的区分；`FAILED` 不等同于 `NO_HAND_DETECTED`，失败消息不写候选，也不补造零坐标。

### 5.2 Core API 的作业和结果接收

Core API 侧由 aicandidate 模块完成：

- HandPoseJobService 创建/重试 job，校验 project membership、approved model、ClipAsset 状态、MediaReport digest/duration、feature flag 和 candidate capacity。
- AiJobExecutionService 校验 job/attempt/message/lease、输入与模型/profile 摘要以及结果契约；成功时在事务内写入 candidate_annotation，并写入 ai_job_result_inbox 的 message/result digest。
- HandPoseCandidateQueryService 和 CandidateEvidenceQueryService 提供候选查询/摘要。

这套异步机制中的 outbox、RabbitMQ、lease、attempt、inbox、幂等和 retry 不是无意义的复杂度：它们服务于跨进程、至少一次投递、重复结果和可重试失败。真正的审计问题是这些事实没有被完整投影到组级 evidence identity，而不是异步机制本身。

## 6. AI 结果存储在哪里？

### 6.1 关系型事实

| 存储 | 内容 | 作用 |
| --- | --- | --- |
| ai_job | project、ClipAsset、algorithm/version、model SHA、input SHA/size/type、sampling/profile、状态、hand_result、幂等键、请求者和时间 | 一次逻辑 AI 作业 |
| ai_job_attempt | attempt number、message id、lease、worker、状态、开始/完成时间、分析范围、帧/候选/左右手/invalid 统计、failure/retryable | 一次执行尝试和运行摘要 |
| candidate_annotation | candidate id、ai_job、project、ClipAsset、frame timestamp、hand index、handedness、score、bbox、landmarks、image dimensions、valid count | 可供人工查看和导出的候选证据 |
| ai_job_result_inbox | message id、job、attempt、result SHA、接收时间 | 结果接收幂等/去重，不是完整的原始 result artifact |
| media_report | Media Probe 的输入、recipe、software、时长、帧数、解码、digest 验证事实 | 证明媒体技术上可读，不保存 AI 候选 |
| 审计记录 | 排队等动作及 request/trace/authorization context | 操作审计；当前实现没有对每次 AI terminal success/failure 都产生完整 V1.27 evidence audit 的证据 |

### 6.2 原始媒体

原始视频仍由 ClipAsset 的对象存储位置和受控读取路径管理。AI Worker 获取的是受控读取输入，不会把视频复制进 CandidateAnnotation 或普通日志。候选几何也不覆盖原始视频；播放器通过时间戳叠加显示。

### 6.3 不存储的内容

- 没有把 AI 结果写入 AnnotationRevision 的正式标签字段。
- 没有把 AI 结果写入 QualityReview、CaptureGroupQualityReview、AnnotationReview 的人工结论字段。
- 没有把 AI 结果直接写入 Cleaning pass 或 training qualification。
- no-hand 帧没有逐帧 candidate rows；可审计事实依赖 attempt/job summary。

## 7. 关键实体和字段的链接判断

| 链接对象 | 当前链接 | 判断 |
| --- | --- | --- |
| Project | ai_job.project_id、candidate_annotation.project_id；V60 增加 project-scoped composite FK | 直接且有数据库隔离约束 |
| ClipAsset | ai_job.clip_asset_id、candidate_annotation.clip_asset_id | 直接且是 AI 当前的主锚点 |
| CaptureGroup | clip_asset → camera_stream → capture_session(captureGroup) | 只有间接链接；AI job、attempt、candidate 和 result contract 没有 capture_group_id |
| Camera / view | camera_stream.camera_index/channel + snapshot member，再通过 ClipAsset 关联 | 只有间接链接；Candidate 查询/API 不返回 camera/view identity |
| Media Probe | AI job 通过 ClipAsset + matching input digest 验证 MediaReport duration/input；没有 media_report_id | 逻辑前置检查存在，但不是一等外键关系 |
| AI attempt | attempt 独立存在于 ai_job_attempt；candidate 只 FK 到 ai_job | 具体 candidate 无法直接证明来自哪个 attempt/message |
| Algorithm/model/profile | AI job 直接保存；v2 candidate query 会将 algorithm/version/model/profile 带到导出 | 主要 provenance 有，但仍依赖 job join |
| Candidate timestamp | candidate_annotation.frame_timestamp_ms | 直接保存 source-local 时间；由视频 container PTS 得到，不是全局墙钟时间 |
| Human action interval | AnnotationRevision/annotation document 的 segment，使用 [start_ms, end_ms) | 对主视图可直接关联到 revision；不是每个 candidate 的独立人工确认 |
| Cross-camera timing | CameraStream 有 time_offset_ms 和 declared sync | 当前没有用于 AI candidate 时间归一化，也没有在 export 中形成可靠跨视图映射 |
| Review / Cleaning | Revision → Review → Cleaning 有显式 ID/FK；AI 证据通过 JSON summary 进入 Review/Cleaning | 人工闸门可追踪，但 AI 证据引用不是 candidate-level immutable reference |

### 7.1 时间语义

AI timestamp 是某个 ClipAsset 内的 source-local PTS 毫秒值。AnnotationRevision 的主 action interval 也使用主视图 ClipAsset 的时间轴，Cleaning 明确把主视图标为 authoritative timebase；support views 只作为事件级证据，不自动复制 action interval。

这是一个安全的保守设计，因为没有伪造跨机位同步。但它也意味着：当前平台不能仅凭 AI candidate timestamp 证明 Camera 2 的候选与 Camera 1 的 action interval 在同一真实时刻对应。time_offset_ms 和 declared sync 仍是 capture fact，不是当前 export 使用的 mapping provenance。

## 8. Review、Cleaning 如何使用 AI evidence？

CaptureGroupAnnotationWorkflow 在准备 group Review 时调用：

`CandidateEvidenceQueryService.findByClipAssets`

Task C 已将该查询收口为每个请求 ClipAsset 一条的、只读的 provenance snapshot。它读取当前 ClipAsset 的 SHA，并联结最新 MediaPipe job、最新 attempt、对应 result inbox 和该 job 的 CandidateAnnotation rows，区分：

- `NO_JOB`、`QUEUED`、`RUNNING`、`FAILED`；
- `SUCCEEDED_NO_HAND`；
- `SUCCEEDED_WITH_CANDIDATES`；
- `INVALID_PROVENANCE`。

只有当 job project、ClipAsset 和当前 ClipAsset project/ID 一致，且 job `input_sha256` 等于当前 ClipAsset SHA 时，job provenance 才有效。成功状态还必须有一致的 attempt、message、result digest、hand result、完整 run summary 和候选数量；候选集合 digest 使用固定字段顺序、排序后的 JSON object keys、规范化数值和 `candidate_annotation_id`/geometry/count 生成。Review 的 `candidate_evidence` 保存这份快照，CaptureGroupCleaning 将同一快照复制为 `candidate_provenance`；Candidate 仍不是人工质量、AnnotationRevision、Review 或 Cleaning outcome 的准入条件。

因此，同一 ClipAsset 被替换或产生旧 result 时，快照会明确标记 `INVALID_PROVENANCE`，而不是把旧结果当作成功 evidence。重试仍保留最新 attempt number、attempt identity、message ID 和 result SHA；`CaptureGroupCleaningService.inputFingerprint` 现在以版本化的 canonical candidate snapshot 参与 replay key，Cleaning 不会在相同 Revision 下静默复用另一份 AI evidence。

本闭环仍有意不把 candidate geometry、MediaReport identity/recipe 或对象存储 key 复制到 Review/Cleaning/v3；候选集合可以通过 digest 与数据库中的 CandidateAnnotation 集合核对，但 v3 不是完整 AI result artifact。

## 9. Training export 是否能完整回溯？

### 9.1 v2 legacy Parquet

历史 v2 实现（已退役；仅用于审计）的事实来源是：

- training_data_eligibility
- training_data_candidate_observations

平台数据库层面，v2 可以通过以下路径进行大部分重建：

candidate_annotation → ai_job → clip_asset → camera_stream → capture_session/CaptureGroup

同时，candidate row 带 candidate_annotation_id 和 frame_timestamp_ms，export row 带 annotation_revision_id、人工 action label/start/end 以及 algorithm/model/profile；eligibility view 也会验证 human quality、Review APPROVED、Cleaning PASS/SUCCEEDED、asset/document/schema digest。

但 v2 Parquet 单独拿出来并不能完整证明全链路：

- row 没有 capture_group_id、camera number、camera_stream_id；
- row 没有 ai_job_id、ai_job_attempt_id、result message/digest；
- row 没有 media_report_id；
- row 没有 AnnotationReview ID/cleaning ID 等完整 gate identity，只保留部分元数据/门禁上下文；
- video_id/ClipAsset ID 能帮助回到数据库，但导出物自身没有对象存储 key 或原始媒体 digest 的完整 lineage；
- candidate 选择是历史 v2 行投影的 latest successful job 语义；当前 V1.27 Review/Cleaning/v3 使用固定的 AI evidence snapshot。

所以，v2 的准确评价是：**使用同一时点且未漂移的数据库可重建大部分关联；仅凭 Parquet 文件不能完成稳定的完整回溯。**

### 9.2 v3 group training-data manifest

实现：datasetexport/TrainingDataV3ExportService，事实来源是 training_data_group_eligibility_v3。

v3 对组级事实更完整，事件中带有：

- capture_group_id、annotation_revision_id、revision；
- primary clip/camera、confirmed view set、参与/排除视图；
- group quality review ID/result；
- annotation_review_id/decision/reviewer/time；
- capture_group_cleaning_id、rule set、outcome/reasons/checks、actor/time；
- view_evidence 中的 cameraStreamId、clipAssetId、camera number 等；
- candidate_evidence 和 candidate_provenance 中的 ClipAsset SHA、执行状态、aiJobId、input SHA、algorithm/model/profile、attempt identity/number、message/result digest、run summary、候选数量/时间范围和候选集合 digest。

但 v3 的性质是组级资格与 provenance manifest，不是候选帧训练数据，也不是可独立验证的 AI result artifact：

- 不直接 join candidate_annotation，不导出 candidate_annotation_id 或候选几何；只保留候选集合的确定性 digest；
- 不复制 ai_job_attempt/result artifact，但保留 attempt identity/number、message id、result digest 和 input SHA；
- 没有 media_report_id 或原始对象存储 key；
- candidate_provenance 和 view_evidence 是 JSON snapshot，V69 只校验 JSON 类型，不对其中的 AI/candidate/media 引用建立外键；
- mapping_provenance 当前可以为空，support view 的 action interval 会被明确清除；这符合事件级证据边界，但不提供跨视图时间映射；
- 通过 clipAssetId 可以回到当前数据库中的原始媒体，但不是 v3 文件内的自包含媒体 lineage。

所以，v3 的准确评价是：**组、人工 revision、Review、Cleaning 的 manifest 链较完整；AI provenance 已能回答当前/冻结 ClipAsset bytes、job、algorithm/model/profile、attempt、result 和执行状态，并用候选集合 digest 绑定 evidence；但 v3 仍不是包含原始 geometry、MediaReport 或对象存储引用的独立 AI artifact。**

### 9.3 `hand-landmarks.v1` feature export

`HandLandmarkTrainingExportService` 复用 v3 的 CaptureGroup eligibility 投影，并进一步读取精确的人工 `AnnotationRevision`、Primary View、冻结的 MediaPipe execution attempt 和 Candidate geometry，按 Primary View 的 `[start_ms, end_ms)` 人工区间生成服务端 CSV。每行代表一个采样 frame 内的一只实际检测到的手，同一 frame 的多只手分别成行；没有手时不补造 row，Supporting View 的 source-local timestamp 也不映射到 Primary View 区间。

该 CSV 是按当前合成数据资格事实动态生成的下载 artifact，不创建新表、DatasetVersion 或训练服务；Java export contract 与 Python readback smoke test 只证明契约和可读性，不等同于实际 training consumer、真实样本 UAT 或模型训练成功。

### 9.4 完整链路结论表

| 要回答的回溯问题 | v2 Parquet | v3 JSON | 当前平台数据库 |
| --- | --- | --- | --- |
| 回到原始 ClipAsset/视频 | 有 video/ClipAsset ID，可查数据库 | 有 view evidence 的 ClipAsset ID，可查数据库 | 可以，ClipAsset 有对象位置、SHA、状态 |

| 回到具体 AI job/attempt/result | 仅可由数据库重新推导部分 job；没有 attempt/result ref | 有 aiJobId、attempt、message/result digest、input SHA 和 run summary；原始 artifact 仍需查数据库 | job/attempt/inbox 分别存在，candidate 通过 job 与 snapshot digest 关联 |

## 10. 已具备的能力

1. **AI 与正式业务真值隔离。** CandidateAnnotation 是辅助证据；AI 不能创建或改写正式 AnnotationRevision、人工质量、Review 或 Cleaning 结果。
2. **CaptureGroup 绑定规则明确。** 外部 manifest/metadata 显式给出 group key、camera numbers 和文件身份，不用文件名、上传顺序或时间猜组。
3. **输入和模型 provenance 有基础。** job 记录 input/model/profile/algorithm 摘要，Worker 校验输入 SHA/size，模型要求 SHA-256。
4. **跨进程可靠性基础较强。** Outbox、RabbitMQ、lease、attempt、inbox、幂等键和 retry 处理了重复消息、租约和失败恢复。
5. **媒体技术闸门存在。** MediaReport 只有在完整解码和 input digest 验证成功后产生；AI 任务要求匹配的媒体技术事实和 INGESTED 状态。
6. **人工闸门完整。** 逐视图质量、组质量、AnnotationRevision、Review、Cleaning 和 training eligibility 分层；no-hand/failed/zero candidates 不自动变成人工拒绝。
7. **导出安全边界清晰。** v2/v3 不复制 MP4；标签来源是人工 AnnotationRevision，候选几何明确不是 ground truth；事务使用 repeatable-read snapshot。
8. **版本化和不变性已有基础。** AnnotationRevision、Review、Cleaning run 和规则 digest 形成可审计的业务链，组视图集合也会在任务/修订阶段快照。

## 11. 缺口与架构风险

| 优先级 | 发现 | 证据 | 影响 |
| --- | --- | --- | --- |
| P0 | AI 证据没有一等 CaptureGroup/CameraStream/view identity，且自动排队依赖绑定时序 | ai_job、candidate 和 AI job/result contracts 只有 project + clip_asset；未绑定时 enabledForHandDetection=false 会跳过自动排队；组/机位只能后置间接查询 | 已绑定后运行的 job 仍无法由 AI 事实直接证明 group/camera；若 Media ingest 先完成，当前自动 hook 可能只记录 skipped，后续是否补排依赖显式动作 |
| 已关闭（Task C） | Review/Cleaning 没有固定具体 AI evidence snapshot | `findByClipAssets` 按 ClipAsset 生成状态化 snapshot；Review/Cleaning 保存同一 JSON，并包含 input/job/attempt/result/run-summary/candidate-set identity | 旧 job、替换后的 asset 或不一致执行会变成 `INVALID_PROVENANCE`；候选 evidence 不会改变人工闸门 |
| 已关闭（Task C） | Cleaning replay 指纹没有覆盖 candidate evidence | `CaptureGroupCleaningService.inputFingerprint` 纳入 `candidate-evidence.v1` canonical snapshot | 同一 Revision 的 evidence 变化会产生新的 Cleaning input fingerprint |
| 仍保留为边界 | Candidate 不直接绑定 attempt/result artifact | candidate_annotation 仍 FK 到 ai_job；attempt/message/result digest 在 attempt/inbox 保存，snapshot 做一致性核验 | 不增加迁移或新 artifact 表；若未来需要行级 FK，应另行版本化，当前 v3 已可用 digest 做数据库侧核对 |
| P1 | AI 与 Media Probe 只有 digest 逻辑关联 | AI job 验证 MediaReport 的 input/duration，但不保存 media_report_id | 无法稳定指出使用的是哪个不可变 MediaReport/recipe/software 事实，尤其在同一 ClipAsset 有多次 probe 时 |
| P1 | AI terminal success/failure 的 V1.27 审计事件不完整 | 当前可见的 AI audit 重点是 queued/auto queued/retry；attempt 有运行摘要但不是完整 group/view audit | 失败原因、attempt、group/view、输入、模型和最终状态未形成统一可检索的完成/失败审计事实 |
| P1 | v3 provenance 依赖弱约束 JSON | capture_group_cleaning 和 v3 view 对 candidate/media 引用只检查 JSON 类型，未建立 candidate/job/media FK | JSON 中的引用可能缺失、漂移或指向不存在/不再可验证的证据；数据库无法阻止此类不一致 |
| P2 | 跨机位时间仍是 capture fact，不是 evidence mapping | CameraStream.time_offset_ms/declared sync 未进入 candidate timestamp 对齐或 export mapping | 可以安全避免伪同步，但不能证明 support camera 的候选与主视图动作区间的精确对应 |
| P2 | 当前 group workbench 的 AI 证据聚合不是一等 group query | AI 查询以 ClipAsset/video 为中心；组 Review 在服务端临时聚合各 view 的 per-ClipAsset provenance snapshot | 组级消费方需要重复组→view→clip→AI 查询，仍可能形成不同的组级展示口径 |
| P2 | AI 候选明细的容量/保留边界尚未成为本审计范围内的闭环事实 | 当前设计把密集候选放 PostgreSQL，并有限制 20,000 candidates/job | P1 批量规模扩大时需要单独验证索引、保留、归档和查询成本；这不是本次建议直接引入对象存储或新队列的理由 |

## 12. 不必要复杂度与应保留的复杂度

### 应保留

MediaPipe 跨进程运行、输入验证、模型审批、outbox、lease、attempt、inbox、幂等和 retry 都对应实际的失败/重复/重试边界。删除它们会降低可靠性和可审计性，不是本次应做的简化方向。

### 运行时遗留复杂度（非 V1.27 产品承诺）

1. V1.27 当前运行时已收口到 CaptureGroup 产品路径；低层 ClipAsset/视频仍作为媒体事实和 AI evidence/job 的输入保留，不再构成独立的单视频任务或 Cleaning 产品路径。历史代码/契约清理不应通过删除数据库迁移或审计文档完成。
2. CaptureSession 同时承载 CaptureGroup identity，导致代码中仍可能存在 clip_asset_id 与 capture_group_id 两套历史入口和条件分支。
3. 退役 v2 Parquet 与当前 v3 group JSON 的历史证据仍可在迁移/文档中出现；当前运行时和公开产品契约只保留 v3 输出。
4. Candidate evidence 在 Review、Cleaning 和 v3 中重复保存不同粒度的 JSON summary；但它们没有共同的 immutable evidence identity。

这些复杂度中，前两项主要是运行时历史尾部，当前不应为了文档冻结贸然删除；第三、四项是后续追溯/收敛工作。应先定义证据身份和所有权，再决定是否统一 exporter 或减少 snapshot 复制，避免一次大范围重构。

## 13. 推荐下一步（仅建议，不在本次实施）

### P0：先定义 immutable AI evidence identity

在下一次 schema/API 设计前，形成一个版本化的 AI evidence snapshot/ref 约定，至少能够稳定引用：

- project、CaptureGroup、CameraStream/view、ClipAsset；
- ai_job、ai_job_attempt、result message/result digest；
- input SHA/size/type、MediaReport/probe recipe；
- algorithm/version/model/profile；
- candidate_annotation IDs 或可验证的 candidate set digest、时间范围和结果状态；
- 创建/完成时间、失败/重试属性、system actor、request/trace。

这应是“审计证据引用”的设计决策，不等于马上新增通用 workflow engine，也不应复制 MP4。

### P0：解决 group binding 与 AI scheduling 的顺序

优先选择可证明的路径之一：

- 在 Media ingest/AI 自动排队前确保显式 CameraStream/CaptureGroup binding 已完成；或
- 在 CameraStream binding 完成时增加明确、幂等、可审计的补排/对账动作。

当前实现并不允许普通 AI queue 绕过 camera hand-detection enablement guard，因此不应为了填补这个时序缺口而默认引入 unbound job；只有在明确设计并版本化其语义后才考虑该方案。

不得用文件名、上传顺序或时间戳事后猜组/机位。

### P0/P1：Review 和 Cleaning 引用 exact snapshot

Task C 已让 Review 在人工决定时固定 evidence snapshot，Cleaning 的幂等输入包含该 snapshot 的版本化 canonical fingerprint，export 只消费这两份固定快照，不再重新选择 latest successful job。重跑形成新的 attempt identity；历史 Review 不会静默改变引用。

### P1：同步更新 export contract

决定 v2/v3 的边界：

- 如果 v2 继续作为 frame-level training data，row 或 metadata 至少应能回到 group/view、AI job/attempt/result、MediaReport、Review 和 Cleaning；
- 如果 v3 继续作为 group manifest，应明确其“manifest only”语义；Task C 已把 exact AI execution refs/digests 放进版本化 candidate_provenance，同时保留不导出 raw geometry 的边界；
- 每次 API/event/export schema 变更都要同步 OpenAPI、JSON Schema 和 compatibility tests。

### P1：补充 terminal evidence audit

AI success、NO_HAND_DETECTED、UNKNOWN/FAILED 和 retry 的 execution identity 已进入 Review/Cleaning/v3 provenance snapshot；后续若要增强独立审计检索，可再增加终态 audit event，但日志中仍不得放 token、signed URL、原始视频或模型文件。

### P1/P2：用回归场景验证血缘

至少增加以下测试场景：

1. 同一 ClipAsset 在 Review 后用新 model/profile 重跑，export 仍引用旧 evidence snapshot。
2. 同一 ai_job 出现 retry，candidate 能证明对应 attempt/result。
3. Media ingest 先于 group binding 或相反时，AI 自动排队/补排结果可解释、幂等且不会靠猜测补写 group/camera。
4. 多机位组中 candidate、primary interval、support view 和 Cleaning provenance 的关联可 round-trip 验证。
5. v2/v3 文件与数据库之间的 trace manifest 能在脱离业务 UI 后独立检查。

## 14. 最终判断

当前实现已经把 MediaPipe 限制在候选证据层，并用人工质量、AnnotationRevision、Review、Cleaning 和导出资格挡住了“AI 直接放行训练数据”的路径。Task C 又将 ClipAsset bytes 与 AI execution identity 收口为版本化 snapshot，同时保持候选 advisory 边界。

当前证据链的中心是 CaptureGroup 内按 ClipAsset 固定的 provenance snapshot，而不是一个会漂移的 latest-successful 查询。因而：

- **候选结果存储：有。**
- **project/ClipAsset 关联：有。**
- **通过数据库间接回到 CaptureGroup/camera/view：有条件地有。**
- **人工 Annotation/Review/Cleaning 链：有。**
- **从导出物稳定证明具体 AI job/attempt/result 与输入 ClipAsset SHA：已具备；从导出物独立取得 raw candidate geometry、Media Probe artifact 和原始对象引用：仍不包含。**

建议下一纵向切片只聚焦 evidence identity/snapshot 和现有导出/Review 的引用一致性；暂不新增通用工作流引擎、恢复未接线的 CaptureSync runtime，或重构现有异步作业基础设施。
