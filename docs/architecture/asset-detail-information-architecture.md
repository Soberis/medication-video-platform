# Asset Detail 信息架构提案

状态：设计提案 / 未实施

本文为 Asset Detail（`/projects/:projectId/assets/:id`）的后续实现提供信息架构、交互边界和分阶段路线。本文不修改生产代码，不新增 API、路由、状态机、权限或业务行为。

## 1. 设计约束

Asset Detail 是单个视频资产的工作台，不是仪表盘，也不是媒体库详情卡片。所有实现继续遵循 `docs/DESIGN_SYSTEM.md` 的 Linear-inspired Quiet Professional Workspace 与 Graphite + Medical Blue 视觉身份：

- 先呈现当前判断和下一步动作，再展开技术事实；
- 用平面 Section、列表和分隔线建立层级，避免 Card 套 Card；
- 状态必须来自服务端事实，不能由前端根据相邻字段推断业务结论；
- 播放、候选骨架、质量判断、正式标注、复核和清洗保持明确边界；
- 只在用户主动请求且服务端授权后创建播放器，不自动播放、预加载或伪造缩略图；
- 所有高风险操作继续受现有权限和确认流程保护。

本提案不改变当前行为：质量合格后由系统自动创建并分配标注任务，手部候选仅为辅助事实，人工复核和清洗仍是正式数据准入条件。

## 2. 当前实现审计

### 2.1 AssetDetailView 当前结构

当前页面已经具备一个可工作的纵向闭环，主要结构如下：

```text
面包屑
└─ 页面标题（视频详情、媒体状态、视频 ID、相机/拍摄信息、刷新）
   └─ 操作错误提示
      └─ 工作台双栏
         ├─ 主区
         │  ├─ PlaybackCard：按需播放、授权到期、骨架叠加、媒体恢复入口
         │  └─ 人工处理
         │     ├─ QualityReviewCard：人工质量判断
         │     └─ AnnotationTaskCard：自动分配后的标注任务事实
         └─ 侧栏
            ├─ Next action：当前唯一建议动作
            ├─ Workflow facts：媒体 → 标注 → 复核 → 清洗
            └─ 渐进披露：流程依据、手部候选
      ├─ 更多信息：媒体检测、文件信息、相机绑定、操作记录
      └─ 更多操作：删除等低频高风险操作
```

这套结构与当前产品闭环基本一致，后续工作应收敛重复表达，而不是重新拆成多个仪表盘卡片。

### 2.2 可复用基础组件

- `Section`：带语义标题和可选操作的轻量主区块；适合主区的状态、标注和元数据分组。
- `InspectorSection`：`Section` 的紧凑侧栏变体；适合下一步、状态、元数据和辅助信息。
- `MetadataList` / `PropertyRow`：语义化的 `dl` 标签/值集合；适合短字段、ID、时间和来源事实。
- `StatusIndicator`：表格和密集列表中的点状状态；不替代详情页中需要解释的状态徽标。
- `StatusBadge`：离散业务事实的文本徽标；用于工作流状态和质量结论。
- `WorkspaceFeedback`：统一的加载、空态和错误反馈。

当前 `AssetDetailSections.tsx` 仍使用 Ant Design `Descriptions` 展示媒体报告和视频信息。这不是重复组件问题：技术事实的二维布局与紧凑属性列表是不同密度。后续只有在字段分组稳定、需要统一复制/折叠行为时，才迁移到 `MetadataList`，不为迁移而增加包装层。

### 2.3 当前需要控制的重复

1. 页面标题、下一步面板和流程列表都可能重复同一状态。未来应保留“标题区简要状态 + 侧栏完整流程”两处必要表达，避免第三处同文案。
2. “查看标注任务”“继续人工标注”“人工复核”等动作必须由 `nextStep` 统一决定；主区卡片只提供与当前区块直接相关的链接。
3. 文件 ID、资产 ID、批次 ID、相机绑定和媒体技术报告应按用途分组，不在标题、侧栏和“更多信息”中重复完整值。
4. 手部候选只能放在辅助披露区，不能与正式标注状态使用同一视觉层级，也不能成为下一步准入条件。

## 3. 目标信息架构

### 3.1 页面级结构

```text
AssetDetailPage
├─ Breadcrumb
├─ PageHeader
│  ├─ h1：视频详情
│  ├─ StatusBadge：当前媒体状态
│  ├─ 视频名称 / 缩略 ID
│  ├─ 相机与拍摄时间（已有事实）
│  └─ 页面操作：刷新；删除放入低频操作区
├─ WorkspaceGrid
│  ├─ MainColumn
│  │  ├─ MediaReviewSection
│  │  │  ├─ PlaybackSurface（按需授权）
│  │  │  ├─ 播放反馈 / 到期提示
│  │  │  └─ SkeletonOverlayNote（有候选时才显示）
│  │  ├─ WorkflowSection
│  │  │  ├─ QualityReviewSection
│  │  │  └─ AnnotationSection（任务已确认后显示）
│  │  └─ OptionalEvidenceSection（必要时展开）
│  └─ Inspector
│     ├─ InspectorSection：下一步
│     ├─ InspectorSection：流程状态
│     ├─ InspectorSection：关键元数据
│     └─ InspectorSection：辅助候选（渐进披露）
└─ DisclosureGroup
   ├─ 更多信息：媒体报告、完整文件事实、相机绑定、活动记录
   └─ 更多操作：删除等低频高风险动作
```

### 3.2 主区职责

主区承载需要连续操作或需要较大阅读宽度的内容：

1. **媒体查看**：说明视频当前能否查看，点击后获取短期播放授权；播放器只使用局部授权状态。
2. **人工质量判断**：紧邻视频但与播放状态分离；保存结论后显示服务端确认的版本和结果。
3. **正式标注事实**：质量合格且任务查询成功后，显示自动分配事实和进入任务页的链接；不在详情页复制完整标注编辑器。
4. **证据和技术信息**：媒体检测报告、文件摘要、相机绑定和活动记录属于支持判断的证据，默认收起，避免首屏被技术细节占满。

主区不应出现：虚构缩略图、未授权播放 URL、批量操作、独立的“训练集已加入”结论或没有契约支撑的时间线编辑器。

### 3.3 Inspector 职责

Inspector 是“现在该做什么”的稳定索引，不是第二个详情页：

| 顺序 | 区块 | 内容 | 交互规则 |
| --- | --- | --- | --- |
| 1 | 下一步 | 当前唯一主动作、阻断原因、不可操作时的明确说明 | 由服务端事实和权限决定；无可执行动作时只读显示 |
| 2 | 流程状态 | 媒体、人工标注、人工复核、清洗四步及状态 | 每步显示文字状态；详细依据使用原生 disclosure |
| 3 | 关键元数据 | 来源、相机、拍摄/接收时间、短 ID、内容类型 | 采用 `MetadataList` / `PropertyRow`，完整值可复制或在 title 中查看 |
| 4 | 辅助候选 | MediaPipe 状态、候选数量和非真值说明 | 默认收起，不改变质量、标注或清洗准入 |
| 5 | 低频操作 | 删除、恢复检测等高风险动作 | 与正常工作流分离，保留确认、原因和权限守卫 |

Inspector 不重复媒体报告中的编码、码率、帧率等完整技术字段；这些字段进入“更多信息”。

## 4. 数据分组与状态来源

### 4.1 三层事实

```text
决策事实：当前下一步、质量结论、任务/复核/清洗状态
↓
操作事实：是否可播放、是否可记录结论、是否可进入任务页、是否可重试
↓
技术事实：媒体报告、文件摘要、相机绑定、活动记录
```

- 决策事实来自现有查询和工作流状态，不能通过多个页面请求的局部结果拼接成新结论。
- 操作事实必须同时考虑服务端状态、项目角色和权限；禁用按钮旁说明原因。
- 技术事实用于解释和审计，不应覆盖或替代正式工作流状态。

### 4.2 字段呈现优先级

首屏只保留：视频名称/短 ID、媒体状态、相机与拍摄时间、当前下一步、质量判断入口和已确认的任务事实。

展开后再显示：完整 UUID、SHA-256、批次和源上传文件 ID、编码/帧率/码率、同步声明、媒体警告和活动记录。列表和标题默认缩短 ID，详情提供完整值的可读方式，不让长字符串挤占判断信息。

### 4.3 状态表达

- 媒体：待检测、检测中、检测完成、检测失败；
- 质量：待判断、合格、不合格、需复核；
- 标注：已自动分配、待提交、已提交、标注完成；
- 复核：待复核、已通过、未通过；
- 清洗：待清洗、已通过清洗、需处理、未通过。

颜色只作辅助，文字状态始终可见；候选检测状态不能伪装成正式标注或质量结论。

## 5. Annotation 扩展点

当前详情页只负责把用户送入任务列表，不应提前实现标注编辑器。未来若产品契约允许在详情内提供上下文辅助，建议保持以下边界：

1. **位置**：主区播放器下方或独立的 `AnnotationSection`，不放在 Inspector 的狭窄状态行中。
2. **时间轴**：只展示已授权视频的当前时间、正式时间段和候选标记；时间轴是读取/定位工具，不自动写入正式标注。
3. **交互**：候选标记可定位播放时间；正式片段的创建、编辑、提交和复核仍遵循 Annotation Task 的路由与权限。
4. **数据边界**：AI 候选使用独立视觉层级并标明“辅助候选”；人工保存必须带版本/冲突处理，不使用浏览器本地状态冒充服务端结果。
5. **可访问性**：所有标记提供文本列表替代；键盘可定位片段，时间输入不只依赖拖拽或颜色。

在没有稳定时间轴、片段读取和冲突契约之前，不创建空的 Timeline 组件或占位操作。

## 6. 响应式与滚动策略

- 桌面使用主区 + Inspector 双栏，主区保持播放器和正文的可读上限；
- 约 1100px 以下按单列排列，DOM 顺序应保证“下一步”不会被技术披露埋在页面末尾；
- 页面禁止级联横向滚动；播放器按容器宽度缩放，长 ID 换行或提供 title；
- 若未来时间轴或表格确有超宽内容，只允许其自身容器滚动，不能让 `body` 或整个工作台出现横向滚动条；
- 目标视口继续覆盖 1366×768、1440×900、1920×1080，并检查窄屏回退不会裁切主操作。

## 7. 实施路线

### Phase 0：契约和查询确认

- 固定 Asset Detail 需要的服务端事实、版本字段、权限和错误码；
- 确认质量、标注、复核、清洗的状态来源和刷新边界；
- 不新增 UI，先补齐查询/契约测试缺口。

### Phase 1：壳层收敛

- 保留现有 `AppShell`、`PageHeader`、`Section`、`InspectorSection`；
- 将标题、下一步和流程区的语义关系固定下来；
- 只在真实重复出现时把局部标题/属性结构迁移到现有基础组件。

### Phase 2：媒体查看与人工处理

- 以现有 `PlaybackCard` 为媒体查看边界，保持点击授权、到期、重试和 Overlay 规则；
- 将质量判断与标注任务事实组织为一个主区 `WorkflowSection`，不改变保存和自动分配行为；
- 用真实状态测试覆盖加载、授权失败、冲突、权限和轮询。

### Phase 3：Inspector 和渐进披露

- 用 `InspectorSection` 收敛下一步、流程和关键元数据的间距/标题层级；
- 将完整技术事实和活动记录保持在“更多信息”中；
- 把删除/恢复等动作保持在单独的低频高风险披露区。

### Phase 4：可访问性与视觉验收

- 验证标题层级、`aria-labelledby`、状态文本、焦点顺序、键盘 disclosure 和错误恢复；
- 验收常用桌面视口，确认无页面横向滚动和主操作裁切；
- 保留现有 API/工作流测试，新增测试只覆盖真实 DOM 行为，不做 CSS 快照。

## 8. 明确不创建的抽象

- 不创建 `UniversalCard`、`UniversalContainer` 或带几十个 props 的 `AssetDetailLayout`；
- 不创建新的 `DataTable`、状态系统或全局 Store；
- 不为未来时间轴、批量动作、数据集页面创建未接线的空组件；
- 不把 `StatusBadge` 和 `StatusIndicator` 合并成一个难以表达两种密度的超级组件；
- 不在详情页复制 Annotation Workflow 的完整业务编辑器。

## 9. 验收标准

未来实现完成后，应能用以下问题验收：

1. 用户进入页面后是否立即知道视频是什么、当前状态是什么、下一步是什么？
2. 页面是否只有一个主下一步动作，且权限/阻断原因可解释？
3. 播放是否完全遵守主动授权、无预加载、无自动播放和到期重试？
4. 是否能区分媒体事实、质量结论、正式标注、人工复核、清洗结果和 AI 候选？
5. 是否避免重复 ID、重复状态和无意义的技术卡片？
6. 1366×768、1440×900、1920×1080 下是否无页面级横向滚动、裁切和控件重叠？
7. 键盘和辅助技术是否能完成主要动作并理解加载、错误和状态变化？

本文件完成后，下一步才是依据已确认的契约分阶段实现 Asset Detail；不在本任务中自动开始页面改造。
