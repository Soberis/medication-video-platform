# 固定多相机配药事件质量评审、标注与清洗用户流程

> 状态：P1 用户流程草案 / 未实施
>
> 本文只定义未来多相机工作流的用户体验和信息边界，不新增 React 页面、后端接口、数据库、状态机或
> 导航入口，也不改变当前 V1.24 P0 单视频闭环。示例使用 3–5 路固定相机；实际相机数量仍由服务端
> 已确认的采集归组事实动态决定。

本文遵循[设计系统](../DESIGN_SYSTEM.md)的 Quiet Professional Workspace 方向和[前端 UX 规范](./web-ux-and-frontend-guidelines.md)。
`CaptureGroup` 是面向操作人员的“一次配药事件”概念；实现时只能映射服务端明确的
`CaptureSession` / `capture_group_key`，不得由前端按文件名、上传顺序、时间邻近或相机号猜测归组。

## 1. 主操作旅程

```text
CaptureGroup 列表
    ↓
CaptureGroup 详情
    ↓
自动质量证据与每路建议
    ↓
人工查看各相机画面并确认视图
    ↓
有效视图继续；排除视图保留并停止下游处理
    ↓
以配药事件为单位完成正式动作标注
    ↓
人工 Review
    ↓
Cleaning
    ↓
可用数据
```

工作流的核心对象是“一个配药事件及其视图集合”，不是五个互相独立的训练样本。每一步都保留
`CaptureGroup` 身份和每路视图的处理结果，便于追溯、重看和后续按事件分组切分数据。

## 2. CaptureGroup 列表

列表是找工作和理解阻断原因的入口，不是统计仪表盘。使用现有工作台的 `PageHeader → Toolbar → Content`
层级，保持紧凑表格，不增加大面积 KPI 卡片。

建议列：

| 列 | 表达内容 |
| --- | --- |
| 配药事件 | `CaptureGroup A001`、采集时间和短 ID；完整 ID 可复制或展开查看 |
| 视图收件情况 | 预期相机数 / 已绑定或已入库相机数；明确“缺失”而不是显示为失败 |
| 相机视图摘要 | 可用、排除、需复核、待处理、缺失的紧凑文字计数 |
| 组状态 | 当前组状态及一句阻断原因 |
| 下一步 | 质量评审、继续标注、查看 Review 或处理 Cleaning |

只显示服务端已经支持的筛选，例如项目上下文、采集时间和组状态。列表不预加载所有视频，也不在浏览器
拼接多页视频推断组状态。缺路相机仍保留其预期编号，例如“相机 5 缺失”，不能把相机 6 重编号为 5。

## 3. CaptureGroup 详情

详情页使用“主工作区 + Inspector”，让用户先看懂整个事件，再处理一条相机视图。

```text
PageHeader
├─ CaptureGroup A001
├─ 组状态：需要复核 / 可进入标注 / 清洗中 / 可用数据
├─ 预期 5 路 · 已入库 4 路 · 当前有效 2 路
└─ 刷新；当前唯一下一步

紧凑相机矩阵
├─ Cam1  可用
├─ Cam2  建议排除 → 人工结论待确认
├─ Cam3  可用
├─ Cam4  需复核
└─ Cam5  缺失

工作区
├─ 主区：当前相机视频、媒体事实、手部证据、自动建议和人工动作
└─ Inspector：视图清单、组级状态、有效视图、下游下一步
```

### 3.1 当前相机视图

主区一次聚焦一条视图，避免把页面变成视频编辑器。顺序固定为：

1. 按现有授权规则点击后播放；不自动播放、不预加载未请求的视频；
2. 播放器旁显示基础媒体事实，如媒体状态、时长、分辨率和相机编号；
3. 显示已存在的 MediaPipe 手部候选证据，例如检测状态、候选数量和覆盖情况；候选是辅助证据，不是
   正式动作标签或质量结论；
4. 显示自动建议及其理由，例如“建议排除：画面大段不可用”或“建议复核：关键动作可能被遮挡”；
5. 提供三个清晰的人工操作：`确认可用`、`排除`、`需复核`。

缺失视图显示缺失原因和后续影响，不显示黑色视频框。技术检测失败、尚未检测和实际缺路必须使用不同的
文字状态。状态不能只靠颜色表达。

### 3.2 相机矩阵与 Inspector

相机矩阵是详情页的快速导航，不重复完整技术报告。每行显示：相机编号、视频是否已入库、人工结论、自动
建议、简短理由和是否进入下游。点击行切换主区视图；缺失行可查看接入事实但没有播放按钮。

Inspector 只回答三个问题：

- 哪些视图可以继续？
- 当前组为什么停在这里？
- 下一步是质量评审、标注、Review 还是 Cleaning？

完整 SHA、编码参数、上传事实和审计详情使用渐进披露，不与相机矩阵和主操作竞争。

## 4. 视图质量状态

自动建议和人工结论必须分成两层，不能把模型建议直接显示成“已通过”。

| 层次 | 状态 | 含义 |
| --- | --- | --- |
| 接入/技术事实 | 缺失 | 预期相机没有对应视频；不是删除，也不是媒体检测失败 |
| 接入/技术事实 | 待检测 / 检测中 / 检测失败 / 可查看 | 服务端媒体检查事实；不替代人工质量判断 |
| 自动建议 | 建议可用 / 建议排除 / 建议需复核 / 无法建议 | 根据可解释的媒体和候选证据给出的建议，不改变下游状态 |
| 人工结论 | 待处理 | 尚未确认该视图 |
| 人工结论 | 可用 | 人工确认该视图可支撑当前配药事件观察 |
| 人工结论 | 排除 | 该视图不进入本组下游处理，但继续保存和审计 |
| 人工结论 | 需复核 | 当前无法作出可靠结论，组或视图保持阻断 |

人工选择与自动建议不一致时，必须填写固定原因或简短说明。服务端应记录原建议、人工结论、原因、操作人、
时间和当时使用的证据/版本；页面只展示已确认的审计事实，不自行拼接历史。

## 5. 组质量行为

组状态由服务端根据预期视图、人工视图结论、媒体事实和当前工作流结果投影。前端不以“可用视图数量大于零”
自行推断组已合格。

建议的可见组状态：

| 组状态 | 进入条件和下一步 |
| --- | --- |
| 待质量评审 | 仍有待处理视图、缺路影响判断，或技术证据未完成；进入逐路评审 |
| 需要复核 | 至少一路明确标为需复核，或当前证据不足以确认视图用途；处理对应视图 |
| 可进入标注 | 服务端定义的最低有效视觉证据已经满足；只将人工确认可用的视图带入标注 |
| 证据不足 | 即使排除坏视图后，仍不足以观察所需配药动作；结束本组下游流程并保留原因 |
| 标注中 / 待 Review / Cleaning | 继承正式动作标注、Review 和 Cleaning 的服务端事实 |
| 可用数据 / 未通过清洗 | Cleaning 结论已确认；未通过时保留可修复原因，不删除组或视图 |

“最低有效视觉证据”必须由采集/任务配置或正式契约定义，例如所需视角或最低有效视图条件。没有该事实时，
页面只能显示“待确认”，不能默认要求所有相机可用，也不能默认任意一路可用就放行。

这里的“可进入标注”是未来 `CaptureGroup` 的服务端投影状态，不等同于 V1.24 单视频
`QualityReview.QUALIFIED`，也不会按每个视图触发逐视频自动 `AnnotationTask`；正式进入组标注前，
必须先冻结锚点任务或 group annotation intent 契约。

例：初始评审可以显示为：

```text
Cam1  可用
Cam2  建议排除
Cam3  可用
Cam4  需复核
Cam5  缺失
组状态：需要复核
```

人工确认后，如果结果为：

```text
Cam1  可用       → 进入下游
Cam2  已排除     → 不进入下游，继续保存和审计
Cam3  可用       → 进入下游
Cam4  可用       → 进入下游
Cam5  缺失       → 保留缺路事实
组状态：可进入标注（仅在最低有效证据满足时）
```

单个坏相机不应自动否定整个组；只有排除、缺失或损坏后没有足够有效画面观察所需动作时，才拒绝整个组。

## 6. 排除行为与删除边界

普通质量评审只做“排除”，不做“删除”：

- 排除视图仍保留原视频、绑定关系、原因、操作人、时间和审计记录；
- 排除视图不进入后续正式动作标注、Review、Cleaning 准入或训练数据投影；
- 组详情默认聚焦有效视图，但允许有权限的用户查看被排除视图及其证据；
- 若后续需要重新评审，应使用受控的重新评审动作，不覆盖历史结论；
- 物理删除仍是独立的管理员/保留策略生命周期操作，使用现有确认机制，不作为质量评审的快捷动作。

## 7. 配药动作标注

### 7.1 进入方式

组达到可进入标注条件后，从详情进入带有 `CaptureGroup` 上下文的标注工作台。现有 Annotation Workbench
仍是正式标注编辑入口；CaptureGroup 详情不复制一套编辑器。

### 7.2 第一版交互

- 默认显示一个聚焦相机，提供相机切换；
- 可选显示少量缩略视图用于对照，不强制同时加载 3–5 路完整视频；
- 只有同步证据可信时，才提供共享逻辑播放位置；
- 同步证据不足、声明未验证或时间误差不确定时，显示明确警告，并允许逐路查看，不把多个时间轴伪装成
  已同步；
- 每路可以独立显示 MediaPipe 21 点/骨架 Overlay；`handedness` 和候选只作辅助信息；
- 对一次配药事件创建一份正式动作标注和 AnnotationRevision，视图集合挂在事件上下文下，不要求为每路
  相机重复创建相同动作标签；
- 标注人可以用不同视图确认同一时间段，但正式动作标签仍来自人工 AnnotationRevision，而不是 Candidate。

如果未来真实场景证明“同一事件内不同相机的动作边界必须不同”，再以明确用例和契约评估视图级补充标注；第一版
不预建五套独立标签编辑器。

## 8. Review

Review 以配药事件的正式 AnnotationRevision 为对象，而不是把每个相机当成独立动作样本。复核界面应保留：

- CaptureGroup 标识和参与/排除视图清单；
- 当前正式动作时间段和标签；
- 可切换的有效相机画面；
- 被排除视图的只读原因和审计入口；
- Review 通过、退回或其他现有正式结果。

Review 不把自动建议、MediaPipe 候选或 handedness 当作人工通过依据，也不因存在一条排除视图就自动退回整组。

## 9. Cleaning

Cleaning 要回答：“这个已标注的配药事件，是否真的可用于下游训练？”它应同时检查：

1. 正式 AnnotationRevision 是否存在且内容完整；
2. Review 是否已通过；
3. 是否有足够的人工确认可用视图支撑所需动作；
4. 哪些视图被排除、缺失或仍有阻断，以及这些事实是否可追溯；
5. 参与视图的媒体完整性和必要技术事实；
6. 手部/画面证据是否足以辅助判断；候选仍是辅助证据，不能成为 Ground Truth。

建议结果语义：

- `PASS`：正式标签、Review、媒体和最低有效视图证据均满足，可进入“可用数据”投影；
- `WARNING`：存在需要处理或明确批准例外的非致命问题，不应直接当作训练可用；
- `REJECT`：当前事件缺少足够有效视觉证据或存在实质完整性问题；保留组、视图和原因，不删除对象。

单个相机的坏画面只影响该视图；若剩余有效视图仍能观察完整配药动作，Cleaning 不应拒绝整个组。只有在剩余视图
不足以支撑正式动作判断时，才将组判为不可用。

## 10. 部分坏数据与时间段排除

第一版默认采用整路视图排除：

```text
坏视图 → 排除并记录原因 → 其余可用视图继续
```

不默认建设片段级清洗编辑器。只有出现一个明确且无法用现有 Annotation 时间段、Review 或 Cleaning 事实处理的
真实工作流，例如同一路视频只有中间一段损坏且保留前后段对组结论有实际价值，才单独评估一等片段排除、审计和
下游投影语义。没有该证据前，不增加时间轴剪切、遮罩、批量修复或派生视频编辑能力。

## 11. 数据集安全

页面不提供 train/validation/test 切分控件，也不创建 DatasetVersion 或数据集构建器。但所有进入后续投影的
记录必须保留不可变的 `CaptureGroup` 身份和事件关联：

- 数据切分的最小防泄漏单位应是 CaptureGroup/配药事件，而不是单路视频；
- 同一事件的所有相机不得被拆到不同 split；
- 排除视图不能脱离原组作为独立样本重新进入下游；
- 导出或训练投影若需要 split，应由后续版本化规则在服务端/离线工具中按组执行，并保留规则版本。

## 12. 与当前工作区的衔接

本文不改变当前实现边界：

- `VideoManagementView` 继续是当前单路视频列表入口；本草案不新增 CaptureGroup 导航或列表路由；
- `AssetDetailView` 继续负责单个视频的授权播放、人工质量判断、手部候选和现有工作流事实；不在其中嵌入多相机
  组编辑器；
- 当前 `QualityReview` 是单个视频资产的人工质量结论。未来组视图结论不能把单视频 `QUALIFIED` 直接解释为整组
 通过，必须先有明确的组级查询/命令契约；
- 当前 Annotation Workbench 负责正式 AnnotationRevision、Review 和后置清洗事实。多相机第一版应增加组上下文和
 视图切换边界，而不是把编辑逻辑复制到详情页；
- 当前 post-cleaning 是按正式 revision 的受控结果。组级 Cleaning 只有在有效视图集合、排除事实和组级最低证据规则
 具备正式契约后才能启用；
- MediaPipe Candidate 始终是辅助候选观测，不是人工标注、Review 或 Cleaning 的替代物。

## 13. 有意延后

- 当前 P0 的 CaptureGroup/Session 列表、详情和多路同步播放入口；
- 以图像内容、ReID、三维融合或 handedness 推断跨相机身份；
- 未经验证同步证据的共享时间轴、自动对齐和跨相机帧匹配；
- 复杂多路视频编辑器、剪切、遮罩和片段级排除；
- 批量质量评审、自动质量策略、批量预标注和新的后台队列；
- 在详情页编辑正式标注、重复创建每路动作标签或自动把 Candidate 转成 Ground Truth；
- DatasetVersion、数据集构建、LeRobot 和页面内数据切分控制；
- 用删除代替质量排除，或因单个坏相机自动拒绝整个事件。

未来实现前的最小前置条件是：冻结 CaptureGroup/视图集合查询事实、人工视图结论与审计契约、组级最低有效证据规则、
同步证据语义，以及 Annotation/Review/Cleaning 如何引用有效视图的版本化契约。本文不因这些前置条件存在而授权代码实现。
